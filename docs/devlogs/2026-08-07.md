## The WRAM binary runs on hardware, first attempt

*2026-08-07 02:22*

Snapshot at 0x027FEF10: wramMagic reads RAH1, wramTicks 2701, wramState 02
(RA_WRAM_CALLED). The whole chain -- built, packed into the .nds, staged at
0x02600000, copied to 0x03740000, recognised as code, called, executing, writing
back -- works end to end.

The strongest part is that ticks also reads 2701. The two counters are in exact
lockstep, so the WRAM binary was called on every frame since boot with none
dropped; an intermittent call would leave wramTicks behind. linesMax stayed at 1,
so the jump into WRAM costs under a scanline.

It also settled the two things no amount of reading could.

0x02600000 really was free. That address came out of reading the bootloader's early
clear list rather than the address constants -- the same reading that caught
0x02700000 being the FAT table cache. Had it been wrong, this would have corrupted
the bootloader's own file tables.

And the colour LUT's retail path works. The block this mirrors hands WRAM to the
ARM7 only in DSi mode, so for a plain DS game the ARM7 writes 0x03740000 with no
handover at all, and whether anyone had ever exercised that path was the largest
unknown in the design. It works, and the MBK mapping survives into gameplay too,
since the ARM9 cardengine reaches the same window afterwards.

What it changes: the cardengine's 28-byte margin stops being the binding constraint
on the project. rcheevos at 48K, a real font, the overlay rewrite, a control
measurement for the per-frame cost, and the reader itself all now have somewhere to
go. The handoff section is updated with the order worth doing them in -- moving the
watchlist first, because it is the smallest thing that both reclaims real room and
proves the window holds state rather than only code.

## Move the watchlist into DSi WRAM, and test whether that window holds state

*2026-08-07 02:32*

First real payload for cardenginei_arm9_ra, and chosen first deliberately: it is
the smallest useful thing to put there, and it tests the one property nothing had
tested. wramTicks is now the WRAM binary's own counter, kept in its own .bss and
copied into the snapshot each frame rather than incremented there -- so if that
window does not persist state between frames it sticks at 1 while ticks climbs.
Finding that out with a watchlist costs a flash cycle; finding it out with rcheevos
half-integrated costs a week.

Moved: the descriptors, the chain walker, the range checks, the add/clear API.
Stayed: the snapshot, the per-frame entry point, the bridge, the overlay.

  ra_reader.o text        648 -> 188
  cardenginei_arm9 free    28 -> 476
  RA_WATCH_MAX              2 -> 16

The snapshot could not move with it. It is the only debug channel this project has,
it is read at a fixed cardengine address the RAM viewer is known to reach, and
keeping it there means the counters still work when the WRAM binary is absent --
which is exactly when you most want to see them. So the WRAM binary owns the
watchlist and mirrors the first RA_RESULT_MAX results into the snapshot in a
12-byte form that drops base and offsets: those are static configuration, and if
they were wrong the address would not resolve, which status already says.

One thing that had to change rather than move. The self-test chain's cells used to
sit beside the watchlist, but a pointer the walker follows must be a main RAM
address and this binary runs from 0x0374xxxx. Relaxing that check to accommodate
our own cells would have weakened it for the game addresses it exists to guard, so
the cells moved into the snapshot -- selfCell and selfCellPtr -- and the WRAM binary
fills them in, being the only side that knows the address.

The host test followed the code: it now compiles arm9_ra/source/cardengine.c
verbatim instead of the cardengine's reader. That is the point of pointing a test at
a source file rather than an interface. It gained coverage on the way -- 16 slots
filling and refusing, only the first four mirrored, and a watch aimed at the WRAM
window itself being refused, since ra_readable() deliberately excludes it.

Snapshot layout bumped to RA2S and moved to 0x027FED50, since the cardengine shrank.

## Give the WRAM window a C library: the crt0 it does not have

*2026-08-07 02:57*

First step towards rcheevos, and it needed something nobody had had to do here yet.

rcheevos calls malloc. There is no crt0 in this window -- the bootloader copies the
image and jumps in, and that is the whole of the startup. .text, .rodata and .data
are inside the image and arrive correct; .bss is not, so it arrives as whatever the
previous occupant left, with staging garbage written over it besides since the loader
copies a fixed length rather than the exact image size.

Everything written for this window so far coped by guarding on a magic and
initialising by hand. newlib will not: its allocator keeps state in .bss and assumes
it starts zeroed, like every C library, and handing it garbage does not fail cleanly
-- it corrupts a heap, which would surface much later as rcheevos misbehaving for no
visible reason.

So startup.c is the crt0 this window lacks. It zeroes .bss once per boot and gives
newlib a heap over the rest of the window through _sbrk(). Measured: 5,836 bytes for
malloc alone, an 18,212-byte image against the 64K the loader copies, and a 237 KB
arena left over. newlib's .data is the surprise at 5,636 bytes -- the reentrancy
structure -- but it is in the image, so it is paid for rather than a risk.

Two decisions worth the words.

The "have we started" flag lives in .data rather than .bss. A .bss flag also works,
but only if written after the zeroing clears it, and that is a subtle ordering
dependency in code that runs once per boot inside an interrupt handler -- nobody
would notice it breaking. .data is initialised from the image on every boot, which
makes this the one claim in the project that is not a bet on garbage not coinciding
with a magic.

And ra_startup() takes the arena bounds as arguments instead of reading __bss_start
and friends itself. That came out of writing the test: the symbols are arrays on the
target and a host test cannot alias them, and rather than stub the one function whose
failure mode is a corrupted heap, the bounds became parameters. The test now exercises
the real zeroing and the real arena arithmetic against a scratch buffer, plus _sbrk
handing out the arena and refusing to overrun it.

The allocator is proven rather than assumed: the first block is written across its
whole length, read back at both ends and freed, and the stage only advances if that
worked. wramStage reports how far it got -- 01 .bss zeroed, 02 arena measured, 03
allocation verified, 04 watchlist running -- so a failure names its own stage.

Snapshot grew by 12 bytes at the end (heapSize, heapUsed, wramStage). Appended rather
than inserted, so every documented offset keeps its address and the magic did not
need another bump.

## Confirmed: newlib runs in the WRAM window, and releases memory too

*2026-08-07 03:04*

wramStage reads 04 on hardware, heapSize reads 243,064 exactly, and the watchlist
still resolves. The C library is up in that window.

heapUsed came back as 4 bytes against a predicted few KB, and being wrong about it
was the useful part. _malloc_trim_r was in the linked symbols: when the probe frees
its 1 KB block, newlib hands the memory back through a negative _sbrk. So the
sequence was sbrk(+4) to align, sbrk(+1052) for the block, sbrk(-1052) on free,
leaving the alignment adjustment behind.

Which means the allocator releases as well as allocates -- and that only works
because _sbrk() bounds-checks growth rather than any change:

    if (incr > 0 && heapBreak + incr > heapTop)

The incr > 0 was deliberate, with a comment saying newlib is allowed to hand space
back. Had the check ignored the sign, trim would have failed and the heap would have
fragmented quietly: invisible until a long session ran out of memory it should have
had. Worth recording because the reading is what confirmed the guard matters, not
the reasoning that put it there.

Two smaller notes. wramTicks was one behind ticks, which is benign -- the cardengine
increments ticks early in the tick and the WRAM binary writes wramTicks later, so a
viewer reading a live buffer can land between the two. Earlier readings matched
exactly by timing luck; what matters is that they track. And linesMax stayed at 6, so
newlib and the heap cost nothing per frame: the startup runs once and the per-frame
path is unchanged.

## rcheevos evaluates a real achievement definition

*2026-08-07 03:33*

The library every official RetroAchievements integration uses, running inside
a DS game's interrupt handler. In as a submodule pinned at v12.4.0 rather than
vendored: the definition syntax evolves server-side, and a vendored copy would
quietly stop understanding definitions the website still produces.

Only the runtime is compiled -- a whitelist, not a blacklist, since upstream's
file set grows. rc_api, rc_client and rhash beyond md5 stay out.

Three things the DS makes different, and all three are in the code rather than
in a comment about future work:

Definitions come from the network, so peek() routes every read through the
same ra_readable() the watchlist uses. One answer in this binary to "may this
address be read" -- an address from the server does not get a weaker check
than a hand-written watch, which is why ra_readable() and ra_read() stopped
being static. A refused read returns zero and is counted, because peek() has
no error channel and zero makes the condition false, which is the safe
direction. rc_runtime_validate_addresses() disables an unsupportable
achievement up front as well; both layers are needed, since a definition can
compute an address at run time through AddAddress.

RetroAchievements addresses are console addresses. Translated with our own
three-line DS map rather than rc_console_memory_regions(), whose switch
references the table for every console it supports. Data TCM is deliberately
refused, not guessed: its base is whatever the game put in CP15 c9,c1, so a
guess would read someone else's memory and return plausible values.

The ARM9 rotates unaligned loads instead of faulting, so multi-byte peeks are
assembled from bytes. Authors write unaligned reads and the server serves
them; refusing would break real definitions and trusting the hardware would
return nonsense that looks fine.

The definition under test is real syntax, not a stub:

    M:0xX{ticks}!=d0xX{ticks}.600.

It exercises a 32-bit memref, a delta memref, a hit target and the measured
flag, and it is observable by eye -- rcMeasured climbs one per frame toward
600, so a hex viewer shows rcheevos evaluating rather than merely present.

Also here, because the size work turned one up: nothing checked the built
image against the fixed length the loader copies. At 68K against a 64K limit
it would have been copied truncated -- booting correctly, since the branch at
+0 survives, then failing inside code that is not there, undetectable at run
time. The Makefile now fails the build and prints the budget. The limit went
to 128K; 20K of the 68K is newlib printf reached through
rc_update_richpresence(), a call site statically reachable from do_frame()
that never executes. Carried rather than cut, and documented as a measured
20K available if space ever gets tight.

Host-tested, not yet read on hardware. tools/ra_reader_test.sh compiles
rcheevos too and covers the parse, the translation at both ends of system RAM,
the DTCM refusal, unaligned assembly across a known two-word straddle, and
rcMeasured both climbing and stopping when the value stops changing.

## ra_startup() reported a dead heap as a working one

*2026-08-07 03:51*

Found from the first hardware reading of the rcheevos block. It said
rcStage = 01 (NO_MEMORY) -- rcheevos could not allocate 32 bytes -- next to
heapSize = 0x2F27C, exactly the 193,148 bytes predicted. Two numbers that
cannot both be right.

heapUsed read 0, which is the tell: if malloc had ever gone through _sbrk it
would have left at least the top chunk behind, so the break never moved and
the malloc(1024) probe in ra_startup() had failed. But wramStage read 04, which
requires the probe to have succeeded.

Both are explained by one line. ra_startup() sets its "already ran" flag
before running the probe, then returned RA_STAGE_ALLOC unconditionally on every
later call. So a probe that failed on frame 1 was reported as a working heap
from frame 2 onward, and every stage above it read as healthy over a dead heap.
It now remembers the stage it actually reached, in .data alongside the flag for
the same reason: written once per boot, read on every call, must not depend on
the .bss zeroing.

That is the bug. Why the probe fails is still open, so this also makes the next
reading decisive rather than ambiguous. The snapshot now carries _sbrk()'s own
two numbers plus both probe results, and ra_startup() asks _sbrk() directly
before giving up. A non-zero sbrkProbe beside a zero mallocProbe puts the fault
in newlib; both zero puts it in the arena bookkeeping. The old reading could
not distinguish these, which is why it cost a cycle.

Two smaller things found on the way. The arena base is now rounded up to 8:
__bss_end is only guaranteed 4-aligned and landed on 0x03750D84, so dlmalloc
was correcting the misalignment by asking _sbrk() for the difference -- which
is where heapUsed = 4 in an earlier session came from. And RA_RC_NO_MEMORY no
longer covers two different failures; rc_runtime_init()'s allocation failing is
now RA_RC_NO_MEMREFS.

The host test now covers the regression, which it could not before: the runner
links with -Wl,--wrap=malloc so the probe can be made to fail, and the test
asserts the second call still reports RA_STAGE_HEAP. Confirmed to fail against
the old code and pass against the new.

## Our own allocator, because newlib's does not work in this window

*2026-08-07 04:05*

The second hardware reading settled the question the first could not. _sbrk()
returned exactly the predicted base address, heapSize matched the prediction to
the byte, and heapBreak had moved by exactly the 64 bytes of the diagnostic
probe and nothing else -- while malloc(1024) refused. So newlib's allocator
declines without ever calling _sbrk() successfully, and whatever it is unhappy
about is inside newlib.

Rather than keep guessing at it, ra_alloc.c replaces it: first-fit with forward
coalescing over the whole arena, 8-byte aligned payloads because rcheevos keeps
64-bit values in its typed-value union. Four reasons that hold regardless of the
bug -- it is testable on the host, where newlib's was not and which is exactly
why this cost two flash cycles; it is deterministic, which matters in a VCOUNT
handler; it needs no crt0; and what rcheevos asks for is ~1K per achievement at
load time and nothing per frame, so the O(n) walk never touches the per-frame
path.

_sbrk() now refuses everything. The arena has exactly one owner -- two
allocators sharing one range is corruption that only shows up under load. It
cannot be deleted outright because newlib's snprintf is still linked, and
through it _malloc_r, which references _sbrk_r.

It did not save the 20K, and the commit that guessed it might was wrong about
that: the image went 68,272 -> 68,776. _malloc_r, _free_r and _vfiprintf_r are
still linked and unreachable, pulled in by that same snprintf reference. Cutting
them is still one separate job.

The probe in ra_startup() calls ra_alloc_malloc() directly, so the host test
exercises the shipped code path. That also made --wrap=malloc unnecessary: the
regression test for the lying stage now drives the failure by handing
ra_startup() a window with no room past .bss, which is a real condition rather
than a mock. Two stale assertions about _sbrk's break were caught by the test
and corrected -- ra_heap_used() reports the allocator now, not the break.

Host test covers allocation, alignment, non-overlap, coalescing, splitting,
exhaustion, double free, out-of-arena pointers, realloc growth and preservation
of the original on failure, and calloc zeroing and overflow refusal.
