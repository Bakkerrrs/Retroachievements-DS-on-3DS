## It is only ever visible on BG0, and now it says so instead of drawing into nothing

*2026-08-10 00:16*

overlayDispcnt finally came back, from a pulse during stage 1 gameplay: 0x00211E10. BG mode 0, no
forced blank, **BG0 off**, BG1/BG2/BG3/OBJ on, no window active, display mode graphics, extended
palettes off. That pulse read overlayState 0x08 -- layer 0 -- and was plainly visible. Both real
unlocks read 0x4A -- layer 1 -- and were never seen.

So the answer had been sitting in a hypothesis I killed on an assumption rather than a measurement.
I said "the pulse is visible during gameplay, and during gameplay the game certainly has BG0 on, so
the layer cannot be it". The "certainly" was never measured, and it was wrong: Contra 4 runs stage 1
with its sub BG0 switched off.

The DS orders backgrounds by BGCNT bits 0-1, lower value in front, and breaks ties by layer number.
The overlay takes priority 0 -- the strongest there is -- so it beats any enabled layer at priority 1
or worse and loses to any lower-numbered enabled layer at priority 0, with nothing below 0 to reach
for. chooseLayer() was returning the first layer the game had switched off; on BG0 that is
unbeatable, on BG1 it is behind the game's BG0. Free and hidden looked exactly like drawn-and-lost.

chooseLayer() now refuses a layer it knows would be covered, as one loop rather than a nested
search: walking in order, the first free layer is usable if and only if no earlier enabled layer
holds priority 0.

What that buys is honesty -- an invisible notification becomes a counted denial, `denied` and
`deniedNoLayer` both move, and overlayDispcnt names the layer that blocked it. What it does not buy
is a notification at the moment that matters, because at the start of stage 2 the game's BG0 is on.
That needs either borrowing BG0 anyway (saving and restoring its registers, never touching its VRAM,
so the layer's content is intact and merely absent for three seconds) or moving to sprites, which
draw above every background at the same priority and work regardless of the game's layers.

The same reading closed the other two doors it was added to test: no window active, so overlayWindow
reading 0 is a fact rather than an accident; display mode graphics; no forced blank. The gate
conditions were fine at that moment -- they were only ever wrong during the transition, which is a
separate and already fixed problem.

The priorities themselves are not published and do not need to be: a denial at layer N together with
N's enable bit in overlayDispcnt says the priority was 0 by construction. Publishing the four BGCNT
registers took the window 92 bytes past its end; a packed priority byte still took it 24 past.

Snapshot back to 0xC0 at 0x027FEEA0, 44 bytes free. Host suite 611 assertions, 0 failures; both
RA_LAUNCHER_WIFI=0 and =2 build.

## Take the layer it needs to be seen on, and stop refusing

*2026-08-10 00:20*

The honest refusal from the last commit was measured to deliver nothing: at the start of stage 2 the
game's BG0 is on at priority 0, and that is exactly when the stage-1 achievement's notification is
due. A notification that is correct and never appears is not a notification.

chooseLayer() now returns the first layer that is either free-and-reachable or enabled at priority 0,
taking the second kind rather than giving up. What that costs is bounded and reversible, and both
halves matter: the layer's VRAM is never touched -- the overlay points its character and screen bases
at a block of its own, so the game's tiles and tilemap for that layer sit there untouched throughout
-- and every register taken is put back by hide(), BGCNT, both scroll registers and the enable bit.
So the layer's content is intact the whole time and simply does not display for the three seconds the
notification is up. On Contra 4 that is part of the bottom-screen map.

The all-four-enabled-and-none-at-priority-0 case is now handled rather than denied: the overlay
outranks every one of them, so any layer will be seen and the last is as good as any. `return -1`
there would have been a refusal with nothing actually in the way.

Two consequences, written down before the next run rather than after it:

deniedNoLayer is retired at 0, like rearmDispstat. chooseLayer() cannot fail any more, so a whole
category of denial is gone; if that field ever moves again, something reintroduced a refusal.

And the "who writes last" race comes back, possibly as flicker. Displacing an *enabled* layer means
the game is still writing that layer's BGCNT from its own code while the overlay re-asserts it once
per frame from VBlank, and whoever writes later in the frame wins it. This is the same mechanism that
flashed the notification one frame in twelve on the old VCOUNT hook. Stated as a prediction so the
next reading can confirm or kill it instead of it being explained afterwards.

Sprites remain the answer that costs nothing -- an OBJ at a given priority draws above every
background at that priority, whatever the game does with its layers, and disturbs no layer at all.
That is the next piece of work; this stays as the fallback for when no object slot is free.

Snapshots: 0x027FEE90 without the pulse (60 bytes free), 0x027FEEB0 with it. Host suite 611
assertions, 0 failures; both RA_LAUNCHER_WIFI=0 and =2 build.

## Move the overlay to DSi WRAM, where sprites can be written

*2026-08-10 00:37*

Sprites are next and they were never going to fit. OAM negotiation, an object-VRAM survey and a
gather blit, against an ARM9 cardengine window that had 60 bytes free and had already refused a
four-byte diagnostic field twice. This is the move docs/retroachievements.md has been predicting
since phase 1, finally forced.

The window went from 60 bytes free to **1,228**, and it cost nothing: this binary is called once a
frame from the same VBlank hook, so the overlay runs exactly as often as it did.

Two things came free with it. The trigger count is now *this* frame's rather than last frame's, so a
notification is raised on the frame the achievement fires instead of the one after. And the rendered
strip is a neighbour's pointer instead of an address crossing a binary boundary, so the range check
that guarded it is gone -- there is nothing left to distrust.

A third thing came free that will save me from a mistake I have already made twice: **the snapshot
address no longer moves between the normal and pulse builds**. It is 0x027FEA00 for both, because the
code the demo flag changes is not in the cardengine any more.

The layering is unchanged. ra_overlay_tick() is still handed a count and some pixels and nothing
else; cardengine.c on this side publishes the counters into the snapshot exactly as ra_reader.c did
on the other. The overlay still knows nothing about RetroAchievements.

RA_OVERLAY_DEMO moved to arm9_ra's Makefile, which is not bookkeeping: left where it was it would
have been a flag reaching nothing, and the pulse probe would have stopped working silently -- the
exact failure its own comment warns about. Verified by checking demoCounter is in the object with the
flag and absent without it.

STATE_MAGIC is kept even though this binary's .bss *is* cleared by ra_startup(). Four bytes of a 256K
window, and it is the only thing that would notice if that stopped being true.

Host suite 611 assertions, 0 failures -- ra_overlay.c now compiles on the host too, since the test
links it. Both RA_LAUNCHER_WIFI=0 and =2 build. No behaviour change intended.

## Sprites: the path that costs the game nothing

*2026-08-10 00:44*

An object at a given priority is drawn above every background at that priority, whatever the game is
doing with its layers. So it does not have to take a layer at all -- and what it does need, a disabled
OAM entry and a range of object VRAM nobody references, it can *find* rather than borrow. The
background path stays as the fallback for when neither can be found.

Eight objects of 32x16, which is 256x16 -- exactly the 32x2 tiles of the strip. Eight rather than four
64x32 ones because 64x16 is not a shape the DS has, and four of the larger size would reserve twice the
object VRAM to leave half of it blank.

Object VRAM is claimed in 2K units and only the first 16K is ever considered. That is a mapping
question, not tidiness: how much VRAM sits behind 0x06600000 depends on the game's VRAMCNT, and a write
past the end does not fail -- it mirrors, onto tiles the game *is* using. OAM entries are taken from the
front, because objects are ordered among themselves by OAM index and lower is in front; that is the same
tie-break that made backgrounds invisible, one level down.

Three places this refuses to guess and falls back instead. 2D mapping addresses object tiles as a
32-wide matrix rather than consecutively, so the arithmetic here is wrong for it. Objects disabled would
mean enabling them, and a game that keeps them off may have an OAM full of entries it never intended to
be seen. And attr3 is never written at all: the fourth halfword of every OAM entry is part of the
interleaved affine matrix table, so a disabled entry's may hold a live parameter for a sprite the game
is rotating.

"Disabled" is exact rather than approximate: with the rotation flag clear, attribute 0 bit 9 is the
disable bit, so (attr0 & 0x0300) == 0x0200 and nothing else means off. With the rotation flag set, bit 9
means double-size and the object is live -- reading that pair as one field would treat every double-size
affine sprite in the game as free.

**Insurance against reading the boundary wrong.** In 1D mapping the tile number steps by the boundary in
DISPCNT bits 20-21; the classic reading, and the only one the GBA had, is a flat 32. Contra 4 sets 128.
If that is wrong in the direction of too large, the game's tiles appear further out than they are, the
survey calls a slot free that is not, and the blit writes over somebody's sprite. So the survey marks
the union of both readings -- one extra range per entry, and it makes that impossible. A free slot
becomes slightly rarer, which is a fallback rather than a fault.

The overlay's own placement is not exposed to the same risk, by construction rather than by luck:
spriteBlit() writes to the byte address of the slot the survey approved, computed without reference to
the boundary at all. A wrong boundary would make our objects *read* their tiles from the wrong place --
a notification of visible nonsense -- and could never make them write to it.

The eight entries are rewritten every frame the notification is up, because a game that keeps a shadow
OAM and DMAs the whole thing each frame would otherwise wipe them; and the claimed slot is re-surveyed
every frame and given back on eviction, for the same reason the character block is.

overlaySpriteOam and overlaySpriteSlot say which path ran and what it took, 0xFF meaning the background
path. A separate field rather than another bit of overlayState, because an object has no layer and no
character block -- reporting through those bits would make "objects" indistinguishable from "layer 0,
block 0".

An invalid object shape (3, prohibited) is measured as the largest object there is rather than the
smallest: one that under-stated its footprint would let the survey call somebody's tiles free.

Snapshot 0xC0 -> 0xC4 at 0x027FEA00, the same address with and without the pulse. Host suite 613
assertions, 0 failures; both RA_LAUNCHER_WIFI=0 and =2 build.

## "Disabled right now" did not mean "not wanted": take OAM from the back

*2026-08-10 00:56*

The sprite path worked and stopped eating scenery, and immediately started eating something worse. On
Contra 4 the notification appeared with no background lost and the game began **losing sprites** --
bullets, and sometimes the player -- erratically, for exactly as long as it was up.

That is my design decision, not an accident. I took OAM entries from the front, reasoning that objects
are ordered among themselves by index and lower is in front, so the earliest free entries would be the
least likely to be covered by the game's own sprites. The reasoning was sound and the premise was
wrong: I read "disabled right now" as "not wanted".

A game builds its object list from index 0 upward each frame, writes as many entries as it has sprites,
leaves the rest disabled, and DMAs the whole thing in its own VBlank handler. Ours is chained after
that, so whatever the game had just put in the eight entries we hold is overwritten before the screen
is drawn, every frame. The entries were not free. They were the next ones the game was going to need,
which is why the loss tracked the action -- more bullets on screen, more reach up the list.

Nothing avoids that except choosing entries the game does not reach, and the back is where those are.
Stealing from 127 downward only costs a sprite when the game is already using more than 120; stealing
from 0 upward cost one almost immediately.

What it gives up is being in front of the game's own sprites: at index 120 the overlay is behind nearly
all of them, so a bullet crossing the text wins that pixel. A fair trade twice over -- text with a
bullet through it is legible, and a deleted bullet is a bug. And it gives up nothing that matters,
because an object still beats every background at the same priority, which is the entire reason for
this path.

One loop direction, and the reasoning that chose the wrong one is kept beside it rather than replaced,
because it is the kind of mistake that would otherwise be made again.

Host suite 613 assertions, 0 failures; both RA_LAUNCHER_WIFI=0 and =2 build. Snapshot unchanged at
0x027FEA00.

## Teach the VRAM survey to read the BG mode

*2026-08-10 02:05*

surveyBlocks() read all four BGCNT registers as though every one described a
text background: character base in 16K units, screen base in 2K, map size from
bits 14-15. It never consulted the BG mode or the colour-depth bit, so three
things were misread, and they fail in both directions -- a block wrongly left
clear is one the overlay may take and corrupt, a block wrongly marked is a
notification denied for nothing.

  - An affine map is one byte per entry, not two. At size 3 that is 16K, a
    whole block, where the text reading says 8K.
  - An extended-affine map is affine-shaped with two-byte entries, so size 3
    is 32K -- four times what the text reading allowed.
  - A bitmap's base is the screen-base field in 16K units, not 2K, and bit 2
    is its colour depth rather than the low bit of a character base. So the
    survey looked in the wrong block entirely, marked a character block that
    does not exist, and missed the blocks the bitmap actually covers.

Split the decision from the registers it used to read. raOverlaySurvey() takes
DISPCNT and the four BGCNT values and is pure; surveyBlocks() is now a wrapper
that samples the registers and calls it. That split is what makes it testable,
and testing is the only way this gets verified: Contra 4 runs in BG mode 0 --
measured, overlayDispcnt came back 0x00211E10 -- where every layer is text and
the old reading is correct by accident. Seeing the bug on hardware would mean
finding a game that puts a non-text background on the sub engine and then
earning an achievement inside it.

The size tables and the 16K-unit bitmap base come from libnds' own headers
rather than from memory: bgInit() asserts "Tile base is unused for bitmaps.
Can be offset using mapBase * 16KB", and bgInitSub() asserts "Sub Display has
no large Bitmaps", which is what rules out mode 6 here.

Two deliberate choices. A mode this engine does not have marks every block
used, so the notification is denied -- the same trade the rest of the survey
makes. And a base pointing outside the 128K window matches nothing rather than
being folded back into it, because guessing how the hardware wraps it would be
an unmeasured assumption.

Still a heuristic and documented as one: tile data is marked as a single 16K
block. How far a character base reaches is not in any register, and the worst
case -- 64K of 256-colour tiles -- would deny nearly every notification.

35 new host assertions cover every mode, both affine kinds, both bitmap
depths, the out-of-window bases and the unusable modes. Suite 642 assertions,
0 failures; builds clean at RA_LAUNCHER_WIFI=0 and =2; snapshot still at
0x027FEA00 with 1224 bytes free, the 12K window untouched.

## Send o= on r=awardachievement, so an unlock is dated when it was earned

*2026-08-10 03:02*

An achievement earned at nine in the evening and submitted at eight the
next morning was recorded by the server as an eight-in-the-morning unlock:
the only time in the request was the moment it arrived. This client is
exactly the case o= exists for, because it cannot reach the network while a
game is running and always reports at least one boot late.

Two things the plan for this got wrong, and both cost more than the rest.

The RTC is not usably in sharedAddr[7]/[8]. Those hold hours and minutes
only, and only while the in-game menu is open, because the menu is what
fills them -- no date, no seconds, and nothing on the frame an achievement
fires. The cardengine reads the RTC itself with rtcGetTimeAndDate().

And o= changes the signature. rcheevos normally hashes id + username +
hardcore; when o= is sent it appends the id a *second* time and then the
seconds, with its own comment explaining that the server overloads its hash
generator that way. o= with the old digest is refused, and refused with a
message that says nothing about which half was wrong. raQueueSign() takes
the seconds and switches URL and digest together so they cannot disagree.

The record becomes <id>\t<YYYYMMDDhhmmss>\n, which grew it from 16 bytes to
32 and the file from 1,024 to 2,048. It migrates itself: the launcher reads
whatever length it finds and always writes RA_QUEUE_BYTES back. The stamp
is optional, so a bare id -- typed by hand, or queued by an older build --
parses as it always did and is sent without o=, which keeps the file
hand-writable and makes the upgrade a non-event.

The cardengine writes digits and does no arithmetic; the launcher does the
calendar. Leap years, month lengths and the epoch stay on the side that has
a host test, and the side running inside a game stays a copy loop.
raUnlockStamp() is called outside the unlock's critical section on purpose:
that section runs with IME off while an ARM9 card read may be waiting, and
two SPI transactions do not belong in it.

rtcGetTimeAndDate() returns integers rather than BCD -- it masks the
12/24-hour bit and calls BCDToInteger(t, 7) itself, read out of the
disassembly of libnds7.a because the header says nothing and the in-game
menu's use of it is ambiguous. It does not normalise the PM flag in
12-hour mode, where the hour arrives with 40 added, so that is subtracted.

Anything implausible sends no o= at all: no stamp, a clock that was never
set, a clock that moved backwards, or a gap over a year. A wrong time would
be worse than the old behaviour; no time merely is the old behaviour. The
log says which, because o= is the one number in the request that nothing
downstream can check -- the reply does not echo it back.

Suite 690 assertions, 0 failures; 48 new, with the conversions pinned
against date -u +%s and the o= digest against md5sum rather than against
this code. Builds clean at RA_LAUNCHER_WIFI=0 and =2. ARM7 cardengine
47,892 of 62,464 bytes; the ARM9 window is untouched, snapshot still at
0x027FEA00 with 1224 free.

## A queued unlock names the game it came from

*2026-08-10 14:21*

Groundwork for listing pending unlocks in the in-game menu, and it began as
a question: what happens if the queue holds more than one game?

Submission was never broken. a= is a globally unique achievement id and
this client sends no m=, so an unlock from game A submitted while booting
game B reaches the right achievement. The project's own files show the id
space is global -- 101000001, the Unknown Emulator notice, appears in the
set for GameID 14856 and again in a boot of GameID 12917.

Two things were. A pending list cannot exist without knowing which game an
unlock belongs to. And the launcher's rule that an answer clears a record
means that if the server ever refuses an award for being outside the
current game's session -- not measured either way -- the record is cleared
and the unlock is gone with nothing said. Naming the game is what makes
that case visible.

gameCode and gameTitle are the first sixteen bytes of every DS header and
the ARM7 cardengine already holds a pointer to the running game's, so a
record can name its game at the moment the achievement fires, with the
radio down. That is the case that needs it.

Two things fell out of the question rather than the plan. RetroAchievements'
GameID is not in the record and does not need to be: submission never
wanted it, and for naming a game the cartridge header is better -- offline,
and a name rather than a number. And the risky change disappeared with it,
because passing a GameID down would have meant a new field in the cardengine
header and its two hand-mirrored copies, which is the .align trap that has
already cost this project a run.

The cardengine copies both fields raw and the launcher sanitises them. That
is a budget, not a preference: cardenginei_arm7 for TWL-SDK games links into
33K and had 76 bytes spare. It is the tightest binary in the project --
tighter than the ARM9 cardengine's 12K window, which has 1,224 -- and it
shares cardengine.c with the roomy one.

Making it fit produced two measurements that are invisible until the linker
refuses. A copy loop with a constant bound of twelve is one gcc unrolls into
twelve load/store pairs, costing 264 bytes; tonccpy() is a call and fits.
And the date was being range-checked in both binaries, so the cardengine's
copy was duplication on the side that could least afford it -- dropping it
took the margin from 12 bytes to 140, with a garbage clock now writing a
well-formed stamp the launcher rejects, which is the same outcome by a
shorter road.

The parser gains a sharp edge worth naming: CONTRA4 ends in a digit, and the
queue's founding rule is that every non-digit is a separator. A title left
unconsumed would have that 4 read as an achievement id and submitted as an
unlock nobody earned. Fields are consumed to their delimiter whatever they
contain -- clipped in the copy, never in the consumption -- and the suite
pins that case.

raQueuePack() now takes indices into the queue rather than parallel arrays,
so a kept record keeps everything it arrived with instead of only the parts
the caller remembered to carry across.

Suite 720 assertions, 0 failures. Builds clean at RA_LAUNCHER_WIFI=0 and =2.
ARM9 window untouched, snapshot still at 0x027FEA00 with 1224 free.

## Group the unlock queue by game, for the menu's pending page

*2026-08-10 16:39*

The in-game menu will show one line per game with three fields -- the
game, how many of its unlocks are still owed, and how long the oldest has
waited. This is that grouping, as pure logic with host tests, ahead of the
staging and the page itself.

Counts rather than a list of achievements, and that is what makes it
cheap. Achievement titles only exist in the staged definitions of the game
that is running, so a list could name the current game's unlocks and could
only ever print bare ids for every other game -- rows of two classes, and
the ugly class is exactly the one this feature exists for. A count reads
the same for every game. The player was already told which achievement by
the notification, with its name, when it fired.

waitDays rather than a date, because a date cannot say what that column is
for without also picking a convention: 08/09 is the ninth of August to one
reader and the eighth of September to another, and the column's whole job
is "how long has this been stuck". A day count is unambiguous in any
locale and needs no month table.

It is also the only form the menu can afford. The in-game menu has no
date -- sharedAddr[7]/[8] carry hours and minutes, and only while the menu
is open -- while the launcher has a real clock it already reads for o=. So
the subtraction happens at boot and the menu prints an integer. A session
lasts hours, so a number computed at boot is still right when the menu
opens.

Three things it refuses to do quietly. An unusable stamp counts toward its
game but contributes no age, because zero days prints as "today", which is
a claim the record never made. A clock that moved backwards wraps the
subtraction, so it contributes nothing either. And a queue spanning more
games than the block holds reports the overflow instead of folding it
away -- a screen that under-reports what is owed would be worse than one
that admits it ran out of rows.

Records with no game at all are counted apart rather than filed under a
blank title. The fields are positional, so a record cannot carry a game
without a stamp in front of it; one with neither is a bare id from a
hand-edited file or an older build.

## Stage the pending tally into the WRAM window

*2026-08-10 17:11*

The menu's Sync Pending page needs its data to survive the game booting,
and the only memory that does is cardenginei_arm9_ra's window. This is the
plumbing: a block of its own, staged by the launcher and copied by the
bootloader on exactly the terms the definitions block already uses.

It sits directly below the definitions and the heap is shortened to stop
below both. Half a kilobyte for a structure of about 180 bytes, so the next
thing to want a reservation here does not have to move two other constants
to get one -- against a 156K arena that is not a trade.

The launcher stages it by re-reading the queue file rather than from the
raQueue it just sent, and that is the point: the block has to describe what
the file ends up holding, and the submit path leaves by half a dozen
different routes -- nothing owed, submit=0, no token, everything sent, some
kept. Reading the result once is correct on all of them, where staging at
each exit would be six chances to describe a state that did not happen. One
file read at boot buys that.

Staged even when nothing is pending, because an empty block and a missing
one mean different things to the menu: "nothing is waiting" against "this
boot never looked".

Two things the host suite now pins that nothing else would have noticed.

The magic exists twice, in two headers that never include each other: the
bootloader checks it from locations.h without knowing what a raPendingBlock
is, and the launcher writes it from ra_wifi.h. Drifting apart would show up
as a page that silently never appears.

And ra_fit_test.c measured the arena against the definitions block, which
stopped being where the arena ends the moment this reservation went in
underneath it. It was reporting 512 bytes more room than the target has --
missing exactly the overflow it exists to catch. It follows the pending
block now, and the printed range says so too.

Suite 740 assertions, 0 failures; arena 157,620 bytes with 29,268 spare.
Builds clean at RA_LAUNCHER_WIFI=0 and =2. No ARM7 cost.

## Show pending unlocks in the in-game menu

*2026-08-10 17:44*

A RetroAchievements entry in the root menu, beside RAM Viewer, with Sync
Pending inside it. A folder rather than a page because the things this
scope will want next -- forcing a sync, reading the launcher's log,
showing the session -- need somewhere to go that is not the root menu.

The page is one line per game with three fields: the game, how many of its
unlocks are still owed, and how long the oldest has waited.

Counts rather than a list of achievements. Achievement titles only exist
in the staged definitions of the game that is running, so a list could
name the current game's unlocks and could only ever print bare ids for
every other game -- and the other games are exactly what this page is for.
The notification already told the player which achievement, by name, when
it fired.

Days rather than a date, because five characters cannot tell 08/09 the
ninth of August from the eighth of September and the column's whole job is
how long something has been stuck. The launcher does the subtraction at
boot; nothing in here has a date at all, since sharedAddr[7]/[8] carry
hours and minutes and only while the menu is open.

Three states are kept distinct rather than collapsed. No magic in the
block means this boot never read a queue, which is not the same as nothing
being owed -- an unset window reads as whatever the previous occupant
left. Games past the block's capacity are reported, because a screen that
quietly under-reports what is owed is worse than one admitting it ran out
of rows. So are records that name no game.

Two things this needed that were not obvious. IgmText's menu table was
exactly eight entries and all eight were in use, so it grew to nine plus
the folder's own label, with its static_assert moved to match -- the
linker script is generated from locations.h, so the entry point shifts
consistently and there is no hand-mirrored constant to keep in step. And
raPendingBlock had to move outside ra_wifi.h's RA_LAUNCHER_WIFI guard: the
in-game menu is a cardengine, built with the switch off, exactly like the
RA_QUEUE_* geometry that was already outside it.

Not offered on the exception screen, like every other entry that reads
staged memory -- a crashed game is the one case where nothing about that
window can be trusted.

## The 17 KB regression never happened; the fallback was stale

*2026-08-10 19:35*

Correcting the previous commit, which recorded a 17,312-byte growth in
cardenginei_arm9_ra and blamed it on including ra_wifi.h. Both halves were
wrong.

Measured properly this time, in two steps. Keeping the include and removing
the two stores moved __bss_end by 32 bytes, so the code was not it. Removing
the include as well moved it by nothing at all -- the arena stayed at
140,340 -- so the include was not it either. A header that declares no
storage was never a plausible cause, and the symbol diff between the two
builds is one entry: ra_rc_frame_step, 292 bytes.

What actually differed was the measurement. ra_fit_test.c takes __bss_end
from a -D the runner fills in from the built .elf, and falls back to a
recorded constant when no .elf exists yet. The earlier reading used that
fallback, 0x0375164C; every reading since has used the real value,
0x037559CC. Comparing one against the other reads as a sudden regression
and is really a comparison between a stale constant and a measurement.

So the fallback is updated to what the binary actually has, and the note
above it now says why it matters: a stale one does not fail, it silently
over-reports the arena on exactly the runs where nothing has been built --
which is the shape of reading that looks like a measurement and is not.

The arena has been ~140 KB with ~12 KB of margin throughout. Nothing about
the binary changed and nothing needs undoing.

## Fix the in-game menu crash: an unchecked mirror of sizeof(IgmText)

*2026-08-10 23:27*

Opening the in-game menu on Contra 4 went black, then white, then back to
TWiLight Menu. Adding the RetroAchievements entry grew IgmText from 0xF40
to 0xF68 in igm_text.h, but arm9_igm's card_engine_header.s reserves that
space by hand -- `.space 0xF40` -- and nothing checks the two against each
other.

So the assembly reserved 0x30 bytes too few and every symbol after the text
block moved: sharedAddr, the palette, and the entry point the ARM9
cardengine jumps to. The jump landed inside the text block instead of on
code.

This is the third positional mirror this project has, alongside
loadCrt0/load_crt0.s and cardengineArm7/card_engine_header.s, and the
failure is the same shape as the .align one that cost a run before -- a
clean build, a correct-looking diff, and a dead game.

Verified rather than assumed this time: sharedAddr now resolves to
0x02F88F70, offset 0xF70 from the window base, which is what
IGM_TEXT_SIZE_ALIGNED computes for a 0xF68 struct. The .align 4 after it is
a power of two, 16 bytes, matching that macro's & ~0xF.

The reservation now carries a comment saying what it mirrors and what
breaks when it drifts, since the compiler will not say it.

Suite 740 assertions, 0 failures. Builds clean at RA_LAUNCHER_WIFI=0 and =2.
