## Centre the quiet screen, and stop writing the console's last column

*2026-08-22 00:08*

"It comes apart from 40% on" was a real layout fault and it names its own
cause: 40% is where the first rung long enough to pulse begins, and the pulsing
character sat at column 31 -- the console's last usable cell -- redrawn more
often than anything else on the screen. Writing that cell advances the cursor
past the end, the console wraps to the next row, and from then on every
absolute row this code addresses is one out. The busiest writer was in the
worst possible place.

So the layout is rebuilt on three rules instead of one assumption.

The geometry is asked for. consoleWidth and consoleHeight come from
PrintConsole rather than a hard-coded 32, because a console this code does not
own is not one it may make assumptions about.

Everything is centred and nothing reaches the edge. raWifiCentre() returns the
column a string of N cells starts at to sit in the middle of the console, and
refuses any position that could touch the final column -- pinned on the host
across every width from 8 to 64 and every length up to it. The bar and its
percentage moved onto separate rows, which is what let the bar be centred at
all, and a percentage under a bar is where a person looks for it anyway.

Regions are cleared, not padded. Padding to the full width has to know how wide
the text prints, and these lines carry colour -- five bytes per escape that
occupy no cell. Clearing the message area whole before writing removes the
dependency: a miscount now costs a line a cell or two off centre instead of one
that overruns the row. The area is two rows and both are cleared every step, so
a long caption cannot leave its tail behind a short one.

The pulse gets a row of its own, centred, which is the second half of the same
fix and also what was asked for: one character changing in its own space.

## Draw the quiet screen into the tile map instead of printing it

*2026-08-22 00:18*

Two versions positioned the cursor and called iprintf(), and both failed the
same way: text arriving in sequence instead of staying where it was put. A text
console has two ways to betray a caller who wants absolute positions and this
hit both.

Writing the last usable cell of a row advances the cursor past the end, so the
console wraps and every absolute row addressed afterwards is one out -- that
was the previous fix. And iprintf() goes through stdio: whether the characters
reach the screen while the cursor is where you set it, or later in a batch when
a buffer flushes, is not this code's decision to make. A batch flushed later
prints in sequence from wherever the cursor happens to be, which is exactly
"the messages are scrolled instead of holding their position".

fontBgMap[y * 32 + x] has neither problem. The write lands when it is made,
there is no cursor to advance and nothing to scroll. It is not a guess at
libnds' internals either: it is the expression consoleDrawChar() uses for a
4bpp text background, with the same asciiOffset, fontCharOffset and fontCurPal.
If the map is not there -- an unexpected console, or none -- raMap stays null
and every draw falls back to printing the same text, sequential and ugly rather
than blank.

Colour becomes a parameter, since a tile map has no notion of an escape and
\x1b[31m written into one would be five glyphs. The palettes are asked for
rather than computed: an escape emits no character, so printing one only moves
fontCurPal, and libnds' own mapping from a colour code to a palette index can
be read back instead of reproduced by hand.

That retires raWifiVisible(), which existed only to count the cells an escape
does not occupy. Its tests go with it. A latent trap goes too -- the drawing
loop indexed the string by visible cells, so any text that did carry an escape
would have drawn the escape bytes as glyphs.

## Own the screen: repaint every visible row, every frame

*2026-08-22 00:28*

Three versions failed the same way -- text arriving in sequence instead of
holding its place -- and each fix addressed a real fault without curing the
symptom. That is the sign the approach was wrong rather than the details.

All three faults are real and all three are now moot. Positioning the cursor
and calling iprintf() leaves the timing of the write to stdio, and a buffer
flushed later prints in sequence from wherever the cursor is by then. Writing
the last usable cell of a row advances the cursor past the end, so the console
wraps and every absolute row addressed afterwards is one out. And drawing into
the tile map, which fixes both, still only holds while nothing else prints a
newline -- any other printf scrolls the map and takes our cells with it. A
launcher is not a program that can promise nothing else prints.

So the screen is a model this code owns. A handful of fixed-width lines are the
state, raWifiPaint() renders all 24 visible rows from them, and it runs on
every change and every frame from raWifiIdle(). Anything that scrolls the
console is undone on the next frame. Brute force -- roughly seven hundred
halfword writes at 60 Hz -- and free in a launcher whose every rung is spent
waiting on a radio.

Two things follow from "every row, every time". A row with nothing in it is a
row that gets blanked, so what the launcher printed before this took over
cannot sit underneath and no row keeps a line from an earlier step. And the
base offset is gone: placing the block below existing output was the
accommodation that kept this from working, because a fixed screen and an origin
computed from a cursor other code may move are different things.

The height is no longer read from PrintConsole either. A 256x256 text
background's map is 32 rows and only 24 are on screen, so trusting
consoleHeight would draw eight rows nobody can see.

And the log now carries the console geometry and whether the tile map was
found, so if this is still wrong the next report is a reading rather than a
fourth guess.

## A set of 101 read as a set of 1: the count field was two cells wide

*2026-08-22 01:18*

Reported on Chrono Trigger, and it was never a counting fault. printDec()
writes exactly the digits it is asked for, taken from the low end, and the
achievements header asked for two. Every other set tested has been under a
hundred, so two cells were enough and the field looked correct for a year.
Chrono Trigger's set is over it, and 101 in two cells is 01.

Widening the field is not the whole fix, because printDec() pads with zeros
and three cells would turn a forty-five-achievement set into 045. raPrintNum()
counts the digits first and places the number right-aligned in the field --
the screen is cleared at the top of every draw, so the leading cells are
already blank and there is nothing to pad with.

The same defect was one page away. Sync Pending printed its total in one cell,
so twelve records waiting read as two, and the queue holds up to RA_QUEUE_MAX
of them. Fixed with the same helper.

Both widths are now checked at compile time rather than believed. That pin is
the actual lesson: a field too narrow for its source does not fail, it reports
a smaller number plausibly and forever, and only a set that crosses the
boundary ever exposes it.

And the percentage joins that line, right-aligned. Queued counts toward it: an
achievement that has fired but not been sent is earned -- the same thing the
list marks with a star -- and a percentage that ignored it would fall behind
the stars on the page underneath. Clamped at 100 rather than trusted, because
the counts come from a block another binary wrote.

## An achievement's detail page says when it was earned

*2026-08-22 01:38*

r=startsession is the only rung in this API that answers it. r=unlocks replies
in bare ids and r=patch describes the set rather than the account, but a
session reply carries objects with a When beside every ID -- a reply this
client was already making, and already parsing for its ids, with the dates
sitting beside them unread.

The path: startsession extracts the ids and their Whens and takes this
console's offset from UTC; the patch scanner gives each earned achievement's #!
record a fifth field carrying the date, packed; the cardengine reads it into
raViewerEntry.when while indexing; the menu unpacks five fields with shifts.

The conversion happens in the launcher and that is the load-bearing choice. The
launcher has a real clock and a real libc, the in-game menu has neither and no
business owning a calendar. Packed into 27 bits rather than left as an epoch,
which costs the same four bytes -- an epoch would have pushed the arithmetic
across the boundary into the binary that cannot afford it.

Two clocks, reconciled by ServerNow. The server answers in UTC and the queue
file's stamps are local, and the page shows both kinds side by side, so one has
to be converted or it tells the truth twice in two timezones. There is no
timezone setting in this fork to consult, and ServerNow is the server's clock
at the moment this console's read time(NULL) -- so the difference between them
is the offset, configured or not. A wrong RTC gives wrong dates here and
already writes wrong stamps into the queue, so nothing new is broken.

Nothing is printed when there is no date, and there are three ways: the account
does not hold it, it was earned this session (the flag flips while the game
runs and sharedAddr carries hours and minutes with no calendar), or the block
filled -- the date is the first field raPatchWriteEarned() trims and the only
one whose loss is not counted.

raViewerEntry went 12 bytes to 16, so the viewer reservation grew from 0x800 to
0xA00, out of the definitions block's 32K that the largest measured set uses
26,663 of. sizeof(raViewerEntry) == 16 is pinned beside the reservation check:
without it the growth would have overrun the pending tally directly above with
nothing failing to compile.

raWhenPack() refuses out-of-range values rather than wrapping them -- both
sources are external, a stamp from an editable file and a timestamp from a
server, and a wrong date shown confidently is worse than none. Zero cannot
collide with a real value because month and day are 1-based.

## Time every stage, and stop paying eight seconds for silence

*2026-08-22 01:55*

The boot has always been slow and the log could not say where the time went.
The rungs are a chip bring-up, a DHCP lease, five HTTP round trips and a
hundred-kilobyte download, and which of them is the fifty seconds is not
guessable from outside. raWifiStep() is already called once per stage in both
modes, so one line there gives a timeline with no new call sites.

Two costs found by reading, both paid on every boot.

The tail drain was eight seconds flat. It exists because dsiwifi narrates
asynchronously and keeps talking after the last rung is decided -- the probe's
first hardware run printed the access point's name after its own summary. What
it did not need was the full eight seconds every time, and there was no early
exit, so eight seconds came off every boot this fork has ever done whether
there was anything left to say or not. It now ends after half a second of
silence, with the same ceiling for a chip that keeps talking.

DNS was resolved once per request. Every rung opens its own connection --
Connection: close, because a DS with 191K of heap after lwip is up is not a
place to keep sockets alive across stages -- and each asked DNS again. lwip
caches, but a miss is a round trip on a link measured at its slowest, and the
address of retroachievements.org does not change between two rungs of the same
boot.

What is left is written into the doc rather than guessed at here: the chip
bring-up and the lease are dsiwifi's and the timeline will say what they cost,
and r=patch re-downloading an unchanged set every boot is the largest single
transfer in a common boot -- with a real tradeoff attached, since a cache that
is reused when the ladder succeeds is a set that can go stale.

## Time the ladder with a hardware timer: time(NULL) does not advance here

*2026-08-22 02:08*

Hardware answered on the first run -- every stage in the log read [  0s].
time(NULL) reads a value the ARM7 refreshes, and in this launcher the ARM7 is
running dsiwifi rather than libnds' own VBlank work, so the clock is set once
at boot and then sits still. Correct for stamping an unlock, which is what it
was measured doing, and useless for measuring a fifty-second boot.

A VBlank counter was the other candidate and it is worse: raWifiIdle() runs in
the wait loops and not inside a blocking recv(), which is precisely where the
seconds are going. A timer counts through a blocked CPU; a frame counter
cannot.

TIMER0 cascaded into TIMER1 gives 32 bits at 32,728 Hz -- about 36 hours before
it wraps, against two seconds for 16 bits alone -- and is read low-high-low so
a wrap between the two registers cannot report a two-second jump. Both are
stopped in raWifiShutdown() beside the one dsiwifi leaves behind. Reported in
tenths now that there is resolution to report.

The same log answered the other open question, which is why the geometry line
was kept: `console 32x24, map no`. consoleGetDefault()->fontBgMap is null in
this launcher, so the tile map the fixed-layout screen drew into was never
there -- which is exactly why that build showed a black bottom screen and
nothing else. Recorded in the doc with the fix it points at.

## Stop reading when the body is whole: 50 of the 60 seconds were a socket timeout

*2026-08-22 02:26*

The timeline came back and it was not what anyone would have guessed. The chip
bring-up everyone would have blamed -- SDIO reset, BMI, a full firmware upload,
WMI, a scan, WPA2 -- is 1.3 seconds, and the DHCP lease is 3.2. The radio is 5
seconds of sixty.

Four requests cost 10.2 seconds each for about a kilobyte, and the fifth is the
same 10.2 plus 3.6 for the 64 KB that actually moved. A cost identical across
four replies of different sizes is not a transfer, it is a wait: both readers
looped on recv() until it returned <= 0, so after the body arrived they sat on
SO_RCVTIMEO before noticing the peer's close.

A note in raNetStreamHeaderLine() had already decided against the fix and reads
as a warning now: Content-Length is not needed because Connection: close and
the chunk terminator both say where the body ends, and a length believed but
not enforced would be worse than none. Both statements are true. What they miss
is that one of those two ways of knowing costs a socket timeout every time it
is used.

So the length is read, and enforced -- done is set only when the counted bytes
reach the declared length, so a reply that promises more than it sends still
ends where it always did, at the close. The streaming reader stops on
stream.done; the plain one keeps returning the raw reply its callers were
written against and scans the headers itself.

raNetHeaderLength() and raNetHeaderChunked() are pure and host-driven, because
every part of this is a string problem: the header is case-insensitive by the
standard, Cloudflare does not send it the way anyone expects, and a
Content-Length appearing inside a body of achievement descriptions must never
be mistaken for the header. That last one is bounded by headerEnd and pinned.

## Hardware: 59.8s to 10.5s, and the staged block is byte-identical

*2026-08-22 02:39*

predicted: 10.2 fixed plus 3.6 real, with only the real part left.

## Re-assert the overlay's pixels and palette, not just its OAM

*2026-08-22 02:46*

The overlay was reported as inconsistent between games and not looking right,
and the cause is the file's own reasoning applied to two of the four things it
needed to be applied to. From the per-frame path, about the OAM entries:
"Rewritten every frame rather than left in place, because a game that keeps a
shadow copy of OAM and DMAs the whole thing each frame -- which is the ordinary
way to do it -- would otherwise wipe these on its next transfer."

Equally true of the pixels and of the two palette entries, and both were
written once in show() and never again. A game that DMAs its object tiles or
its object palette every frame is doing something as ordinary as DMAing OAM,
and the result is one of our OAM entries pointing at tiles that are now the
game's, in colours that are now the game's: a notification that appears, in
the right place, made of the wrong pixels. Inconsistent between games and
consistent within one, which is what was reported.

The eviction survey cannot catch it either. surveyObjVram() looks for an OAM
entry referencing our slot, and a blanket transfer of tile data with no entry
pointing here passes it while having overwritten every byte.

Both are re-asserted every visible frame now, on both paths. The background
path is if anything more exposed, since the block it borrows is character VRAM
a game may be streaming into. 512 word writes and two halfwords, only while a
notification is up.

And a real bug, introduced and caught in the same edit: draw() saves the
palette entries it is about to overwrite so hide() can put them back, so its
second call would have saved our own colours as the game's originals and
hide() would have restored those -- two entries of the game's palette
permanently ours, on every game, for the rest of the session. drawTiles() is
the split that makes the per-frame path unable to do it. The sprite path never
had the problem because its palette save lives in spriteShow() rather than in
spriteBlit(), which is what made the asymmetry visible.

Checked and ruled out first: SUB_DISPCNT bit 31, object extended palettes, the
counterpart of the bit 30 this project already got wrong once on the background
side. Nothing reads it and nothing needs to -- extended palettes apply only to
256-colour objects and ours are 16-colour, which always take standard object
palette RAM. Ruled out by reading the sprite's attribute setup rather than by
building anything.

## Probe before rewriting the overlay's pixels: Ketsui hung at a boss kill

*2026-08-22 02:58*

The unconditional per-frame blit was about two kilobytes, which measures cheap
in scanlines. Hardware disagreed with "cheap". Contra 4 came back correct, so
the fix itself works -- and Ketsui hung on killing the first Novice boss, which
is both the moment an achievement fires and the moment a bullet-hell shooter
has least to spare. This runs inside the game's VBlank on top of a memref pass
already using 47 of the 70 available scanlines, and this fork has already
killed one game by adding per-frame work to that budget.

So the rewrite is conditional now, on two probes -- the first and last words of
our range -- which turns 512 writes a frame into two reads on every frame
nothing trampled us. The background path had more to lose, since drawTiles()
also clears a thousand map entries. A transfer that overwrote the middle and
left both ends intact is missed, and that is a stripe of wrong pixels for one
frame rather than a frame the game did not get: the right way round for a
notification to fail.

spriteLastWord is kept rather than recomputed because the sprite blit is a
gather -- it rearranges the strip's background layout into per-object order --
so the word at the end of our object VRAM is not the word at the end of the
strip, and finding out which one it is means redoing the index arithmetic the
blit already did.

overlayRedrawn is appended to the snapshot, so every existing offset keeps its
address. It exists because re-asserting the pixels was a deduction, and a
deduction that spends time inside a game's VBlank has to be able to say whether
it was needed: zero on a game that leaves object VRAM alone, climbing on the
game whose notification looked wrong.

## fileWrite's read-modify-write trusted a cache over a shared buffer

*2026-08-22 22:11*

ra_unlocks.txt came back from a Ketsui session with 464 bytes of somebody
else's memory in it, and the file diagnosed itself: exactly 3,072 bytes, right
size and no overrun, with the new record perfect in slot 1, slot 0 empty, and
non-zero bytes running from offset 48 to offset 511 and stopping. One 512-byte
sector rewritten, the record correct inside it, unrelated audio-shaped data
around it on a 128-byte stride.

A 48-byte record at offset 48 is a partial sector, so fileWrite() reads the
sector, pastes the record over part of it and writes all 512 back. The read is
loadSectorBuf(), which skips the read whenever file, cluster and sector match
what it last loaded -- a claim about globalBuffer, which it does not own and
which anything else may have used since.

Three independent confirmations, one from the file itself. The record landed in
slot 1 with slot 0 empty, so the slot scan read a digit out of a buffer that no
longer held the queue. Exactly 512 bytes came back rewritten with the record
correct and the surroundings not, so the merge used stale contents. And
loadSectorBuf() skips the read with nothing invalidating it, which is the
mechanism by reading.

Fixed at the top of fileWrite() rather than at the call site, and the placement
is the decision. The first attempt exported a helper and called it from the
cardengine, and the TWL-SDK ARM7 failed to link -- .bss past the end of its
region, on the binary that had 60 bytes spare before this. In fileWrite() it
costs that binary nothing and fixes every caller: any partial write anywhere in
nds-bootstrap had the same exposure. Cost is one sector read per fileWrite()
that begins mid-sector, which an aligned write pays once for a whole transfer.

The slot scan keeps one clear of its own before its first read rather than one
per iteration, because the first read is the one that decides and that binary
cannot afford the other 63.

What this does not explain is the crash. Ketsui hung killing a boss before and
after the overlay change, and writing 464 wrong bytes to a file on the SD card
cannot hang a game. Recorded as a separate fault. The achievement that fires
there is 301278, Bomb Quartet, "Get 4 bombs in Single Play by beating a boss
without dying" -- so an unlock does happen at that moment and the notification
path is still where to look.

## Force the sector read in fileWrite, where the corrupting merge actually is

*2026-08-22 22:23*

The previous commit documented a fix to fileWrite() and patched fileRead()
instead -- the same two lines of context appear in both, and the first match
won. The file came back clean on hardware anyway, for a reason that is not the
fix: the queue's slot scan reads immediately before the write, so forcing that
read left a correct buffer for the merge to land in. A second unlock in one
session skips the scan and the corruption would have returned.

So the invalidation is in fileWrite() now, where the read-modify-write is. It
covers every caller, since any partial write anywhere had the same exposure,
and costs one sector read per write that begins mid-sector.

Three attempts, and the ARM7 refused two, which is the constraint that shaped
the result. Exporting a helper for the cardengine to call: link failed, .bss
past the end of vram on cardenginei_arm7_twlsdk. Using resetPrevSect() -- which
already existed in my_fat.c for exactly this -- from both fileRead() and
fileWrite(): failed again, the retained body plus two calls grew .text and .bss
follows it. Inline in fileWrite() plus one inline clear in the slot scan: fits.
.bss overflowing when no variable was added is the tell.

fileRead() is deliberately left alone and that is a limitation, not a
preference: a partial read can still be served from a stale buffer. The one
place it mattered clears the cache itself before its first read, because that
read decides which slot gets written.

And the crash is now confirmed independent: with the file coming back clean --
42 non-zero bytes and nothing else -- Ketsui still froze on the same boss kill.

The hole is one line: a disabled OAM entry's tiles counted as free, on the
reasoning that an object which is not drawn is not using its VRAM. That is not
true. An entry off this frame still points at tile data the game means to keep,
and toggling entries while leaving their banks loaded is the ordinary way to
run a lot of sprites -- a bullet-hell does it constantly.

Ketsui gave three symptoms of one cause: the notification was garbage for its
full three seconds, the game's own graphics broke, and it froze at a stage
transition, which is exactly when a game reaches for the banks it had parked.
Re-blitting could never win that race because the game was writing there too.

So every entry is measured now, enabled or not. Our own eight are excluded by
index -- they used to be excluded by being disabled, which is what tied the two
rules together, so dropping the one meant naming ourselves in the other or the
overlay would evict itself on its first frame.

What it costs is visibility: fewer slots look free, so more games fall back to
the background path or decline to show anything. That is the right direction. A
notification nobody sees is a smaller failure than a game that breaks, and this
file already says so in three other places.
