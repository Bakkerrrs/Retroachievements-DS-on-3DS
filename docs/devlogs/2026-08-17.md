## The menu freeze is upstream's, and it is a rate rather than a switch

*2026-08-17 01:49*

An unmodified official nds-bootstrap release does it too. This fork raises the
rate, which is why it looked like ours for a dozen flash cycles.

Open the menu, navigate it, return to the game, and one to three seconds later
the last sound stretches out and the picture stops. The ARM9 dies and the ARM7
lives. No exception screen, so a hang rather than a fault. Playing for fifteen
minutes without opening the menu does nothing.

The menu is paged in over 0xA000 bytes of what nds-bootstrap uses to cache the
ROM, and paged back out on the way past. The stretched audio is that SD
traffic with the ARM9 spinning at IME zero -- normal, and the official release
does it too. Failing to recover afterwards is not.

Every game fails; only the rate differs. Chrono Trigger and SM64DS take two or
three menu cycles, Contra 4 takes many more and presents differently, with the
menu stuck on screen and the game never returning.

That rate is what cost the investigation. A bisect over 225 commits converged
confidently on 67b28dd, whose only additions cannot execute unless the RAM
viewer is opened -- and it was not. Padding the previous commit to the same
size did not reproduce it. The contradiction was the tell and was misread
twice. A short negative on a probabilistic failure is not a negative: every
clean verdict was six to eight cycles on a build needing twenty, and the
bisect was reading a gradient where each commit that added per-frame ARM9 work
nudged the probability up. The same mistake made "not upstream" look settled,
from one early run with the few cycles that sufficed for SM64DS here.

Twelve eliminations are written down because they cost a dozen flash cycles
and none of them is wasted: this session's work, the network, the achievements
pages, cardenginei_arm9_ra, the reader's VBlank hook, three IGM mirrors, the
menu item array, printDec, binary size, .bss against the stack, symbol
alignment, and the ARM9/ARM7 handshake.

Three unrestored things are recorded without being called the cause, including
bgBak linking unaligned and being tonccpy'd into VRAM, which is a lesson this
project already paid for in the overlay.

Nothing is changed on suspicion. What is honest is to report it upstream, and
to know that this fork meets it sooner because it adds per-frame ARM9 work and
takes DSi WRAM that would otherwise cache the ROM.

Documentation only; no code changed.
