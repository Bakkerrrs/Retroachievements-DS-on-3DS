## The snapshot lives in a RAM mirror, so its console address needs one

*2026-08-08 01:41*

Third hardware reading. The allocator works: heapSize 0x2EF78 exactly as
predicted, mallocProbe 0x03751090 -- heapBase plus the 8-byte block header --
heapUsed 2728 bytes of real rcheevos allocations, wramStage 04. That question
is closed.

rcheevos parsed the definition (rcActivate = RC_OK) and then disabled the
achievement: rcTriggerState 07, one event delivered, rcPeeks 0, rcMeasured 0.
That is rc_runtime_validate_addresses() refusing an address, and it was right
to. The cardengine sits at 0x027FC000, inside main RAM's second 4M mirror, so
subtracting RA_DS_SYSTEM_RAM_BASE gave a console address of 0x7FED54 -- past the
4M RetroAchievements maps for the DS. The validation layer caught a bug of mine
in exactly the case it was built for, which is the system working rather than
failing.

Masking into the 4M window fixes it here and would be wrong on the twlsdk
variants, where main RAM really is 16M and 0x02FDxxxx is its own memory rather
than a mirror of 0x003Dxxxx. So ra_rc_console_address() proves the mirror
instead of assuming it: a sentinel written through the address, read back at the
candidate, twice with different values so a stale coincidence cannot pass, and
the original restored either way. No console address means the self-test does
not install and says so -- RA_RC_NO_ADDRESS. Real achievements are unaffected;
they point at game memory, and only this self-test needs to name an address
inside our own binary.

The first version of that function took the sentinel through a different field
of the snapshot and applied the conclusion to the address being translated.
Proving one region mirrors says nothing about another. The host test caught it.

Host test now builds a real mirror -- one page mapped twice, 8M apart, via
memfd -- so the positive case is checked against actual mirrored memory rather
than an assertion that some exists, alongside a separately mapped page that
masks to the same console address and must be refused.

Stage numbering shifted to keep failures below successes: NO_ADDRESS is 3,
ACTIVE 5, FRAME 6.

## Anchor the self-test where the RetroAchievements map actually reaches

*2026-08-08 02:31*

Fourth reading: rcStage 03, RA_RC_NO_ADDRESS. The mirror proof ran and said no
-- a sentinel written through 0x027FED54 and read at 0x023FED54 came back
different, twice. They are separate memory, not a mirror.

Which settles the underlying question. RetroAchievements maps 4M of DS system
RAM; main RAM on this hardware is 16M. The cardengine sits at 0x027FC000, eight
megabytes in, so no console address names the snapshot and none ever will. The
previous commit assumed a 4M mirror, which a real DS would have made true and
this hardware does not.

So the definition moves to an address the map reaches:

    M:0xH000000>=0.600.

Measured, the byte at console 0 is at least zero, six hundred times. Always
true, so it counts one hit per frame and unlocks after 600 -- and console 0 is
the first word of the game's own RAM, always mapped, never written by us. It
covers a memref read, a comparison, a hit target, the measured flag, the trigger
firing, and do_frame reaching memory every frame. It does not cover the delta
memref, which needs a value that changes and therefore a game address nobody can
name in advance; the first real achievement will exercise it.

Real achievements were never affected. A retail DS game lives entirely inside
that 4M, which is why the map is drawn that way. Only code reading its own
memory falls outside it, and only the self-test wanted to.

The mirror machinery is gone rather than left unused, and with it the hex writer
that built the definition string -- there is no address to format now, so the
definition is a literal. Nothing in this project ever builds a definition; real
ones arrive as strings from the server.

The host test now runs the achievement out to its target and asserts the trigger
actually fires, which the delta-based definition could not do deterministically.

Also confirmed by this reading, and worth recording: the allocator works.
heapUsed 2728 bytes of real rcheevos allocations, mallocProbe exactly on
heapBase + 8 -- the block header -- and heapSize matching the prediction. That
question is closed.

## TLS is not required, and that was measurable rather than askable

*2026-08-08 03:01*

Two of the three questions I was about to put to Discord did not need asking.

The one that would have decided everything on its own -- is HTTPS mandatory for
dorequest.php? -- is testable. Plain HTTP, port 80, no redirect, returns JSON
byte-identical to the HTTPS request. rcheevos anticipates this: rc_api_common.c
defines RETROACHIEVEMENTS_HOST_NONSSL as a first-class host and rc_api_set_host()
recognises it specifically, switching the image host to its non-SSL counterpart
so a cleartext client does not mix schemes. That affordance is deliberate.

Recorded with its two costs rather than as good news alone. It is true today and
RA could require HTTPS at any point. And cleartext means credentials cross the
network in the clear, since r=login takes a username and password. That is the
user's call to make knowingly.

The prior art answered the second question. odelot's adapters -- nes-ra-adapter
on a Pico, wii-ra-adapter as an ESP32 memory card, the MiSTer cores -- do not one
of them network from the constrained side. The evaluator watches memory and hands
results to something that owns the network. odelot needs an ESP32 because a NES
has no second computer.

And a correction worth stating plainly, because it is easy to get backwards:
scoping this project to the 3DS family does not relax the WiFi constraint. A 3DS
running a DS game is in DS/TWL mode -- its own OS, ARM11 and WiFi stack are not
running, and for our purposes the console is a DSi. The scope buys SCFG and DSi
WRAM, which this project already spends. What it does buy is the fallback: the
companion that owns the network can be a 3DS-mode homebrew app on the same
console, with no extra hardware.

So one question is left, and it is worth more than it was: before this, live
contact needed reachable WiFi *and* a way around TLS. TLS is not in the way. Is
the Atheros chip reachable from nds-bootstrap's ARM7 while an NTR game runs? That
one cannot be read or measured from here.

## Record the hardware answer on WiFi, with two corrections from our own source

*2026-08-08 03:09*

The question "is the Atheros reachable from nds-bootstrap's ARM7 while an NTR
game runs" came back as "possible, at the edge of realistic", with three
obstacles, none of them CPU or RAM. Recorded, and checked against this
repository where it made claims about this repository.

Confirmed: the bus exists and the same SCFG bit that pays for our 256 KB of DSi
WRAM is what exposes the WiFi SDIO at ARM7 ports 0x04004A00-0x04004BFF.

Corrected: the WiFi SDIO does not share a controller with SD/eMMC. The warning
was that nds-bootstrap's ROM reads would contend for the same hardware, making it
the likeliest conflict in the project. my_sdmmc.h puts the card at SDMMC_BASE
0x04004800 and the WiFi is at 0x04004A00 -- two instances of the same IP block,
0x200 apart. The contention is for ARM7 time, not for a controller.

Corrected: the NDMA slots do not collide either. driveInitialize() calls
sdmmc_set_ndma_slot(0); libnds' WiFi uses channel 3.

Standing, and the structural cost: the ARM7 is not ours. Our code hangs off the
interrupt hooks nds-bootstrap already inserted into the ARM7 running the game,
and a WiFi stack cannot block there without costing the game its frame pacing.
A non-blocking state machine is feasible but is a rewrite of how dsiwifi waits,
not an integration. Worth holding next to the measurement: one scanline of 263 is
generous for rcheevos, not for a network stack.

Standing, and the highest risk: the AR6002/AR6013/AR6014 keeps no firmware in
flash. The Xtensa code is uploaded to RAM each boot by the system menu, and
booting through ntrboot does not necessarily pass through it. The chip may arrive
needing only WMI init, or cold and needing BMI plus a firmware upload from eMMC.
dsiwifi assumes a starting point.

And one thing this project did to itself: taking 256 KB of WRAM lowered the
isROMLoadableInRAM() budget, so more games read from SD during play -- on the
ARM7, which is where a stack would want to live. We made the contention slightly
worse before knowing we would care.

The consequence is an ordering, and it is not "build the client". First a plain
DSi-mode homebrew that proves dsiwifi associates and POSTs on this actual 3DS
board; then whether WLANFIRM is loaded under our boot path; only then integration.
The risk sits in step two and step two is cheap.

## A WiFi probe, so the cheapest question gets asked first

*2026-08-08 03:23*

Step one of the ladder: a standalone DSi-mode homebrew .nds that answers whether
WiFi works on this console at all, before any of it is nds-bootstrap's problem.
No cardengine, no injected code, no game running. It is a control, and it is
deliberately outside the main build -- a control that shares code with the thing
it is controlling is not one.

dsiwifi comes in as a submodule and builds clean against the pinned devkitARM
r65 / libnds 1.8.0. That was the first thing that could have stopped this and it
did not.

The probe reports a stage number, 0 to 6, from "the library did not return" to
"RetroAchievements answered over plain HTTP", and passes dsiwifi's own log
through unedited. That log is the point: it is the only place that distinguishes
the Atheros arriving warm and needing WMI init from arriving cold and needing BMI
plus a firmware upload, which is the highest risk in the whole plan.

Three decisions worth keeping:

The .nds is stamped -u 00030004 as a DSi title. Launched as NTR the console never
opens SCFG, isDSiMode() is false, the ARM7 skips the extended I/O setup and the
Atheros is not on the bus -- so the probe would report "no WiFi" for a reason
that has nothing to do with the question. That is the one failure mode a control
must not have.

It asks for no credentials. The request logs in as a user that does not exist,
because a well-formed invalid_credentials reply proves DNS, TCP, HTTP and the API
parsing our query without this program ever handling a real password. Over
cleartext that distinction is worth keeping.

It checks the reply for content, not bytes. A captive portal or a Cloudflare
interstitial would succeed at the socket level and mean nothing; the API's own
error code is what proves we reached RetroAchievements.

The log is written to /wifiprobe.log on the SD as well as the screen. Every
hardware answer in this project so far has been read by photographing a hex
viewer, and forty lines of stack log is where that stops being reasonable.

## The firmware obstacle dissolves: dsiwifi's upload path is #if 0

*2026-08-08 03:38*

The probe's log settles the question that was supposed to be the highest risk
in the plan, and the answer is better than "it passed".

The chip did arrive cold. `AR6014 needs firmware upload 0` is dsiwifi reporting
that the host-interest word at +0x58 -- the flag the system menu would have set
-- reads zero. Then it reset into the bootloader, ran BMI, and launched, and the
handshake succeeded.

The reason is in the source rather than in luck: dsiwifi's entire AR6014
firmware-upload block is inside #if 0. No ar6014_part*_bin is written, nothing
is read from eMMC, nothing is read from anywhere. The driver resets the chip
into its bootloader, pokes a few BMI registers, and starts what is already
there. Upstream's own comment above the disabled block -- "TODO: Source AR6014
bins from SAFE_FIRM nwm? Or just leave them because they're only 4KiB" -- reads
like they found it unnecessary.

So bringing the chip up needs no external data at all: no eMMC, no NAND, no SD.
The worst of the three obstacles was a concern about a code path that does not
execute, and that also removes SD contention from the firmware question
specifically -- though not from the rest of the ARM7, where nds-bootstrap serves
ROM reads.

The rest of the log is a clean WPA2 association: four-way handshake, GTK, DHCP,
192.168.0.111. And the chip is an AR6014 -- the 3DS's DWM-W028, the variant
dsiwifi is least tested against and the one this project actually has.

Of the obstacles named before any of this was tested, three are now gone, one is
reduced, and one is untouched: the ARM7 belongs to the game. That last one is
the whole of open question #1 now.

## The launcher is a third network context, and the right one

*2026-08-08 03:44*

Everything so far was argued as a choice between networking inside the game,
where the ARM7 belongs to the game, and a separate 3DS-mode companion app. That
missed the obvious place: nds-bootstrap's own launcher is ordinary DSi-mode
homebrew with its own ARM7, running before a single instruction of the game.
main.cpp calls consoleDemoInit() and checks isDSiMode(); it is the same context
the probe just succeeded in.

It is better than either alternative. No companion app, so one launch. No ARM7
contention, because there is no game yet -- which was the last obstacle standing.
And it is where the work belongs anyway: identifying the game and fetching its
achievement set happen before play, not during. The pipe already exists too --
the staging buffer and SRA1 magic built to carry a binary into DSi WRAM can carry
definitions the same way.

What it cannot do is submit at the instant of unlock, since the launcher is gone
by then. Unlocks queue in WRAM and flush afterwards, via the SD card the ARM7
cardengine already writes to, or the in-game menu that already exists. The
Connect API's bulk endpoint exists for this.

So live submission from inside the game is now an optimisation rather than a
prerequisite.

## Achievement definitions come from a file, not from a rebuild

*2026-08-08 03:56*

Step one of what is left in phase 2 is to evaluate a real published achievement
against a real game. Hardcoding the definition would have meant a build, a flash,
a play session and a photograph per attempt -- and a definition is exactly the
kind of thing that is wrong the first two times.

So cardenginei_arm9_ra reads its definition from
sd:/_nds/nds-bootstrap/ra_achievements.txt. One line of the server's own memaddr
syntax, no rebuild. Absent, the binary falls back to its built-in self-test, and
rcFromFile at +0x98 says which is running -- a definition that does not unlock is
a different problem depending on whether the file was picked up at all.

It is phase 3's mechanism in miniature. When the launcher logs in and fetches a
real set before the game boots, definitions will travel exactly this path:
launcher -> staging -> DSi WRAM. Building it for a hand-typed file means the part
that has to work under a network later is already the part exercised.

Placement cost a decision. Inside the image would have been free -- the loader
already copies 128K into a 68K image -- but it would land in memory the allocator
hands out. So the block sits at the top of the window, 0x03778000-0x03780000,
and the heap stops below it: heapSize 188K -> 156K, still room for well over a
hundred achievements at the ~1K each measured.

The file is the one input here that does not come from us, so it is bounded by
the launcher before a byte is read -- deliberately not through
loadCardEngineBinary(), which reads a whole file into its destination unbounded.
Fine for a binary we ship; not fine for a text file a user edits. It is
re-terminated on the WRAM side regardless of what the file held, and trailing
whitespace is trimmed because a text editor adds a newline and rcheevos would
reject it as syntax.

Host-tested: no magic falls back, a staged definition is used verbatim, a
trailing CRLF is trimmed, and empty or oversized both fall back rather than
reaching the parser.

## Several definitions per file, and three real ones to try

*2026-08-08 04:07*

The achievement set's logic turned out not to be public -- r=patch needs
credentials, the Web API needs a key -- but the game's code notes are, and for
this purpose they are better: documented addresses with their meanings,
published by the people who wrote the set. Whether a definition string came from
the server or from us changes nothing about what rcheevos has to do with it.

tools/ra_achievements.example.txt carries three, in increasing order of what
they prove: a direct 32-bit read, a delta memref, and an AddAddress pointer
chain for "It's Fever Time!" built from the 24-bit game-state pointer at
0x159164 and the state at +0x9c.

The third is the one worth a session. Its computed address is not a memref, so
rc_runtime_validate_addresses() never sees it -- which is exactly why peek()
validates every read as well, and this is the first thing to test that. And when
the pointer is null between scenes the computed address is refused and counted
rather than dereferenced, which here is the difference between a false negative
and a Data Abort in the game's interrupt handler.

The file now holds several definitions, one per line, each activated as its own
achievement, with '#' comments and blank lines skipped so notes travel with it.
A hardware session is the scarce resource in this project and testing one
definition per session wastes it. rcActivated says how many parsed and
rcBadLine names the first that did not, because "two of three worked" is a
completely different situation from "none did" and a hex viewer cannot show a
parser message.

Host-tested: splitting, comments, blank lines, leading and trailing whitespace,
CRLF, and a file with more lines than there are slots stopping rather than
overrunning.

## Measure the addresses instead of guessing at another definition

*2026-08-08 04:24*

The first run with real definitions passed every mechanical test and fired
nothing. rcActivated 3, rcBadLine 0, rcPeeks 4 -- exactly the four distinct
memrefs, so the AddAddress chain is walked every frame -- rcPeeksRejected 0,
rcLines 2 of 263. rcTriggered 0 after reaching Fever Time, with rcEvents 2:
two triggers left WAITING and are evaluating, and the third (stage == 0) was
true at activation, which rcheevos requires to be false once before it may fire.

So the machinery works and the conditions do not match this ROM. The definitions
came from published code notes; something in them does not describe the copy
being played.

Guessing at another definition costs a play session. Reading the addresses costs
nothing extra, because the watchlist already resolves chains and reports into the
snapshot. So the definitions file now also carries watches:

    W:<address>:<size>[:<offset>[:<offset>]]

W:159164:4:9c resolves the same chain the Fever definition uses and puts the
resolved address and value in results[1]. A plausible 0x02xxxxxx address means
the pointer is real and the question is the offset or the meaning; BAD_POINTER
means the word is not a usable pointer at all. Either way the next session
answers what the memory holds rather than whether the next guess worked.

Watch lines replace the built-in self-test watches so the first four land in
results[], and a file of watches alone is legitimate -- the self-test definition
is reactivated so the runtime keeps doing something either way.

Host-tested: the hex parser including empty fields, watch lines with and without
offsets, malformed and out-of-range refused without half-installing, and the
default watches restored afterwards so the borrowed list does not fail later
tests for an unrelated reason.

## The walker was reading RetroAchievements' DS pointers wrong

*2026-08-08 04:37*

Measuring instead of guessing paid on the first run. Three of four watches
resolved -- Current Stage, Stages Completed and the Red->Red counter, all on
plausible addresses with plausible values -- which settles that the published
code notes do describe this ROM. The addresses were never the problem.

The fourth, the pointer chain, came back BAD_TARGET while rcheevos reported
rcPeeksRejected 0 for the same location. Our walker read the word at 0x02159164
as a 32-bit DS address, added 0x9c and landed outside main RAM; rcheevos read it
as 24 bits, added 0x9c and got a console address it was happy with. Two readers
disagreeing about one word is what identified the model as wrong rather than the
address.

RetroAchievements' DS pointers are 24-bit console pointers. That is what the map
means, not a quirk of this game: a 32-bit DS pointer of 0x02xxxxxx is past the
4M the map covers, so the low 24 bits are the console address by definition and
whatever the game keeps in the top byte is not part of the pointer. The notes say
"[24-Bit Pointer]" for exactly this reason.

So RA_WATCH_FLAG_PTR24 masks each mid-chain pointer and adds main RAM's base, and
the file selects it with W24: instead of W:. rcheevos already did this, which is
why its side never complained -- this brings the walker in line with the library
rather than working around it. raWatch.reserved became flags; the struct is the
same size.

The host test reproduces the hardware failure exactly: the same watch resolves
with the flag and returns BAD_TARGET without it, against a cell whose top byte is
deliberately not 0x02. A regression test derived from an observation rather than
from a guess.

The file also now reads the raw word behind the pointer, so the next run shows
its actual value instead of leaving it inferred from a status code.

## The zeros were the wrong cartridge, not the wrong walker

*2026-08-08 04:52*

With the 24-bit mask in, the chain resolved -- status BAD_TARGET -> OK -- and
landed on 0x0200009C, main RAM's base plus the offset, which is exactly where a
null pointer lands. A direct watch on the raw word confirmed it: 0x02159164 held
zero, as did Current Stage and Stages Completed, during active play.

Three zeros can be an uneventful moment. A null pointer during gameplay cannot.
The explanation was the dullest available: the code notes are for Space Invaders
Extreme 2 and the cartridge running was the first game, which has no achievement
set at all. Right memory map, wrong cartridge.

The two results are independent and only one was a bug. The masking fix was
correct on its own evidence -- our walker and rcheevos disagreed about one word
and the library was right -- and it stays. What it bought was a chain that
resolves; what it revealed was that nothing was at the end of it.

The example file now targets Extreme 2 and leads with a canary: Extreme Mode
Unlocked, documented as 0x55 or 0xFF and derived from saved data, so it is one of
the few bytes in the game that is essentially never zero. It decides in one
reading whether the addresses describe the cartridge actually running, before any
time is spent playing toward an achievement.

Both of these rounds cost a text edit and ten minutes of play -- no build, no
flash. That is what the definitions file was introduced for, one round before it
turned out to be needed.

## Correct the record: the 24-bit mask fixed nothing

*2026-08-08 05:00*

Running the same watches against the right cartridge disproves the reasoning
behind the previous commit's masking change. The raw word at 0x02159164 reads
0x02159158 -- an ordinary DS address with 0x02 in the top byte. Masking to 24
bits and adding main RAM's base gives 0x02159158 again. The mask changes nothing
on this game.

So the walker/rcheevos disagreement that motivated it was never about masking
semantics. It was a null pointer: unmasked, 0 + 0x9c is 0x9c, outside main RAM,
and the walker correctly refused; masked, 0 + 0x02000000 + 0x9c is 0x0200009C,
inside main RAM, and the walker resolved to nothing. The mask turned a visible
failure into a false success, which is the opposite of what it was added to do.

The code stays -- it is what RetroAchievements means and what rcheevos does, and

## Step 3b: the ROM's hash, with rcheevos as the reference

*2026-08-08 21:06*

The launcher now computes the RetroAchievements hash of the ROM it is about to
boot and logs it, before touching the network. Without it there is no way to ask
the server which achievement set to fetch.

The first version just called rc_hash_nintendo_ds(), which is already in the
vendored submodule. Then it got measured: that function allocates
max(0xA00, arm9_size, arm7_size) in one block so it can hash each region from
memory -- 353,164 bytes for nds-bootstrap's own .nds, and a real game is commonly
larger -- against 352K of launcher heap before lwip and 184K after. It does not
fit in the best case, so no reordering would have saved it.

ra_hash.c streams the same four ranges through a 1K buffer instead: 352 bytes of
header, the arm9 code, the arm7 code, 2560 bytes of zero-padded icon block, plus
the SuperCard skip. Fixed cost at any ROM size, which is also the right shape for
the shipped feature.

That makes divergence the whole risk, and it is the nastiest failure mode in step
three: a hash over almost-the-right bytes is a well-formed MD5 the server does not
recognise, indistinguishable on hardware from a game with no set. So
tools/ra_hash_test.c compiles the real rc_hash_nintendo_ds() -- there and never in
the launcher -- and requires the two to agree on whatever .nds files the build
produced. rcheevos stays the definition; ours is an implementation of it that
cannot drift quietly. Only md5.c is linked into the launcher, about 6.5K.

Putting that check inside ra_reader_test.c segfaulted the suite at -O1 and passed
at -O0, several sections before the new code ran, and the cause is not the new
code. That file defines __bss_start, __bss_end and __vram_top as 1-byte dummies
because the cardengine takes their addresses -- ra_startup() zeroes between the
first two and puts its arena at the second -- so on the host the arena is whatever
the linker's ordering makes it. Adding rcheevos' hash.c and hash_rom.c to the link
put __vram_top below __bss_end, the span became -1, and the allocator's arena
became the whole process. It had always been luck: fakeArena sits in that file
unused, so the intent was there and never wired up. The fix here is narrow -- the
hash check is its own binary, joining none of that link and needing none of it.
Making the arena explicit is a separate change and is recorded as open.

## The probe could still hang, and it did: recv() had no timeout

*2026-08-08 21:22*

The build that added 3b froze twice on the line after "request sent". The cause is
not 3b, it is an unbounded recv().

The reply is 994 bytes, so the first recv() returns all of it and the loop asks
again. That second call waits for the server's FIN, and Connection: close is a
request rather than a promise -- if the FIN is late or lost, a blocking recv() with
no timeout waits for it forever. The run that reached stage 9 got its FIN promptly;
the next one did not. The difference was luck, which means that earlier stage 9 was
a real result obtained by a probe that could have hung at any time.

Every other wait in this file counts frames and gives up, because a probe that
hangs teaches nothing. The socket read was the one place that rule was not applied
and the one place lwip can block indefinitely.

SO_RCVTIMEO, which dsiwifi's lwipopts already enables, plus a report of what each
call returned: a timeout with bytes in hand is not a failure -- it means the reply
arrived and only the close is missing, which the API's own error code being present
settles. The log now tells "peer closed after 994" from "recv stopped after 994"
from "recv stopped after 0", three worlds that all used to look like a frozen
screen.

Also reports free heap after the hash, with lwip up, and after the HTTP exchange.
That is the number step 3d runs into, and it is better measured on a run that

## The heap is not bounded by anything, and that is the real finding

*2026-08-08 22:16*

Third attempt at one log line, and both wrong versions were wrong in a flattering
direction, which is why this gets written down rather than quietly fixed.

mallinfo().arena is what newlib has claimed by sbrk() so far, not what is available,
so "8528 free of 96452" read as almost out of memory and was not. Then
fake_heap_end - sbrk(0) reported 13,438,976 bytes, which is true and useless: libnds
sets fake_heap_end from main RAM and knows nothing about nds-bootstrap. On hardware
it is 0x02FF3794.

What actually bounds the heap is IMAGES_LOCATION, and nothing enforces it. The
launcher decompresses the boot images to 0x02338000 and ds_arm9_ndsbs.mem ends the
link region at exactly that address, but the enforcement libnds would provide lives
in fake_heap_end and that sits 12.8MB higher. So malloc grows through the images,
then the RA staging block at 0x02600000, the cardengine staging at 0x026F0000, the
ARM7's at 0x027B2000 and the NDS header -- silently. The failure would look like a
corrupt boot screen or a cardengine that starts and dies inside code overwritten
after it was staged.

Measured: static data ends 0x0230AF30, heap top 0x02322794, real ceiling 0x02338000,
so 88,172 bytes of safe headroom.

Which retires the reason given earlier for streaming the ROM hash and replaces it
with a better one. rc_hash_nintendo_ds() wanting 382,212 bytes would not have failed
to allocate -- there are 12.8MB behind fake_heap_end. It would have succeeded and
overrun IMAGES_LOCATION by 294,040 bytes, destroying the boot images the launcher had
just written. Streaming was necessary; the earlier claim that it did not fit was
wrong about the mechanism while landing on the right decision.

with the network live -- #1d's contention, seen for the first time. Log syncs are
throttled to roughly eight a second and the tail window is marked so a repeat says

## Step 3c: r=login, with credentials from a config file

*2026-08-08 22:28*

The format is odelot's MiSTer core's -- key=value, # comments, credentials at the
top -- because that is the file this project's user already has, and one you can copy
from a working example beats a tidier one you have to learn.
tools/ra.example.cfg ships it; the launcher reads
sd:/_nds/nds-bootstrap/ra.cfg. His popup and leaderboard keys are recognised and
parsed and do nothing, because the overlay they describe has no font yet: rejecting
them would make his file unusable here, accepting them silently would make a typo
indistinguishable from a feature that is not built.

The password stays in the file, chosen knowingly over caching a token after one
login. So it goes over the wire in the clear every boot and sits readable on the
card. What the code does do is keep it out of the log: raConfigRedact() turns any
secret into "(set, N chars)", and the token gets the same treatment, because a token
grants the same power over the account and the log's whole purpose is to be sent to
someone.

Percent-encoding is the part that would otherwise have been blamed on the user. An &
in a password ends the query parameter early, a + decodes as a space, a % opens an
escape that is not there -- each builds a well-formed request that comes back
invalid_credentials, which from the console is indistinguishable from a wrong
password. The user would have been told their password was wrong when it was not. So
raNetUrlEncode() is a function with a host test, fed exactly those characters plus a
non-ASCII one, and truncation is reported rather than swallowed. The config parser is
tested against odelot's example verbatim, since "his file works here" is the actual
requirement and an invented fixture cannot check it.

ra_net exists now, which the layering table has promised since phase 0. The GET lived
in ra_wifi.c while there was one request to make; with r=login there are two and
r=patch makes three. raNetJsonString() is deliberately not a JSON parser -- it is
enough for r=login's flat object and knowingly not enough for r=patch's nested one,
which is 3d's job.

The ladder grows to 10 rungs. The log the host test reads is still a 9-rung run,
which is the point of reading real logs rather than transcriptions: the fixture did
not need editing to stay true.

## Room for a real achievement set: 8 definitions becomes 128

*2026-08-08 22:53*

The staging block has always held 32,760 bytes of definition text, but the
reader would only ever split eight lines out of it. That was the right number
while the definitions came from a hand-typed file; `r=patch` is about to make
the server the source, and a real set is a hundred definitions or more.

The 128 pointers are static rather than automatic. ra_rc_init() is reached from
the cardengine's own context, and 512 bytes of that stack is not this binary's
to spend. It runs once per boot, so nothing is lost.

Raising the constant also exposed a landmine in the host test that had already
fired twice, and this time it is fixed rather than documented. tools/ra_reader_test.c
defined __bss_start, __bss_end and __vram_top as 1-byte dummies, and the
cardengine takes their *addresses* -- so the allocator's arena was whatever the
linker's ordering of three symbols happened to make it. Adding rcheevos' hash.c
to the link once made the span negative; 512 bytes of new statics in this file
did it again. Both times the suite passed at -O0 and crashed at -O1, in tests
unrelated to the change.

They now come from --defsym as absolute addresses inside the real WRAM window,
which the test mmaps in full instead of just the definitions block at the top of
it. The arena is chosen rather than inherited. The scratch window the direct
ra_startup() tests use is one buffer with offsets for the same reason: `fakeBss`
and `fakeArena` were only contiguous by the linker's good manners, and the
arena has to be contiguous with the .bss it follows.

Two smaller things came out of the same change. The over-limit fixture was
`char many[256]`, sized by hand for twelve 12-byte lines; at 128 it overflowed
and glibc's fortify check caught it, so it is now derived from the constant.
And the test pins the two halves of the limit against each other -- 128
definitions in 32,760 bytes averages 255 bytes each, which is the number worth
knowing when RA memaddr strings run from tens to a few hundred characters.

## Step 3d: r=patch, streamed into the staging block

*2026-08-08 23:08*

The last rung of the network ladder, and the first one that leaves something
behind. Stage 12 asks dorequest.php for GameID 14856's achievement set and
writes it to CARDENGINEI_ARM9_RA_DEFS_BUFFERED_LOCATION -- the same block a
hand-written ra_achievements.txt already goes to, with the same header and the
magic written last. None of that path is new, which is the point of having
built it for a file first.

The reply cannot be held. It is over 100 KB, the heap has 85,656 bytes, and the
destination is 32,751 bytes of text -- so it is read through rather than into:
recv() into a 1 KB static window, hand each window to a scanner, forget it. The
largest reply in this project allocates nothing, and the run's heap line is
there to check that rather than assume it.

Two state machines, both pure and both tested at every byte boundary.

raNetStreamFeed() strips HTTP headers and undoes chunked transfer encoding. The
chunk framing is the reason it exists as testable code instead of a loop: a hex
length written into the byte stream, landing inside a memaddr string, would
corrupt exactly one definition out of a hundred and nothing anywhere would say
so. The set would load, most achievements would work, and one would silently
never fire. Every reply this project has read so far came back unchunked, but
each was one packet, and whether a CDN chunks is a decision about size.

raPatchFeed() pulls the definitions out. Not a JSON parser, and sound rather
than merely convenient: JSON escapes an interior quote as \", so the eleven
bytes "MemAddr":" cannot occur inside a value -- an achievement titled
"MemAddr":" arrives as \"MemAddr\":\" and does not match. The fixture carries
exactly that achievement instead of leaving the argument unchecked. What the
scanner does not know is which object the key belonged to; today MemAddr is an
achievement field and nothing else, and that is written down as a limitation.

Unofficial achievements come down in the same array as published ones,
distinguished only by Flags: 3 is core, 5 is unofficial. Counting them would
inflate the one number this rung exists to produce. Flags arrives after MemAddr,
so a definition waits in a 2 KB carry buffer until its flag comes, or until the
next MemAddr or the end of the document says none is coming -- which is why
raPatchFinish() exists: the last achievement in the reply is the one whose Flags
is followed by the end of the document, so without it a set is always exactly one
definition short.

Three smaller decisions of the same kind. \/ is unescaped back to /, because RA
escapes forward slashes and memaddr syntax uses / as its division operator. A
definition longer than the carry buffer is dropped rather than clipped -- a
truncated memaddr is not a shorter achievement, it is a different one. And a
reply cut off mid-value is counted apart from one that overran the buffer,
because the two say opposite things about what to do next.

Every outcome is counted and reported: a set that lost thirty definitions to a
full block looks exactly like a set with thirty fewer achievements from the
block alone. `wanted` is the measurement the step is for -- what a complete set
would have needed, whether it fit or not.

The screen gets a dot every 8 KB and the card gets nothing. recv() blocks, so a
run that stalls halfway would look identical to one that never started; iprintf()
is writes to console memory, where raWifiLog() would be libfat plus an fsync()
over the FIFO to the ARM7 running the WiFi stack. That combination froze a v6 run.

Steps 3b through 3d took the launcher's static floor from 569,136 to 598,220 of
753,664, and the stale figure in raWifiReportHeap()'s comment is corrected to
match. It costs this rung nothing, since it allocates nothing; it is the number
step 4 inherits.

## Step 4, offline: run the server's 56 definitions, and fix the clock first

*2026-08-08 23:48*

The set is staged and rcheevos accepts it on a host. What has never happened is a
retail game evaluating it. That stacks two untested things -- a real set inside
the game, and WiFi in context B where the ARM7 belongs to the game -- which fail
for unrelated reasons and have unrelated fixes, so this does the first one alone.

Copying the staged file to sd:/_nds/nds-bootstrap/ra_achievements.txt is not a
different code path. ra_definition() decides the block is real by the magic at
CARDENGINEI_ARM9_RA_DEFS_LOCATION and nothing else, so the cardengine cannot tell
a file from an r=patch: same address, same header, same rcFromFile, same
ra_split_definitions(). It is the same code with the network removed as a
variable. There is also a hard reason -- RA_LAUNCHER_WIFI=1 does not boot games,
by design, so no build today both fetches a set and boots one.

The measurement had to be fixed before spending a flash cycle. rcInitLines was a
single VCOUNT delta around ra_rc_init() taken modulo 263: correct for three
definitions, silently wrong for fifty-six, because a parse spanning four frames
reports whatever remainder it lands on and a slow init reads as a fast one. That
matters because rcheevos dedups memrefs against a list that grows as definitions
are added, so ~1,946 conditions over two parse passes is plausibly ten frames or
more spent inside the game's VCOUNT handler -- a hazard to the game, and exactly
what a wrapping number would have hidden.

There is no way to count frames from inside a handler that is not being
re-entered, so the measurement moved down a level. Each activation is timed on its
own; rcInitLines is now the slowest single one and rcInitTotal the sum. Per-
definition deltas add up correctly as long as no single activation exceeds a
frame, and rcInitLines saturating at 255 is what says whether that held. Both are
published as the loop runs rather than after it, so a hang shows how far it got.

rcFirstTriggered went in beside them, because with fifty-six definitions loaded a
climbing counter says something fired and nothing about what. The set opens with
`1=1.300.` -- always true, three hundred hits -- so line 1 should unlock about five
seconds in, and any other line first means a definition is reading memory it
should not. That is a prediction that can be wrong, which a counter is not.

Both fields fit in reserved4[3]: one u8 and one aligned u16 at an odd offset, so
every offset above them keeps its address and the hardware checklist stays valid
for every reading already photographed. The host test pins the two new offsets and
the 0xA0 struct size along with the rest.

The docs carry the full checklist with a prediction against every field, and name
the two that are genuinely open: rcInitTotal and rcLinesMax. rcPeeksRejected gets
its own note -- the set's addresses run to 0x00189074 and should all translate,
but nothing has ever tested that with addresses this project did not choose.

Nothing amortises the parse across frames yet. That is the obvious fix if
rcInitTotal comes back large, and doing it before measuring would be guessing at a
cost -- the same mistake as the three wrong heap lines in step 3.
