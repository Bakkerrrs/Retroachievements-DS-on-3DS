## overlay=0, and fix the release guard that let a failing suite ship

*2026-08-23 00:01*

Asked whether the overlay approach is sustainable and whether the 3DS's ARM11
could be used instead. It cannot: a 3DS running a DS game is in DS/TWL mode
with its OS and its ARM11 not running, which this project already recorded for
the radio. There is no 3DS-side layer reachable from here.

But the concern is right and worth naming. The overlay is the only part of this
fork that negotiates with a running game for its hardware; everything else
reads memory or writes into a window nobody else owns. To draw it has to answer
"which object VRAM and which OAM entry is this game not using", and that
question has no reliable answer from outside the game. Four rounds, four
inferences: the game will not overwrite our tiles (it did), an overwrite will
touch an end of the range (it landed in the middle), it will stop once we put
them back (it writes every frame), a disabled entry's tiles are free (they are
a parked bank). The last is a real correction; the shape of the list is the
point.

So overlay=0 in ra.cfg stops the popup, checked at the top of
ra_overlay_tick() rather than at each place that draws -- a switch that turns
this off should turn off the surveys and the register reads too. With it off an
unlock is still detected, queued, submitted and listed in the menu with its
date; only the part that can touch the game goes. It rides in a spare byte of
the session block, so the bootloader's own offsets into that block are
undisturbed, and those are now pinned to say so.

And the guard that should have caught a stale pin and did not. Appending
overlayRedrawn left CHECK(sizeof(raSnapshot) == 0xCC) naming the old size and
the suite failed -- but ra_release.sh checked its result with
`| grep -q "PASSED"`, and the suite runs several binaries and prints a verdict
for each, so one FAILED among three PASSED still matched. It uses the exit
status now, which ra_reader_test.sh was already returning correctly, plus a
second look for the word FAILED. Verified by breaking a pin on purpose and
watching it refuse.

That matters more than the pin did: "always build with tools/ra_release.sh" is
a rule this project rests on, and the most important thing that script promised
to check was being read with a grep.

## queue=0: the overlay was not the cause, and the empty file names the suspect

*2026-08-23 00:21*

overlay=0 confirmed in the log and Ketsui froze at the same boss anyway. Four
rounds on the overlay were four rounds in the wrong place, and that is a method
failure rather than only a wrong guess: the overlay was suspected because it is
the part that draws and the symptom was visual, it did have real bugs worth
fixing, and the freeze was never once tested against it until a switch existed
to test it with. Building that switch took one commit against four spent
patching.

What is left is what the queue file points at: it came back empty, so the
unlock never reached it. With the popup off, the frame an achievement fires
still runs rcheevos -> the ring -> ra_rc_offer_unlock() -> sharedAddr -> the
ARM7's FIFO handler -> raUnlockAppend() -> fileRead xN -> fileWrite. That last
step is a blocking SD transaction on the ARM7 while the game streams from the
same card, and this project has already watched that contention corrupt this
very file twice with the game's own data. An empty file is consistent with
hanging inside the write rather than before it.

So queue=0 stops the handoff in ra_rc_offer_unlock(), one step before the FIFO
request, so nothing downstream runs: no request, no file read, no sector write.
Detection and counting keep working, so the snapshot still reports the unlock.

Gated on the ARM9 side because it has to be: the session block lives in DSi
WRAM, which is the ARM9's, so the CPU that does the writing cannot read the
switch.

What it costs is what makes it a diagnostic and not a setting -- with queue=0 an
unlock does not survive the session, because the file is the only thing that
does. Defaults to 1 for that reason.

## The write waited for nothing: a suspended card read is not protected by IME off

*2026-08-23 00:57*

`queue=0` did not freeze. Same game, same boss, one boot, and four rounds spent
on the overlay were four rounds in the wrong place.

The critical section around the queue append came with an argument -- "a
competing read cannot *start* underneath this write, and on this CPU reads are
driven from interrupt handlers, which IME off prevents". True, and insufficient.
The ROM read path is resumable by design: between fileReadNonBLocking() and
resumeFileRead() the game's read exists only as one outstanding sdmmc command
and 512 bytes of my_fat.c's single globalBuffer. IME off protects neither. A
VBlank landing in that window ran the append straight through it.

That one collision accounts for everything reported, in both directions at once:
the game's read never completing and the ARM9 spinning on it forever, the record
coming back holding Ketsui's credits text, the queue coming back empty on the
last hang, and it only ever happening at a scene transition. The fileWrite()
sector-cache fix earlier in this branch was the same collision seen from the
other side, which is why it cleaned the file and left the freeze.

So the work waits, on two sides for two different reasons.

ARM7, correctness: raUnlockService() returns while readOngoing is set, leaving
the request word standing so the next frame retries. It can only live there --
the flag is that CPU's own state.

ARM9, courtesy: ra_rc_offer_unlock() does not raise the request while a card
read of its own is unserved. An unserved request cannot corrupt anything, but
the ARM7 answers it from the VBlank handler, which cannot run while the append
holds IME off. The unlock stays in the ring and goes out a frame later.

The split is measured, not aesthetic. cardenginei_arm7 for TWL-SDK games links
into 33K with 60 bytes spare and .bss follows .text, so text growth overflows
the region (translation unit text, baseline 7737):

  one bool test added to the condition, in place   7829  +92
  the two-word predicate added in place            7905  +168
  lifted to a function, gcc inlined it back        7817  +80
  lifted, noinline, both halves of the predicate   7793  +56  -- 4 bytes over
  lifted, noinline, readOngoing only               7753  +16  -- ships

Ninety-two bytes for one bool test is register pressure across an 1860-byte
straight-line function, not the test; lifted into its own noinline function the
handler drops to 1260 and the test costs what a test costs. And the second half
runs on the ARM9 because on the ARM7 it was four bytes too expensive.

raCardReadPending() is in ra.h so both sides see it and the host suite can pin
its truth table -- the one part of this checkable without a card. queue stays at
1 and stays documented as a diagnostic; it earned its keep in one boot.

Built with tools/ra_release.sh, md5 ec4fcb655bd42862f167194d5ac4d37c, 966 host
checks passing. Not yet confirmed on hardware: the next boot on the same boss is
the check.

## queue becomes a ladder: three suspects, one flash, and the record says the write finished

*2026-08-23 01:19*

It froze again on the same boss, and the queue file from that session came back
COMPLETE -- id, stamp, game code, title, hardcore flag. So the append did not
hang. It ran to the end and cleared the request. Whatever stops the game is a
side effect of that work, not a stall inside it, which retires the shape of the
previous commit's argument and not only its conclusion. That gate is correct and
stays; it was not what was wrong.

Two corrections found by reading rather than by another boot:

There is no IRQ nesting on this ARM7. irqHandler in card_engine_header.s
dispatches one handler and returns, and nothing clears the CPSR I bit hardware
set on entry, so VBlank cannot preempt FIFO and the append can never land inside
a blocking card read or a save.

The RTC is not on SPI -- rtcTransaction() bit-bangs RTC_CR8, a dedicated
register. What it costs is time: 64 bits at two swiDelay(48) per edge plus a
second transaction, order 4-5 ms inside the VBlank handler with interrupts
masked. Nothing else in nds-bootstrap reads the RTC while a game runs; the menu
only does it paused. This fork added that and it has never been tested alone.

Three suspects left -- the handoff, the RTC read, the SD work -- no way to read
the answer, and the last two guesses were both wrong. So the switch becomes a
ladder, walked from the quiet end, one ra.cfg edit per rung:

  0  nothing crosses to the ARM7
  3  the request is acknowledged and cleared, nothing else
  2  everything except the RTC read; record stamped 20000000000000
  1  everything

Whichever rung the freeze reappears at is the rung that causes it. Level 2 is
also a usable fallback rather than purely diagnostic: month 00 makes
raQueueStampToUnix() refuse the stamp, so the launcher submits without o= --
the same outcome as a bare record, and visible in the file as what it is.

The level rides in shared slot 11 rather than in more magics, which inverts the
call made for the mode and for a stated reason: a missing mode reads as softcore
by omission and mis-files a real unlock, while an unrecognised level lands on
FULL because the ARM7 tests only the two values that skip work.

Not compiled in for TWL-SDK: the slot read and its branches cost 100 bytes and
that binary has 60, measured at every arrangement worth trying. It ignores the
level and does the whole thing -- the safe direction, and the game this exists
to bisect is NTR, which loads the variant with 11K spare.

Built with tools/ra_release.sh, 983 host checks passing.

## The block survey exempted the layer being borrowed, which is the one it could least afford to

*2026-08-23 02:26*

Three rows of the RAM viewer on a real Ketsui unlock:

  overlayState    0x6A  -> extpal off, layer 1, block 1, real fade, held back
  overlayDispcnt  0x00010700 -> BG0, BG1, BG2 enabled; BG3 and OBJ not
  spriteOam/Slot  FF/FF -> the background path, not sprites

So the overlay borrowed BG1 -- correctly, by chooseLayer()'s rules -- and then
chose block 1, which is the block BG1 itself was using. It wrote glyphs and a
full 32x32 tilemap into a live layer's character block while the game kept
writing into it. Garbage in the place and for the duration the notification
would have had, which is exactly what was reported.

The cause is one `continue`:

    if (i == skipLayer) continue;   /* the layer being borrowed */

The reasoning was that the overlay is taking that layer so its VRAM is going
spare. The layer is taken; its VRAM is not. chooseLayer() promises exactly that
-- "the overlay points its character and screen bases at a block of its own, so
the game's tiles and tilemap for this layer sit there untouched throughout" --
and the skip made that promise impossible to keep. It also contradicted the
paragraph directly beneath it, which already says a block referenced by any
layer counts as in use, enabled or not, learned the hard way on Contra 4. This
was the one layer exempted from that rule.

Deleted, and raOverlaySurvey() loses the parameter. The host case that asserted
"the skipped layer contributes nothing" now asserts the opposite on the same
input.

Also kills a long-standing suspicion by measurement rather than argument: bit 0
of overlayState is clear, so BG extended palettes were off and were never the
reason the glyphs did not show.

Recorded but not patched: bit 6 says the notification was held back until a fade
ended, and overlayDispcnt is what the sub engine looks like immediately after one
-- BG3 off, OBJ off, mid-transition. Deferring past a fade puts the survey at the
least representative moment there is. Same mistake the block survey already
learned, one level up. Not touched, because the last two things patched on this
trail were patched before they were understood.

Built with tools/ra_release.sh, 984 host checks passing. Independent of the queue
ladder: the garbage is still there at queue=3, where the ARM7 does nothing.

## The clock is read once at init: bisected, and it is what froze Ketsui

*2026-08-23 02:42*

The ladder answered in three boots and no rebuilds:

  queue=0  nothing crosses                      clear
  queue=3  request acknowledged, nothing else   clear
  queue=2  everything except reading the RTC    clear
  queue=1  everything                           freezes

2 and 1 differ in exactly one call. Both earlier diagnoses -- made by reading
rather than by testing -- were wrong; this took three ra.cfg edits.

rtcGetTimeAndDate() bit-bangs RTC_CR8 with swiDelay(48) on every clock edge and
does it twice: about 166 delays, near a millisecond, inside the VBlank handler
with the I bit set. Either that starves the FIFO handler of the ARM9's card
reads at the worst moment a shooter has, or it lands on top of a transaction the
game's own ARM7 had in flight on the same serial bus. The fix does not need to
know which, because it removes both: the clock is captured in initialize(),
while the game is setting up its interrupts and has no main loop to interrupt.

Nothing in nds-bootstrap read the RTC during gameplay before this fork added it.
The in-game menu only ever did it with the game paused. That was the rule.

What it costs, stated rather than hidden: every unlock in a session is now
stamped with the moment the session started. The exact version -- count VBlanks,
write the elapsed seconds beside the stamp, let the launcher add them and roll
the day over -- does not fit the record: the fields come to 46 of
RA_QUEUE_RECORD's 48 bytes and a frame count needs seven more, so it needs the
record and RA_QUEUE_MAX to change together. Recorded in "What is left".

Fitting it into cardenginei_arm7_twlsdk took four arrangements:

  - raStampCache is initialised data, not .bss, so it arrives holding
    20000000000000 -- a stamp raQueueStampToUnix() refuses -- which let the read
    path drop its validity magic and fallback branch entirely
  - raUnlockAppend() takes raStampCache by pointer; the local, its copy and the
    function that copied it were what put .bss past the region
  - raStampCapture() is noinline, so the RTC code exists once (12 bytes)
  - raUnlockWritten and raUnlockDropped are deleted: incremented, never read,
    nothing on that CPU reports them, and the ARM9's unlockLost covers what
    matters. Counting into a variable no one can see is not counting.

44 bytes spare. queue=2 is retired to full in the same change and keeps its
number rather than being renumbered, so the recorded readings still mean what
they say.

Built with tools/ra_release.sh, 984 host checks passing.

## Confirmed on hardware, and three readings for what a photograph could not settle

*2026-08-23 03:18*

queue=1, same boss, no freeze. Reading the RTC on the unlock frame was it. Six
sessions of Ketsui had ended at that boss.

The overlay's garbage survives, and the photograph of the results screen is
where reasoning ran out: the sub screen shows the game's own score table with
bars in a green that looks wrong, and "looks wrong" is not a reading. Two
candidates point opposite ways and both are settled by a register:

  the palette theft   draw() writes white and black into bank 15's ink and
                      shadow entries and restores them on hide. Free if the game
                      was not using them, destructive if it was, and nothing has
                      ever checked which. The colours the game lost are
                      recoverable exactly -- they are already saved.

  8bpp                the palette argument assumes 4bpp, where bank 15 is a
                      corner a game using banks 0-3 will not miss. At 256
                      colours there are no banks: the map's palette field is
                      ignored and OVERLAY_PAL_BANK * 16 + ink is plain entry
                      241, in the middle of the range a game fills. BGCNT bit 7
                      says which, and the overlay has never looked.

So three fields the background path already holds and throws away are published
instead of argued about:

  overlaySavedInk     +0xCE   the game's colour at the ink entry, before
  overlaySavedShadow  +0xD0   ...and at the shadow entry
  overlayBgCnt        +0xD2   the borrowed layer's whole BGCNT, bit 7 included

Snapshot to 0xD4, pins updated. Same instrument that killed the extended-palette
theory and found the borrowed-block collision, pointed at what is left.
