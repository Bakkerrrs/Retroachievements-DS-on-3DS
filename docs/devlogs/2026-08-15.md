## Document sync and submit in the example config

*2026-08-15 17:09*

Both are this fork's own keys, both default to 1, and neither was in the
example -- so the file that is meant to be the reference for what the config
accepts was missing two of the four keys that actually do something.

sync=0 skips the network ladder and plays from the per-game cache, which is
worth having for a measured reason: forty seconds failing to associate with
no access point in range, fifteen redoing yesterday's work with one.

submit=0 reads the queue and reports it without sending or clearing it,
which is a testing key -- an achievement is spent the moment it lands, so
the cheapest repeatable case on the card disappears the first time it works.

## Drop the in-game log reader

*2026-08-15 17:35*

The item existed to avoid a physical cost -- power down, take the card out,
read it on a PC, put it back -- which is what made a two-line reading
expensive enough to justify building a viewer for it.

Both halves of that have gone. Sync Pending answers the question that comes
up mid-session, which is whether what was just earned is safe and how much
is waiting; that was what anyone was opening the log for while playing. And
the card no longer has to move, because the log comes off it over FTP after
quitting.

What is left over is real debugging, and that wants the whole file on a
screen with a scrollbar rather than thirty-two columns of a DS panel.

Recorded rather than deleted, with the reason, because "we decided not to"
and "nobody got around to it" are different things and the next reader
cannot tell them apart from an absence.

## Put the notification in the top right, with a drop shadow

*2026-08-15 17:49*

Three changes to how the achievement notification presents itself.

The heading. `RA UNLOCKED` was a debugging label -- it said "the
RetroAchievements code in this fork fired", which is a sentence about the
implementation. The line underneath carries the achievement's own name now,
so the heading's only remaining job is to tell a player that the words below
are not part of the game. `ACHIEVEMENT` does that.

The position. `OVERLAY_ROW` was 10, the middle of a 24-row screen, which was
never a decision -- the overlay had one row to be in and the middle is where
it landed. It is 1 now, with a row of clearance rather than flush against the
edge. The horizontal half is separate and had to be: the strip is already the
full width of the screen, so moving it up and leaving the text centred inside
it would have left the message floating in the middle, only higher. So the
text right-aligns against RA_TEXT_MARGIN, and only the two together are "the
top right".

The shadow, which cost a second borrowed palette entry and a rewrite of the
renderer. A glyph used to be written as eight whole words into the one tile
it belonged to -- structurally incapable of drawing a shadow, because a pixel
right of column 7 is the next tile. `raTextPixel()` addresses the strip as a
256x16 bitmap instead, dropping out-of-range writes rather than wrapping them:
a shadow hanging off the bottom row is the ordinary case for a descender, and
wrapping it would smear the far end of the row above.

Both shadows are drawn before either glyph, and that is a correctness argument
rather than a preference. Per-letter shadow-then-glyph would let a later
letter's shadow fall on an earlier letter's ink -- a grey notch bitten out of
a white stroke, which reads as a broken font rather than as an ordering bug.

RA_TEXT_INK and RA_TEXT_SHADOW live in ra.h next to the geometry. They were a
literal 1 in ra_text.c and an OVERLAY_PAL_INDEX in ra_overlay.c, two constants
that had to agree and agreed only because nobody had had a reason to change
either. A second colour is exactly that reason.

The host suite states the nibble-order test in two colours: `nibbleSpan()`
became `nibbleSpanOf(word, colour)`, since "something is set here" can no
longer tell ink from the shadow of the letter to its left. It pins the
ink-wins-on-overlap asymmetry on `L` and pins the margin on `d`, whose bowl
reaches pixel 7 so its shadow lands in column 31.

## Clear the pending block's staging word in the launcher

*2026-08-15 22:55*

The bootloader checks CARDENGINEI_ARM9_RA_PENDING_BUFFERED_LOCATION exactly
as it checks the image and definitions magics beside it, and the launcher
cleared two of the three. The only thing that had ever cleared the pending one
was the *previous* boot's bootloader on its way out, so the launcher's
guarantee was not self-contained: it held only for a boot that followed one
which had got that far.

Two ways that bites. On the first boot after power-on the word is whatever RAM
came up holding. And on any boot where the wifi ladder stops before stage 13 --
no access point, no config file, a refused login, all ordinary paths --
raWifiStagePending() never writes, and that stale word is what decides whether
the in-game menu shows a pending list and whose.

Found while investigating a report of an unlock that was accepted by the server
and still listed as pending in the menu. This is not yet established to be that
bug; it is a defect the search turned up on the way, and it is the one part of
the path that can be proven wrong from the source alone.
