## Take the pending tally out of the heap again, now that the evidence is void

*2026-08-13 01:49*

Sync Pending has been showing nothing, and the reason was known and accepted
at the time: the block sits inside rcheevos' arena, so the allocator hands
out the memory the menu reads.

It was put there because two builds that moved it elsewhere failed on
hardware. That evidence is void. The failure has since been seen and not
seen with the same binary -- the last run worked, with rcFromFile 1 and all
45 definitions activated, on a build that changed nothing but added a probe.
So every placement conclusion drawn by comparing those builds was reading an
intermittent fault, including "it is the arena" and "it is this address".

What decides the placement is the design, not that evidence. The definitions
reserve 32 KB, the heap already stops below them, and the largest real set
measured uses 8,306. The tally goes in the top of that reservation: out of
the arena, which keeps its full 140 KB, and out of reach of the allocator.

The launcher's cap comes down by the same 512 bytes so a set can never grow
into it. That change was written once before and silently did not apply --
the scripted edit matched a comment and not the expression, so a comment
claimed a subtraction that was not there. It is applied and checked now.

The intermittent fault stays open, and raSnapshot.defsMagic is in place to
catch it the next time it happens rather than reasoning about it again.

## Build the deliverable with a script that verifies what it produced

*2026-08-13 02:04*

Several days of this branch's debugging chased an intermittent fault that
was not intermittent and was not a fault. The pre-delivery checklist says a
ROM must compile at RA_LAUNCHER_WIFI=0 and =2; running both makes satisfies
it and leaves retail/bin/nds-bootstrap.nds holding whichever ran last.
Copying it after a =0 build hands over a launcher with no network at all.

The symptom is not obviously a build problem, which is what made it
expensive: nothing stages, so the bootloader finds no magic and clears the
destination, and cardenginei_arm9_ra falls back to its built-in self-test --
one unlock, seconds into the game, with the synthetic id 0xF0000000. The
arena, the pending block's address and the launcher's statics were each
blamed and each exonerated on evidence that was really "did the =2 build
happen to run last". And the logs agreed with each other rather than with
the console, because a boot with no network never rewrites
ra_wifi_launcher.log -- so the log being read was the previous boot's.

tools/ra_release.sh fixes the order rather than remembering it: =0 first
because it is only a compile check, =2 last because it is the deliverable.
Then it proves the result from the ELF rather than from intent -- a =2
launcher links dsiwifi into its ARM7 and a =0 launcher does not -- runs the
host suite, prints the snapshot budget, and refuses to emit a file if any of
it fails. It reports the commit, marks a dirty tree, and prints the md5 so
the file that was handed over can be identified later.

Verified against the ROM built by hand: same md5.

Not verified: the refusal path itself. The check is a backstop behind the
ordering, which is the part that actually fixes this.

## Take the game's identity at init, and keep the queue file at its full length

*2026-08-13 15:37*

Two confirmed defects in the queue, both small, both in the record's own
contents rather than its format.

The cardengine read gameCode and gameTitle from ndsHeader on the frame an
achievement fires. That header is the loader's, in main RAM, and the game
reuses the memory once it is running -- so an unlock earned in the first
seconds carries YCTE and CONTRA 4 and one earned at a stage end minutes
later carries neither, from the same build. That pairing is what proved it.
Both fields are copied once at cardengine init now, beside the queue file
they travel with.

That costs cardenginei_arm7 for TWL-SDK games 80 bytes of the 140 it had, so
it is down to 60. Worth knowing before the next thing wants room there.

And the queue file is brought up to RA_QUEUE_BYTES when it is short. Only
the empty-queue path could ever leave it that way -- every other exit
rewrites the whole file -- and that path returned early without touching it.
The consequence is not cosmetic: the cardengine computes a record's offset as
slot * RA_QUEUE_RECORD, can reach the last slot, and cannot allocate, so
against a file left at an older and smaller record size a high enough slot
writes past the end of it and into the next file's clusters. Raising the
record from 16 to 32 and then to 48 each left every existing card in that
state, and nothing would have fixed it on its own: the file only grew on a
boot that had something to send, and a card that cannot sync is the one
accumulating unlocks.

Reachable only with more than forty queued unlocks on a pre-upgrade file, so
it has almost certainly never fired. It is still someone else's file being
written into.

Suite passes with 0 failures. Builds clean at RA_LAUNCHER_WIFI=0 and =2.
