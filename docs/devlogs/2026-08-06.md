## Phase 1 confirmed on hardware, and open question #2 answered

*2026-08-06 01:51*

3DS, Space Invaders Extreme, cardenginei_arm9, snapshot at 0x027FEEE0, after
7,433 frames of play.

Both self-test chains resolved to 0x027FEEE4 -- the snapshot address plus 4,
which is ticks -- and both read 7,433, the live value of that field. One chain
walked a single indirection and the other walked two, each re-resolved from
scratch that frame against memory changing underneath it. The self-test cells
read back as 0x027FEEE0 and 0x027FEF58, exactly the addresses the chains
started from. watchCount and resolved were both 3, so the direct watch was
reading a register at the same time.

The per-frame cost: linesMax stayed at 1 across all 7,433 frames. A tick short
enough to fit inside one scanline still reads 1 whenever a scanline boundary
falls inside it, so a maximum of 1 over that many samples puts the cost *under*
one scanline of 262 -- roughly 1,600 ARM9 cycles, with three watches active and
two of them walking chains. That is open question #2, which has been open since
the project brief, answered with a measurement instead of an estimate.

The overlay reported 9 shows, 0 denied, 0 evicted, against 4/0/1 at phase 0.5
on the same game. That is a longer session rather than a behaviour change, but
it does mean the negotiation kept working with the reader doing more per frame.

## Second game on hardware: the walker holds, and the overlay gets refused

*2026-08-06 02:03*

Two samples from one session on a second title, 2,844 frames apart. Both
chains resolved to snapshot+4 and read the live value of ticks in both, so the
walker behaves the same on a game it has not seen before -- which is the reason
to run a second one.

Two findings.

The overlay was refused 4 times out of 13 attempts (denied = 4). That is the
first time on hardware, and it confirms what phase 0.5 predicted from first
principles: a game that keeps its sub layers busy leaves nowhere to draw, so
unlocks have to queue rather than be dropped. It was a design argument; it is
now a number. evicted stayed 0, so a block once granted was never reclaimed
mid-notification.

And a correction. The previous commit claimed the per-frame cost is "under one
scanline of 262" on the strength of one game, where linesMax was 1. On this one
it reached 11, so the general claim does not hold. What does hold is that
linesLast was 0 in every sample taken across both games, so the typical tick is
under a scanline.

The spread is almost certainly not the reader. Its work per tick is fixed --
three watches, two chain walks, ~30 memory accesses, a few hundred cycles --
and 11 scanlines is ~17,000. The measurement times the elapsed window, which on
a DS includes DMA halting the CPU, another interrupt landing inside it, and main
RAM wait states under contention. So linesMax is a ceiling on the window, not a
cost, and the docs now say that rather than the stronger thing. Separating the
two needs a control measurement -- an empty window timed alongside the real one
and subtracted -- which costs about 20 of the 44 remaining bytes and therefore
waits for the separate ARM9 binary.

## Field report from Final Fantasy III: a palette bug, and split the denials

*2026-08-06 02:15*

Three things came out of playing a real game that no snapshot field was going
to find.

The palette bug is the one that mattered. A graphical fault showed up on the
title screen at the moment a notification appeared. draw() was saving and
whitening all sixteen entries of palette bank 15, but the glyphs are drawn
entirely in colour index 1 -- it ORs a nibble of 1 per set pixel -- so fifteen
entries were being overwritten for nothing. Any game using them saw them go
white for the three seconds the notification was up and come back on hide,
which is exactly a transient fault tied to the toaster.

Now it borrows the one entry the design needs. That freed 30 bytes of .bss,
more than the new counter below costs, so the margin on cardenginei_arm9 went
from 44 bytes to 104. One entry is still one the game may be using -- the text
has to be some colour -- but that is the floor rather than fifteen times it.

The lesson generalises and is now in the docs next to the other hardware ones:
"ask for what is needed at the moment it is needed" applies to how *much* is
borrowed, not only to when. Phase 0.5 got the timing right and the quantity
wrong.

Second, the notification appeared on the top screen in the field and the bottom
in battle. Not a bug: the overlay draws on the sub engine, and which panel the
sub engine feeds is POWCNT1 bit 15, the display-swap bit, which belongs to the
game. FF3 flips it by context and nothing here reads it, so the overlay does not
know which screen its own text is on. Fine for a proof, a deliberate decision
for a real notification.

Third, the notification went missing across map transitions -- where the game
fades to black, plausibly by enabling every sub layer, which would leave
chooseLayer() nothing to take. denied could not confirm that because it counted
both failure modes as one. Split: deniedNoLayer counts the no-free-layer case,
and denied - deniedNoLayer the no-free-VRAM case. The snapshot header grew by
one u32, so the watch blocks moved to +0x1C/+0x34/+0x4C/+0x64 -- the host test
pins those and the docs match.

Also recorded but not fixed: surveyBlocks() reads every enabled layer's BGCNT as
a text background and never checks the BG mode or the colour-depth bit. For a
bitmap background the base is in 16K units rather than 2K, so the survey can
both miss blocks in use and mark ones that are not. Not the cause of the fault
above, but a real way to pick a block the game is using. It belongs with the
overlay rewrite in the separate ARM9 binary.

## The split counter answers it: every denial was a missing layer, not missing VRAM

*2026-08-06 02:28*

Two more Final Fantasy III samples with the palette fix and the split denial
counter in.

deniedNoLayer equals denied in both -- 1 of 1 and 4 of 4. Every refusal was "no
background layer was switched off" and VRAM was never once the reason, which
confirms the map-transition fade hypothesis completely and also clears the
surveyBlocks() bitmap-mode hole of any part in the denials. So the fix is the
unlock queue and nothing else; block management does not need touching.

evicted reached 3, having been 0 in every previous session. The give-it-back
path phase 0.5 wrote from a hardware lesson had therefore never actually run
until now. When it did, reported graphical faults went down rather than up.
That is a lesson in its own right and is now in the hardware list: code written
from a correct lesson can sit unexercised for a long time, and a counter is what
tells you when it finally ran.

The palette fix holds -- faults dropped to a single one, at the moment of
pressing X to open the in-game menu. That is the menu taking both screens while
the overlay may hold a borrowed layer, an interaction by construction rather
than a new bug, and no achievement unlocks on that exact frame. Accepted as-is
and documented; the clean answer is for the overlay to stand down while the menu
is up, when it gets rewritten.

Also recorded: a caveat that undercuts the cost measurement. linesLast was 11 in
one sample, and that reading was taken with the menu open -- the menu runs on the
ARM9 and contends with what is being measured. linesMax is a running maximum, so
menu frames feed it, and the only way to read it is to open the menu. The 11 may
be entirely a menu artefact with the gameplay cost nearer 0-1 lines. The current
instrumentation cannot separate them: the observation perturbs the observed.

## Catalogue the overlay's graphical limitations and defer them on the record

*2026-08-06 02:34*

Phase 1 turned up five ways the overlay falls short, and the decision to ship
without fixing them should be explicit rather than implicit in what nobody got
around to. So they are listed in one place with a severity each and a stated
disposition, including for a first public release.

Four of the five are not defects. The menu collision and the borrowed palette
entry are cosmetic and transient; having no control over which physical screen
the notification lands on, and skipping notifications when no layer is free, are
properties of drawing on an engine the game owns. The skip needs a queue, which
needs a client that generates unlocks, so it cannot be built yet anyway.

The fifth is a real bug: surveyBlocks() reads every enabled layer's BGCNT as a
text background and never checks the BG mode or the colour-depth bit, so for a
bitmap background -- whose base is in 16K units rather than 2K -- it can both
miss blocks in use and mark ones that are not. Picking an in-use block would
overwrite the game's tiles. It has never been observed, and phase 1 gave positive
evidence it is not firing: all five recorded denials were missing-layer, so the
block search was never the deciding factor.

All of it belongs with the overlay rewrite in cardenginei_arm9_ra, which the
overlay needs regardless for a font that fits. Patching it into a 104-byte margin
first would be work done twice.

## Research where cardenginei_arm9_ra goes, and measure whether rcheevos fits

*2026-08-06 02:42*

Done before writing any of it, because placement is hard to undo once the
bootloader plumbing exists. Measured on devkitARM r65 or read out of the
bootloader source; nothing here is estimated.

The region is settled: DSi WRAM at 0x03700000, 512 KB. The 0x0C/0x0D extended
RAM was already ruled out -- MPU region 3 has instruction permission 0x0, so
code cannot execute there -- and 0x02xxxxxx belongs to the running game. DSi
WRAM is the only candidate with a working precedent, since the colour LUT
executes from 0x03732800 today. It is available on a 3DS with SCFG unlocked:
dsiWramAccess is true outright when REG_SCFG_EXT7 != 0, and dsiWramMirrored --
the flashcard case where only the shared 32 KB exists -- is out of scope anyway.

One assumption in my earlier summary was wrong and is corrected here. Reserving
WRAM does not cost ROM cache; the ROM cache is in 0x0C/0x0D. wramSize feeds
isROMLoadableInRAM(), where it is added to the ROM-in-RAM size limit, and
loadNitroFileInfoIntoRAM(), which skips its optimisation rather than failing.
On a 3DS the limit moves between 27.875 and 28.375 MiB depending on how much is
reserved -- a cliff rather than a gradient, over a 0.5 MiB band out of 28, which
no standard cart size sits inside.

Also wrong: I thought the colour LUT left a 243 KB hole in WRAM. It does not.
The apparent gap is its stored-palette buffers at 0x03733800 through 0x0376C000.
The LUT holds 317 KB and the whole region is claimed.

rcheevos, compiled for armv5te thumb -Os: 121 KB for the entire library
unlinked, of which the runtime that parses and evaluates conditions is 35 KB.
Linked with --gc-sections for the shape phase 2 needs -- activate an achievement
from a definition string, evaluate it per frame -- it is 48 KB of text/rodata/data
and 492 bytes of bss, including everything newlib contributes. Runtime state
measured by wrapping malloc against definition shapes RetroAchievements really
uses: about 1 KB per achievement, so 50-150 KB of heap for a real set.

So ~100 KB minimum, ~270 KB for the full client with a large set, against 512 KB.
It fits. And the phase 0 question is now quantified from the other side: 48 KB is
460 times what the cardengine has left.

Two things to decide deliberately rather than by accident. RA and the colour
filter compete for the region -- the minimum configuration coexists with the
LUT's 317 KB, the full one does not. And rcheevos needs malloc, snprintf and
fmod, so the RA binary has to be a properly linked program with its own allocator
over a reserved arena, not an injected blob like the colour LUT it is otherwise
copying. That is the biggest structural difference from the pattern, and better
known now than after.

## Scope the project to the 3DS family, enforced at runtime

*2026-08-06 03:07*

Decided rather than drifted into. consoleModel > 0 -- the 3DS family, New 3DS
included -- is the only configuration this fork supports for RetroAchievements.
On a DSi, or a DS through a flashcard, it now behaves exactly like upstream: no
reader, no overlay, no IRQ_VCOUNT forced on.

The reasoning is that two of the things this fork does are real behaviour changes
to a running game -- forcing a VCOUNT interrupt on for games that never enabled
one, and borrowing a background layer and a palette entry from the sub engine.
Both surface as intermittent oddities rather than crashes, which is exactly what a
console nobody tests on cannot be trusted to reveal. Shipping them to a DSi on the
strength of "it should work" is not a good trade. It also removes speculative work:
the DSi WRAM the separate binary needs is guaranteed on a 3DS with SCFG unlocked,
so no fallback has to be designed for its absence.

No new plumbing was needed. consoleModel comes from CONSOLE_MODEL in the config
file -- the launcher knows the console -- and was already passed through as
ce9->consoleModel.

Two checks, both necessary. hookIPC_SYNC() will not install the VCOUNT hook for
the reader unless the console qualifies, which is the one that matters since
installing it is what forces the interrupt on. And ra_tick(), a new single
per-frame entry point, checks again because the colour LUT installs the same
handler and does run on a DSi, so being called is not proof the reader was wanted.

ra_tick() replaces the two direct calls from cardengine.c. It costs 8 bytes more
than the inline version -- measured, not assumed -- and is kept anyway because the
separate ARM9 binary will need a bridge in the same place and one entry point is
the right shape for it. The gate as a whole costs 48 bytes, taking the
cardenginei_arm9 margin from 104 to 56.

DSi-enhanced games on a 3DS come along for free: they load the twlsdk variants,
which already carry the reader with ~7,100 bytes spare. All eight variants still
compile, since this is a runtime check and not a build configuration.

Verified with a clean top-level build on the pinned toolchain, no overrides, exit 0,
and the host test covers the gate for consoleModel 0, 1 and 2.

## cardenginei_arm9_ra: build it, pack it, call it -- but do not load it yet

*2026-08-06 03:25*

The separate ARM9 binary now exists: retail/cardenginei/arm9_ra/, linked into
DSi WRAM at 0x03740000 with a 256K window, built by retail/Makefile, packed as
nitro:/cardenginei_arm9_ra.bin, and called once per frame from ra_tick().

It is deliberately inert. Nothing sets b_raWramLoaded yet, so on hardware
wramState reads 00 (absent) and the window is never entered. That is the safe
half of the work done first: the launcher-side buffer and the ARM7 copy can
break a boot, and this cannot.

The stub writes RAH1 into wramMagic on first call and increments wramTicks. The
milestone is the chain, not the payload -- built, packed, loaded, copied,
recognised, called -- with each link reported separately in the snapshot so a
failure names itself instead of showing up as one silent absence. Same order,
and the same reason, as phases 0 and 0.5.

The call is gated twice: the bootloader's claim that it copied the binary in, and
the first halfword at +2 reading 0xEA00. The binary begins with a branch by
construction, so that is its signature, and DSi WRAM holds whatever its previous
occupant left -- an unloaded window reads as plausible garbage, not as zeroes.
Calling into it would be a jump into arbitrary data inside an interrupt handler.
The colour LUT checks itself the same way.

What it cost: 84 bytes against the 56 that were left. Paid by taking RA_WATCH_MAX
from 4 to 2 and dropping the depth-1 self-test watch, which leaves the two
defaults filling both slots and cardenginei_arm9 with 28 bytes. The depth-2 chain
walks every line of the depth-1 path plus one more, and the per-watch status codes
still say where a chain broke, so the diagnostic loss is small -- but it is a loss,
and the hardware checklist in the docs is updated for it.

Worth stating plainly: the cardengine is now full enough that adding anything
means removing something. That is not a problem to solve here, it is the argument
for the binary this commit adds -- once the loader works and it is proven on
hardware, the reader and overlay move into the 256K window and stop competing for
12K.

Still open, and stated in the docs rather than guessed at: the launcher needs to
read the nitrofile into a main-RAM buffer before the ARM7 can copy it, and that
buffer has to be somewhere genuinely free at launcher time. The colour LUT's
equivalent is 6K against a binary heading for 256K. Choosing an address without
mapping what else is live there is how a bootloader quietly corrupts something.

Verified: clean top-level build on the pinned toolchain, exit 0, all variants
link with the .bss assert in place, the nitrofile is present in the packed .nds,
and the host test passes against the new two-watch layout.

## Map main RAM to place the RA staging buffer, and record the trap it nearly hit

*2026-08-06 03:40*

The staging address for cardenginei_arm9_ra is 0x02600000, capped at 256K.

Finding it hinged on a mechanism that is invisible from the address list, so the
map is now in the docs. Before anything else, the bootloader's ARM7 blanks most of
EWRAM through a list of memset ranges -- so anything the launcher stages inside one
of them is wiped before the bootloader can use it. That is *why* the existing
staging addresses are where they are: 0x026F0000, 0x027CE800 and 0x027D0000 all sit
in the gaps between clears, and the comment on one of the clear lines says as much.

The surviving ranges are tabulated in the docs. 0x02400000-0x02680000 is 2.5MB that
is both preserved and unclaimed, which is where this goes -- 512K clear of the donor
ROM above it.

Recording the wrong turn as well, because it is exactly the failure this exercise
existed to avoid. 0x02700000 looked free: it appears in no location constant, and
the first hits a grep returns are in retail/bootloader/, the B4DS path rather than
ours. Widening the search showed bootloaderi clears that whole span on startup and
puts the FAT table cache there. Two truncated greps in a row would have shipped a
bootloader that corrupts its own file tables.

The requirement is also smaller than assumed: only the loadable image goes through
the buffer, not the 256K window, since the heap is allocated in WRAM and never
copied. rcheevos is 48K linked, so the cap is generous.

Which gives the staging strategy for the load path itself -- prove it with the
48-byte stub that already exists. If the address is wrong anyway, the blast radius
is 48 bytes and it fails a verification on hardware before anything grows into it.

## Stop the RAM viewer crashing on a mistyped address

*2026-08-06 03:57*

Not this fork's bug, but a bug in the tool this fork's whole debug workflow runs
on, which turned up the first time the two-watch layout was read on hardware.

The in-game menu's RAM viewer has no value search -- only a jump-to-address screen
edited one hex digit at a time -- and then dereferences `address` with no bounds
check anywhere in the file. Typing the snapshot's magic where its address belongs
points it at unmapped memory and lands on the red exception screen.

The real damage is the persistence. `address` is a global, commented "global so
it's persistant" so the viewer reopens where you left it, so a poisoned value
faults again on every re-entry before any keypress can fix it. The only way out is
rebooting the game.

clampAddress() now runs before every read and on leaving the jump screen: an
address whose whole visible span is not inside a real region snaps back to
0x02000000, which also un-poisons the global. The range list is deliberately
generous -- main RAM, shared and DSi WRAM, I/O, palette, VRAM, OAM, the GBA slot,
and the extended RAM above 0x0C000000 -- because the point is catching a typo, not
policing where anyone looks. 176 bytes in a binary with 11.4 KB spare, so for once
not a trade.

Also recorded: the third hardware confirmation. On the two-watch build every value
predicted in advance matched field for field -- magic, counts, both watches' bases,
offsets, resolved addresses, values and status bytes, and both self-test cells.
Losing the depth-1 self-test cost the walker nothing, and wramState read 00 rather
than 01 or 02, so the bridge recognised the absent binary and did not jump into an
empty WRAM window. That was the point of the reading: proving the bridge is inert
before writing the loader that makes it live.

## Write the loader for cardenginei_arm9_ra: stage, copy into WRAM, set the flag

*2026-08-06 12:58*

The three steps the handoff called for. Builds clean on the pinned toolchain; has
never run, so nothing here is confirmed yet.

conf_sd.cpp stages nitro:/cardenginei_arm9_ra.bin at the staging buffer + 0x10 and
writes an 'SRA1' magic at +0x00 afterwards. The magic is how the bootloader knows
the launcher really put something there -- the region is uninitialised otherwise --
which is the same device the colour LUT uses with its 'cLUT' word. It is cleared
before the read and only written on success, so a stale one cannot be believed.
Gated on consoleModel > 0, and on !colorTable because the two compete for the same
WRAM: the LUT's stored palettes live inside the window the RA binary takes, and an
explicit choice of colour filters should win over a feature nobody asked for yet.

main.arm7.c copies it into CARDENGINEI_ARM9_RA_LOCATION, mirroring the colour LUT's
*retail-path* block rather than the DSiWare one. Establishing which of the two
mattered: line 1878 opens `if (isDSiWare && !dsiWareAsSlot1)` and closes at 2176
with `} else {`, so the second copy site is the one a retail DS game reaches. That
block hands WRAM to the ARM7 only in DSi mode, and this mirrors it exactly, since
what the LUT does is the only thing known to work. Placed immediately after it so
raWramLoaded is set before isROMLoadableInRAM() reads the budget -- that call is at
line 2414, the copy at 2371.

dsiWramCacheSize() replaces three copies of (colorLutEnabled ? 0x32800 : 0x80000)
spread across two files, and returns CARDENGINEI_ARM9_RA_WRAMSIZE when the RA
binary is loaded. It deliberately does not check dsiWramAccess: the callers already
have, and returning 0 would make loadNitroFileInfoIntoRAM() skip its preload for
the wrong reason. Checked in the disassembly rather than assumed -- the compiler
emits a branchless select over all three values.

Designed to fail safe and to name the stage that failed. The bootloader compares
the first word after copying, which proves the copy landed; the cardengine checks
the window starts with a branch, which proves what landed is code. Neither alone
would be enough: a garbage staging area can pass a copy comparison trivially.

Still proving it with the 48-byte stub, not rcheevos, because the one risk the main
RAM mapping could not fully retire is 0x02600000 turning out to be live after all --
and 48 bytes is a blast radius worth accepting to find out.
