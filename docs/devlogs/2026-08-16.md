## Write down the test rig, and what it let us rule out

*2026-08-16 00:01*

Every hardware reading in the document was taken with TWiLight Menu at its
defaults -- no colour LUT, no PHAT_COLORS, no per-game overrides -- and that

## Stop the self-test queueing itself as an achievement

*2026-08-16 00:17*

In every game RetroAchievements does not know, this fork earned a fake
achievement, filed it on the card, showed it to the player as work waiting to
sync, and sent it to the server -- once per boot, forever.

The card settled it in three lines. sd:/ra_unlocks.txt held

    4026531840	20260815183256	C6PJ	PICROSS3D

and 4026531840 is 0xF0000000, which is RA_SYNTHETIC_ID_BASE: the id an id-less
definition gets, and the built-in self-test is exactly such a definition. The
next boot's log submitted it and got

    4026531840  refused: Unknown achievement.
    {"Success":false,"Status":404,"Code":"not_found",...}

Picross 3D is a game the server answers for with no definitions -- its set is
literally called "Unsupported Game Version". With nothing staged, arm9_ra falls
back to the self-test, it triggers seconds in, the trigger goes down the unlock
ring, and the ARM7 appends it as though a player had earned it. The launcher
clears the queue every boot and the self-test refills it before the player
reaches a menu, which from the outside looks exactly like a queue that never
clears.

The guard goes in ra_rc_queue_unlock(), the one function every trigger passes
through, because that is the only place that knows the id is synthetic --
downstream it is just a large number, and a large number is what a real id
looks like. The notification is untouched: the overlay runs off triggeredCount,
which the event handler bumps before calling this, so the self-test still proves
on screen that the reader, runtime, ring and overlay work.

Counted as raSnapshot.unlockSynthetic in the two padding bytes already there, so
the snapshot stays 0xCC. "The self-test fired and was correctly not queued" and
"nothing fired at all" are the two states worth telling apart on a game with no
definitions, and last time it took a card's queue file to tell them apart.

For cards already carrying them, raQueueScan() drops synthetic ids and counts
them apart from `dropped` -- these are well-formed records, not corruption. The
drop happens after the stamp, code and title are consumed: dropping at the id
would leave 20260815183256 and PICROSS3D to be read as two more ids. The
launcher now rewrites the file even when the queue reads as empty, which it
does once the fakes are discarded, so the record does not sit there being
counted by the menu forever.

One test changed rather than added: the parser's upper bound used to assert the
largest u32 survives a scan. It is above RA_SYNTHETIC_ID_BASE now, so the
boundary is stated on RA_SYNTHETIC_ID_BASE - 1. Real ids are six or seven
digits.

This also retires a symptom closed on the wrong evidence. "RA UNLOCKED appeared
at the start of the game where the probe should no longer be" was blamed on the
RA_LAUNCHER_WIFI=0 delivery fault. That fault was real, but the self-test also
fires on a correct =2 build in any game the server does not know, so the symptom
had a second cause and it was never closed.

## Discard staged definitions when the server disowns the ROM

*2026-08-16 00:32*

loadRaDefinitions() stages sd:/_nds/nds-bootstrap/ra_definitions.txt for
whatever game is booting, unconditionally -- it is a hand-managed debugging file
with no way to know which game it belongs to, and it says so. Harmless while
something overwrites it, which for a ROM the server knows is what stage 15 does.

A ROM the server does not know never reaches stage 15 ("no GameID; the set
cannot be asked for"), raWifiCacheLoad() has no cache for it either, and the
hand file survives into the game. Read off a card: ra_definitions.txt held
Ketsui Death Label's fifteen definitions and the console booted Arkanoid DS,
which the server does not know -- so Ketsui's triggers spent that session
watching Ketsui's addresses inside Arkanoid's RAM.

Worse than the self-test bug this branch started with, in the one way that
matters: these are real RetroAchievements ids. A synthetic id gets a 404. A real
id gets accepted, and the player wakes up holding an achievement for a game they
were not playing. Nothing undoes that from here. Nothing fired during the
observed session, which is luck rather than design.

Cleared in raWifiIdentify() where the fact exists, rather than at the done:
fallback. A ladder that never got that far cannot tell "no set for this ROM"
from "never asked", and the hand file is the only way to test definitions with
no access point at all -- so it stays staged on every path except the one that
positively contradicts it.

## Definitions carry the description and the points

*2026-08-16 00:49*

The record becomes

    <id>:<memaddr>\t<title>\t<points>\t<description>

and the field order is the design rather than an ordering. Every valid form is
a prefix ending at a tab boundary -- full, then without the description, then
without points, then the bare `<id>:<memaddr>\t<title>` every build before this
wrote, then no label at all. So the block filling up walks that table upwards
one field at a time, a reader never meets a hole in the middle, and every
cached set already on a card still parses.

Points sits before the description although it is read less often, because it
is one to four bytes and the description is up to sixty-four. Dropping the
expensive field first is the whole point of the order.

RA_PATCH_DESC_MAX is 65 -- 64 characters -- sized from the viewer rather than
from what the server sends: the in-game menu is 32 columns, so 64 characters is
two full lines under a title.

The scanner gains two needles, and both satisfy raPatchAdvance's
restart-and-retest property, which is the thing that makes this a scanner
instead of a parser. `"Description":"` repeats only the quote and the `i`, and
no proper prefix of length two or more is a suffix of a longer one.
`"Points":` repeats only the quote. Points is the one field here that is a JSON
number rather than a string: it has no closing quote, so it reads to the first
non-digit and *reprocesses* that byte rather than swallowing it -- a swallowed
`{` is a pending id that never gets cleared.

The degradation is a loop over the three lengths rather than three nested
tests, because the question at each step is the same one and stating it three
times is how the second and third get subtly different bounds. It keeps the
outer guard the single-field version had: trim only when trimming can actually
save the achievement, or a definition that was going to be dropped anyway has
its label counted as "dropped for room", which is a different fact.

Measured, on the largest real set: 56 definitions, 28,585 of 32,759 bytes with
no labels at all. Titles and points take it to about 29,985, leaving 2,774 for
descriptions -- 49 bytes each. So a set that size will lose descriptions and
say so in descNoRoom; Contra 4, at a quarter of the block, keeps all of them.

## Earned achievements are written for the viewer, not dropped

*2026-08-16 00:54*

The skip list from r=unlocks left an already-earned achievement out of the
block entirely, and the header said what that cost: "the cardengine cannot know
they exist, so it could not one day show 30 of 55 earned... the fix would be a
format change rather than a flag". This is that change.

An earned achievement is written as

    #!<id>\t<title>\t<points>\t<description>

with no memaddr at all, which is what makes it nearly free. The largest real
set averages over 500 bytes a line for the memaddr against about 100 for
everything a person reads, so an achievement moving from "to earn" to "earned"
gives the block back four fifths of its space rather than all of it. The worst
case for the block is therefore still a set where nothing has been earned --
the case already measured at 87% full -- and adding the earned half costs
nothing there because there is no earned half.

The `#` is not a new convention. ra_split_definitions() in cardenginei_arm9_ra
has skipped lines beginning with one since it was written, so these are
invisible to rcheevos without a line changing over there: no empty memaddr to
refuse, no error counter to move, nothing armed that must not be. The `!`
separates them from a comment a person typed in a hand-written file.

They degrade in the same order as an armed definition, and `earned` /
`earnedNoRoom` are counted apart from `kept` / `dropped`, because a set whose
armed half is empty because the player finished it reads very differently from
one whose armed half is empty because the block overflowed.

And the fixture for it found a bug older than this branch. Every early exit in
raPatchCommit() -- unofficial, odd id, already earned -- cleared the memaddr and
the flags and *not* the title, while the only path that cleared the title was
the one at the end of the function. So a definition following a discarded one
inherited its label, and RA sends unofficial achievements interleaved with
published ones, so it was reachable on a real set: the wrong achievement's name
on the notification. Invisible until now because a wrong label is a wrong label
and nothing compared it to anything. raPatchForget() is now the one place that
abandons a held definition, and the test pins the case.

## Write down why the viewer needs an index rather than a parser

*2026-08-16 01:02*

The launcher half of the viewer is done. The menu half is blocked on one thing
worth stating before someone rediscovers it: ra_split_definitions() mutates the
block in place -- newline to NUL so rcheevos gets C strings, and the tabs after
the memaddr and the title likewise -- so by the time the menu can be opened, the
NUL that ends a record is indistinguishable from the two that came from tabs.

Every scheme for recovering the boundaries from the bytes alone is a heuristic,
so arm9_ra should publish a viewer index built at init while the block is still
pristine, in the definitions' own reservation beside raPendingBlock. And the
three things that then move together are named, including the .space mirror of
sizeof(IgmText) in card_engine_header.s that no compiler checks and that crashed
the menu the first time the folder was added.

## Reserve the viewer's index, and pin it against its neighbours

*2026-08-16 01:43*

The menu cannot parse the definitions block, and the reason is that the block is
mutated in place. ra_split_definitions() turns a record's newline into a NUL so
rcheevos is handed C strings, and the tab after the memaddr and the tab after
the title likewise. By the time a player can open the menu, the NUL that ends a
record is indistinguishable from the two that came from tabs -- and an earned
`#!` record, which that function skips entirely, still has its tabs. Two shapes
in one buffer and no rule that separates them without guessing.

So the offsets are recorded while the block is still pristine, by the same pass
that is about to mutate it, and the menu reads a table instead of a text.

Offsets rather than pointers, because the block sits at one address in the
launcher where it is staged and another in DSi WRAM where it is read; a pointer
recorded on one side is meaningless on the other. Offset 0 means absent, which
is unambiguous because offset 0 is the first record's first byte and no field
can start there -- and that is exactly what a record degraded by a full block
looks like from here.

2K below the pending tally, in the same reservation and on the same terms, and
the launcher's blockMax comes down by both. That number is the only thing
standing between a large set and those two structures, since the scanner fills
whatever it is given.

The host suite pins sizeof(raViewerBlock) against the reservation, the two
copies of the magic against each other, and the arithmetic that says the index
ends exactly where the pending tally begins. raViewerEntry is 12 bytes only
because its three offsets are u16: widening one to u32 would push 128 entries
over the reservation and into the tally above it without a line failing to
compile.

## Fill the viewer's index, and let it own where a field begins

*2026-08-16 01:48*

ra_split_definitions() now indexes every record as it walks, while the block is
still pristine, and ra_viewer_add() replaces each field's tab with a NUL as it
records that field's offset. So every offset in the index is the start of a C
string, in both record shapes.

That last part is a correction the host suite forced, and it is worth keeping.
The first version recorded offsets and left the cutting to the caller, which had
it half right: the armed path cut the first two tabs and nothing cut the third,
so pointsOff pointed at "5\tClear Stage 2" -- and an earned `#!` record, which
the split skips entirely, kept all three tabs and gave a title of "Welcome to
the Jungle\t3\tClear Stage 1". The menu would have printed those verbatim. The
test found it by reading the fields back through the index against the *mutated*
block, which is the state the menu actually sees, rather than by inspecting the
buffer beforehand.

Cutting in one place also removed a duplication. The memaddr and the title are
terminated by two of those same cuts, so the split takes both from the entry
instead of walking the record again with its own copy of the rule -- one place
now decides where a field begins, and the notification and the menu cannot
disagree about it.

The magic is written before the entries rather than after, which is the opposite
of every other block here and deliberate: elsewhere it means "this is complete",
here it means "this binary owns the window", and the count beside it says how
much is real. A half-filled read cannot happen anyway -- the split runs at init,
long before a player can open the menu.

A full index gives no entry and the definition still arms. An achievement that
cannot be listed is a smaller loss than one that cannot fire.

## The achievements page, and a check for the mirror that kept breaking

*2026-08-16 01:55*

The page reads the index cardenginei_arm9_ra built at init and never parses the
block. Two levels, because 32 columns cannot hold a title, its points and its
description at once: the list gives one line each -- a mark, the title, the
points -- and A opens the description of the line under the cursor. That split
is also what keeps it usable on a large set, since forty achievements are eight
screens of one line and forty screens of three.

The mark is a character rather than a colour alone. The two palettes are close
enough on a lit DS screen that a photograph could not settle which row was
which, and this project reads a lot of photographs. It sits at column 1 because
column 0 belongs to drawCursor(), which clears that column on every row to erase
the previous caret -- a mark at 0 would survive exactly until the cursor moved.

Descriptions are wrapped by hand at 32 columns, broken at a space where there is
one within reach, with a one-long-word fallback that cuts rather than looping.

An empty page says which kind of empty it is. No magic means this boot staged
nothing -- no network, or a game the server does not know. A magic with no
entries means a set that arrived empty, which is what an unsupported ROM's own
set looks like.

And the mirror. struct IgmText grew twenty bytes for the second label, so
`.space` in card_engine_header.s went 0xF68 to 0xF7C alongside the C++
static_assert. Nothing links those two files, and when they last disagreed every
symbol after the text block landed short of where the C side computes it: the
menu jumped into the middle of its own text and Contra 4 died on the frame it
opened, on a build that compiled clean.

So tools/ra_release.sh now takes the answer from the link instead of from
intent. sharedAddr sits immediately after the block, 16-byte aligned, so its
offset from igmText *is* IGM_TEXT_SIZE_ALIGNED; the script compares that against
the header's own number and refuses on a mismatch. Verified by putting 0xF68
back and watching it refuse. The linked binary agrees on all three derived
offsets -- sharedAddr 0xF80, igmPal 0xF8E, igm_arm9 0xFA0.

## The page shows what is queued, pages sideways, and stops losing its A

*2026-08-16 02:19*

Four things, and the first is the one I had already written a warning about.

`chievements`, and `02 of 45` as `2 of 45`. drawCursor() clears column 0 of
every row to erase the previous caret, so anything printed there loses its first
character the moment the cursor is drawn. The mark was put at column 1 for
exactly this reason and the header was not. Nothing on this page starts at
column 0 now, the description included -- which also drops its wrap from 32
columns to 30, since it begins at 1 and the last column is left clear.

Queued achievements get the star in red. Three states rather than two, and the
middle one is what a player actually wants to see: earned on the server, earned
and still in the queue, not earned. Queued keeps the star because it *is*
earned; what is missing is the acknowledgement, and red says that without
pretending it did not happen. The detail page says `(sync pending)` in red where
an acknowledged one says `earned` in green -- the sending is what is outstanding,
and saying it that way is what stops a player wondering whether the achievement
itself is in doubt.

Knowing which ones are queued needed both halves of the fork, because neither
knows alone. The launcher reads the queue file at boot and now leaves the ids
beside the pending tally it already stages; cardenginei_arm9_ra matches them
while it indexes the set. And an achievement that fires *this* session is in
neither list, so ra_rc_queue_unlock() flags its entry as it queues the id --
"I just got that, is it safe" being the question this page exists to answer.

Bounded at 32 ids, well under RA_QUEUE_MAX. A deeper queue is a card that has
been offline a long time, and the honest failure there is a few unmarked rows
rather than 256 bytes taken off a 512-byte reservation for a case nobody is in.

Left and right page through the list, clamped rather than wrapped, with the
cursor pulled back to the last real row on the final page -- a caret on a blank
line below the set would be the page inviting a press that does nothing.

And the two footer lines became one, `A: OK / B: Back`. The row that frees is a
row of the list, and on a 24-row screen with forty-five achievements to show a
row is worth more than a second hint.

## Measure the Rich Presence script, and keep nothing

*2026-08-16 03:35*

Rich presence has two halves and only one of them is blocked. Rendering a script
on the console is reachable -- it is memory reads against a script, which is what
this fork already does sixty times a second, with rcheevos already here and an
arena with margin. Sending one is not: the game's boot kills the link, and
dsiwifi's ARM7 half wants 104,148 bytes against 12,636 free. That is measured
and written down.

So the open question for the reachable half is not whether a script can be
evaluated but whether it can be *stored*. The block is 32K less the viewer's
index and the pending tally, and a real set already takes 9,662 of it. RA's
scripts run from a single line to tens of kilobytes depending on how many lookup
tables the author used, and no amount of reasoning settles which this project is
facing.

One counter and one boot does. A fifth needle counts `RichPresencePatch` as it
streams past and throws every byte away. Decoded length, by the same rule the
title and the description use, so the number is comparable with theirs rather
than being a wire length nobody would store. `richSeen` is separate from a zero
count because a script of length 0 and no script at all are different answers.

The needle satisfies raPatchAdvance's restart-and-retest property like the other
four: `"RichPresencePatch":"` repeats the quote and several letters, but the
two-character prefix is `"R` and no later quote is followed by an `R`.

Nothing else changes. The suite pins the count against the fixture's own script
and pins that the block came out byte-for-byte what it was before the needle
existed.

## Three boots answer the rich presence budget question

*2026-08-16 14:42*

Ketsui 1,786 bytes, Contra 4 1,768, Super Mario 64 DS 14,115. An eight-fold
spread, and the two extremes are the same game: Mario 64 DS has both the largest
set and the largest script, so they compete exactly where competition hurts.

Its 28,585-byte set is measured *without* titles, points or descriptions -- with
them it passes 33,600 and overflows the 30,199-byte block on its own, before any
script. Its arena is at 91% as well, so there is nowhere inside the window to
move either.

The policy that follows is fit-or-drop, counted and logged, rather than a cap: a
truncated Rich Presence script is not a shorter script, since its lookup tables
are most of its length and rcheevos would refuse the remainder. Two of the three
games measured can have rich presence and the largest cannot.

The route that would cover it too -- put the script on the SD and hand the
cardengine its cluster the way ra_unlocks.txt is handed over, so it never
competes with the definitions -- is named rather than pretended away. It moves
the cost to the arena at parse time, which for the one game that needs it is
already at 91%, so it needs its own measurement before it is a plan.

## Refuse hardcore rather than claim it, and say what is in the way

*2026-08-16 14:51*

Hardcore's rules forbid cheats, savestates, rewind and slowdown. What this fork
can be held to is what it can observe, and reading nds-bootstrap for it turned
up one thing that is not there and one that is.

Savestates: **nds-bootstrap has none.** There is no savestate feature anywhere
in the tree. Nothing to switch off and nothing to check, and it is stated in the
code rather than left as an assumed gap -- "we did not find it" and "it does not
exist" are different claims and only one of them is true.

Cheats: conf->cheatSize is non-zero when a cheat file is loaded for this ROM.
Observable at boot, and gated.

And the one that was not on the list. **The in-game menu's RAM viewer writes** --
inGameMenu.c sends RAMW alongside RAMR. That is a cheat device by any reading of
the rules, it is two button presses away in every build that has the menu, and
it is live during play rather than decided at boot. So the gate refuses hardcore
unconditionally for now: there is no setting to consult, the capability is simply
present. Gating it properly is the next piece and it belongs in the cardengine,
not here.

The rule the gate follows is fall back to softcore and log why, never claim
hardcore and hope. An unlock claimed as hardcore under a cheat file is exactly
what gets a client's User-Agent refused, and this fork's is still trying to be
recognised at all.

Decided before stage 10 so every request in the ladder is signed with the mode
the session actually runs in -- deciding it later would sign the login one way
and the awards another.

## The RAM viewer closes for a hardcore session

*2026-08-16 15:19*

The hardcore gate refused every session, and only one of its two reasons was
about the player's configuration. The other was that the in-game menu's RAM
viewer writes: a cheat device by any reading of the rules, live during play
rather than decided at boot, and present in every build with the menu. There
was no state to consult, so the gate consulted none.

There is state now. The launcher stages the mode it settled on into a fourth
block in the RA window, the bootloader copies it like the other three, and the
menu refuses to enter edit mode when it reads hardcore. Reading memory is
untouched -- the rules are about modifying, and a hex dump of a running game is
a debugging tool this fork has no reason to take away.

The block is separate from the pending tally rather than a field in it, and the
reason is when rather than where. raWifiStagePending() runs at stage 13, so
every ordinary early exit -- sync=0, no access point, a refused login -- leaves
no tally at all, while the ladder still falls through to done:, loads the
cached set and plays the game. Earning achievements with the radio off is the
normal case here. A flag in a block absent on exactly those boots would read as
"not hardcore" precisely when it matters. This one is written the moment ra.cfg
is parsed, above every goto done.

Absent means unlocked, which is the safe direction: every boot that stages no
block is a boot that cannot submit a hardcore unlock. loadFromSD() clears the
fourth staging word alongside the three it already cleared, so the guarantee
does not depend on the previous boot.

One bug found on the way past: loadRaDefinitions() capped the hand-written
definitions file against the reservation without subtracting the structures at
the top of it. raWifiFetchPatch() has subtracted them for a while; a hand file
looked safe because it is bounded by whoever wrote it. It is the same bound,
and at 30 KB it would have written through the session block and handed a
hardcore session its RAM editor back. Both caps now subtract all three.

Not settled, and now the next real question: the queue records no mode, so
flipping hardcore=1 between the boot that earned an unlock and the boot that
sends it upgrades it. The fix fits in the record's spare bytes and is held only
because it depends on whether RetroAchievements sanctions deferred submission
at all. docs/ra-registration-request.md drafts that conversation.

Built with tools/ra_release.sh, host suite green. Not yet on hardware; what to
look for is in the doc.

## A queued unlock carries the mode it was earned in

*2026-08-16 15:34*

Closing the RAM viewer exposed the other half of the same problem. The mode
was applied at submission time, from ra.cfg: play softcore with the editor
open, earn unlocks, quit, set hardcore=1, boot, and the launcher sends every
one of them with h=1, correctly signed and indistinguishable at the server's
end from the real thing.

That was theoretical while the gate refused every session outright. Lifting
the gate made it reachable, which is what moves it from a note to a fix.

The session that earned an unlock is over by the time it is sent -- possibly
days over, on another game, in another mode -- and ra.cfg describes the session
about to start. The record is the only object crossing between the two, so it
is where the mode has to live: a fifth field on the queue record, appended so
every existing file still parses, and no migration because the record was
already 48 bytes and the longest one went from 44 to 46.

h= and the signature now come from the record, in both directions: an unlock
earned in hardcore is still sent as hardcore on a boot since set to softcore.
raWifiSubmitOne() lost its const raConfig* to this, which says it better than
a comment could.

The ARM7 writes the record and cannot read the session block -- that window is
not mapped for it -- so the mode crosses with the unlock. It crosses in the
request's magic rather than a slot of its own: there are four usable slots and
this feature already holds two, and a separate flag could be left unset by a
path added later, where a magic cannot be raised without saying which kind it
is.

Absent reads as softcore, which covers hand-typed ids, older builds, and a
record whose clock failed. The parser consumes the digit whether or not it
uses it -- left behind, the outer loop reads 1 as the next record's id, which
is the CONTRA4 lesson again. raQueuePack() writes it back, because kept
records are the ones the server never answered and are exactly the population
that must not be downgraded on retry.

Cost: cardenginei_arm7_twlsdk is down to 60 bytes of link margin from 76. It
is the tightest binary in the tree and this spent 16 bytes of it.

Built with tools/ra_release.sh, host suite green including the consumption
test that would have caught the id-from-a-digit bug. Not yet on hardware.

## Ask whether cheats are on, not whether a cheat file exists

*2026-08-16 16:11*

The gate's surviving half was conf->cheatSize != 0, which is the wrong
question asked of the wrong file, and wrong in both directions.

nds-bootstrap decides cheats from three inputs, not one:

  cheatSizeTotal = wideCheatSize + cheatSize + (apPatchIsCheat ? apPatchSize : 0)
  cheatsEnabled  = cheatSizeTotal > 4 && cheatSizeTotal <= 0x8000

Two of the three were never looked at. A card with wide cheats and no
cheatData.bin, or with an AP patch that is really a cheat file -- pck_load.cpp
sets apPatchIsCheat for a .bin AP fix and for a cheatVer pack entry -- ran the
cheat engine while the gate reported a clean session and let it claim
hardcore.

And the floor is > 4 rather than > 0 for a reason. TWiLight Menu writes
cheatData.bin when the player opens the cheat list for a game; turning every
cheat back off leaves the file there holding its terminator. Testing != 0
refused hardcore to a player who had looked at the cheat screen once and
switched everything off, which is the state RA would call clean.

The launcher now sums the same three files against the same floor. It
deliberately does not reproduce the ceiling: that comes out of the ROM's
layout and already exists three times in the bootloader with two different
values. So the bootloader has the last word, one line after it copies the
session block, where the answer is finally settled -- and it can only
downgrade, because the launcher has already signed r=startsession with what it
believed.

It reaches the flag by offset rather than through the struct, like every other
reach into these blocks from that file, which does not include ra_wifi.h. The
host suite pins offsetof(raSessionBlock, hardcore) against the constant: a
field inserted before it would move the flag, the bootloader would clear a
byte of the magic instead, and a cheating session would get its RAM editor
back with nothing failing to compile.

Free on the ARM7 -- the total was already computed there for the engine's own
sake -- so cardenginei_arm7_twlsdk stays at 60 bytes of margin.

Built with tools/ra_release.sh, host suite green. Not yet on hardware; the doc
names the third boot this needs.

## The menu says which mode the session is in, and why

*2026-08-16 16:24*

Everything so far changed what the loader does without changing what a player
can see. The only visible trace of hardcore was a refusal in the RAM viewer,
two pages deep, which only appears if you go looking for the one thing that is
now forbidden.

So the RetroAchievements folder carries a line above its own name:

  Hardcore -- RAM editing locked   the session is hardcore
  Softcore -- cheats are on        asked for, and the cheat engine took it
  Softcore                         ra.cfg says so, or there is no ra.cfg
  No session this boot             nothing staged one -- a plain build

A line rather than a page: it is one fact, and a page for one fact charges a
button press for nothing. The folder's own comment has said since it was
written that it exists so showing the session has somewhere to go.

The reason is the half that earns it. "Softcore" alone answers a question
nobody was asking; the player who needs this screen set hardcore=1, is looking
at a softcore session, and until now could only find out why by powering off,
taking the card out and reading ra_wifi_launcher.log on a PC.

So the session block grew a refusal byte beside the flag -- a code rather than
a string, because it crosses into a binary with no formatter and the set of
reasons is small and closed. The bootloader sets it when it takes hardcore
away for cheats, and only when there was something to take: writing it on a
session that never asked would have the menu explaining a refusal that never
happened.

hardcore stays a flag rather than folding the reason into it as an enum, and
the host suite pins the byte at one byte to keep it that way. Two places read
it as a capability -- the RAM viewer opening its editor, the unlock path
choosing a magic -- and both test != 0, so a third value added later would
read as hardcore in exactly the two places where being wrong is expensive.

cardenginei_arm9_igm grew 280 bytes, to 21,428 of the 28,160 the B4DS layout
allows.

Built with tools/ra_release.sh, host suite green. Not yet on hardware -- but
this is now the cheapest way to read the result of the other three changes,
without pulling the card.

## Say what hardcore=1 costs today, and how to try it safely

*2026-08-16 16:42*

The example config still described this fork as softcore with "no restrictions
on savestates or cheats". Both halves are now false, and the replacement had
to say more than that.

Setting hardcore=1 with sync=1 before the User-Agent is recognised can lose
unlocks. raWifiSubmitOne() keeps a record only when nobody answered; one the
server answers and does not accept is cleared, because that rule was written
for "unknown achievement" and "already held", where retrying forever is wrong.
Nobody has seen what the server does with h=1 from a client it does not know,
and if the answer is a refusal, that rule discards a real achievement.

Deliberately not guarded against. A guard would have to tell "this client may

about.

with sync=0. The session is staged before the radio is touched, so the lock,
the menu line and the recorded mode all work and nothing is sent or cleared.
The hardware checklist now says to use it for every hardcore test.

## Write down that there is no cheats switch to read

*2026-08-16 16:53*

`cheatSizeTotal > 4` reads like a threshold somebody tuned, and the reason it
is not was left implicit.

nds-bootstrap has no cheats on/off setting anywhere. Not in the configuration
struct -- the only cheat-shaped fields are file clusters and lengths. Not in
the in-game menu: MenuItem has no cheats entry and the "Cheats..." string is
commented out in conf_sd.cpp, with menu[6] since reclaimed by "RAM Viewer...".
The engine binary is staged unconditionally on every non-DSiWare boot, so its
presence means nothing either.

The switch is TWiLight Menu, which writes only the cheats the player ticked.
By the time nds-bootstrap sees it, an intention has already become a length --
so asking how many bytes of cheats are about to be installed is not a proxy
for the question. It is the question, and the only form of it available on
this side.

Which also explains the 4: it is the length of a file holding a terminator and
no cheats, left behind when the player opens the cheat list and ticks nothing.

The registration draft said the same thing loosely; it now says the loader has
no switch, since that is the part a reader would otherwise assume we skipped.

## Name the hardcore risk correctly: silent acceptance, not refusal

*2026-08-16 17:28*

The warning written two commits ago was the intuitive one and the wrong one,
and both wrong versions are now kept in the doc because the wrong ones are the
ones a reader arrives with.

It said hardcore=1 can lose unlocks, on the grounds that a refused award is
cleared from the queue rather than kept. The mechanism is real, but the
conclusion is not: a refusal means the server recorded nothing, so r=unlocks
does not list it, the scanner does not skip it, the definition is staged again
and rcheevos arms it again. The player replays that stretch of the game.
A cost, not a loss.

The irreversible case is the opposite one. If the server accepts h=1 and files
it as a softcore award -- a reasonable way to implement "this client may not
earn hardcore" -- the account holds it in softcore, raWifiUnlocks() asks with
h=0 and always has, so that id lands in the skip list, the definition is left
out of the block, and it can never be earned in hardcore. The danger is the
silent acceptance, not the refusal.

Two other things the earlier advice got wrong. sync=0 protects the queue only
as a side effect of turning the whole network off; submit=0 is the knob that
addresses this, and it keeps the ladder and the fetch. And sync=0 has a cost
that went unmentioned: no set is fetched, so a ROM with no cache fires
nothing, and the pending tally is staged ten rungs past that exit.

Also written down: the first boot after switching hardcore on risks nothing
either way, because the queue then holds only records from before the mode
field, which read as softcore and go out h=0. The exposure needs a hardcore
session to have queued something and a later boot to send it.

Still not guarded against, and now for a stronger reason -- the silent case
has nothing in the reply to match on, which is the whole problem.

Documentation only; no code changed.

## The mode digit was read as an achievement id, and submitted

*2026-08-16 17:39*

First hardware run with hardcore=1, sync=1, submit=1 on Contra 4 sent two
unlocks. One of them was id 1, which the server accepted --
AchievementsRemaining 34 against 44 for the real one, so it belongs to a
different game and the account now holds it.

It was the mode field's digit, left in front of the outer loop. The exact
failure that field's own comment warned about, from the one cause the comment
did not think of.

raUnlockAppend() writes gameTitle as a fixed twelve bytes straight out of the
ROM header, because trimming costs bytes the ARM7 does not have. Contra 4 pads
CONTRA 4 with four NULs. takeField() stops at the first byte outside printable
ASCII, so it stopped on the padding, four bytes short of the tab introducing
the mode. The parser looked for a tab, found a NUL, and gave up. Harmless for
as long as the title was the last field; appending one turned it into a
submitted unlock.

The test for this existed and passed. It was written against raQueuePack()'s
output, which trims. Two writers, one reader, and every test in the file
exercised the writer that agreed with it -- the cardengine's own record shape
had never been fed to the parser on a host. The suite now builds the record
byte for byte as the ARM7 does. Neutered, the fix fails it six times.

Fixed twice. skipPadding() steps over NUL padding inside a fixed-width field
so the next delimiter can be found -- only NULs, which is the bound that keeps
it from swallowing the record after this one.

The second gate is structural and is the one to keep: a record that carried a
stamp is machine-written, so nothing else on its line is an id, and the parser
runs to the newline whatever is left. A tab after the id is what no hand-typed
list can contain, which already licenses reading fourteen digits as a date.
Bare ids on a tabless line keep the forgiving behaviour that makes the file
hand-writable.

Measured: with skipPadding() disabled and only the newline guard, the
hardware-shaped records parse as the right count with nothing fabricated,
losing only the mode they could not reach. Six failures become three, none of
them an invented unlock. Consuming each field correctly is a rule every future
field has to re-earn; stopping at the newline holds for fields nobody has
written yet.

The run also did not test hardcore. With the mode unparsed both awards went
out h=0, and the missing "earned in hardcore, per the record" line is the
tell. What the server does with h=1 is as unknown as before the boot.

## The self-test's id was 1, and 1 is a real achievement

*2026-08-16 18:03*

A player asked where achievement 1 kept coming from. It had been arriving
since early on, belongs to no DS set, and looked like something
RetroAchievements did rather than something we did. It is ours.

RA_TEST_ACHIEVEMENT_ID was 1, under a comment reading "any non-zero number
does; it is only how the runtime identifies the trigger back to us, and
nothing here talks to the server yet". Every clause was true when written. The
last stopped being true when step 6b closed the loop, and the constant did not
follow.

So the guard in ra_rc_queue_unlock() was written for this exact failure and
did not catch it. It tests id >= RA_SYNTHETIC_ID_BASE, because the card that
exposed the bug carried 4026531840 -- 0xF0000000, what a staged definition
with no id gets. The built-in self-test is the other kind of idless definition
and had its own constant four hundred lines away. One bug, two spellings, and
the fix spelled it one way.

Consequence is the kind that section already called worse: a synthetic id gets
a 404, a real id gets accepted. Achievement 1 is published on a Mega Drive
game, so every boot of a DS game the server does not know filed a Sonic unlock
on the account. Confirmed from the site by the player, and deleted there.

Fixed by removing the second number rather than adding a second check:
RA_TEST_ACHIEVEMENT_ID is now RA_SYNTHETIC_ID_BASE. Nothing collides -- an
idless staged definition takes the base plus its index, and the self-test only
activates when nothing else did, so index 0 is never both.

Pinned by calling the guard, not by comparing constants:
ra_rc_queue_unlock(RA_TEST_ACHIEVEMENT_ID) must leave the ring untouched and
bump unlockSynthetic. What has to hold is that nothing this binary invents can
be queued. With the old value the test fails three times.

Nothing filters a queued 1 on the way in. 4026531840 can be dropped safely
because no real id is near it; 1 cannot, because 1 is real. A rule that
dropped it would be a guess about RA's id space dressed as a check. Deleting
sd:/ra_unlocks.txt clears a card that still holds one.

And it was not the id in the run that found it: that one arrived without o=,
where a self-test record carries a stamp like the 4026531840 one does. That 1
was the mode field's digit behind the padding bug. Two independent sources,
one wrong id, and only the missing timestamp separates them.

## Two boots answer the hardcore question, and confirm the parser fix

*2026-08-16 18:20*

Boot 1: empty queue, hardcore=1, sync=1, submit=1, Contra 4 played, two
achievements earned. Boot 2: same ROM, booted only to sync.

The queue file settles the parser half in bytes rather than in argument:

  b'302349\t20260816140959\tYCTE\tCONTRA 4\x00\x00\x00\x00\t1\n\x00...'

There is the padding -- CONTRA 4 in a twelve-byte field, four NULs, then the
tab and the mode. The old parser stopped on the first of those NULs. Boot 2
read both records, both stamped, both hardcore, with no phantom id and the
line "2 of them earned in hardcore, per the record". skipPadding() and the
end-of-line guard are confirmed on the exact byte pattern that broke them.

And that line is also the proof h=1 was really sent, since it prints the same
q.hard the URL and the signature are built from. The server answered:

  {"Success":true,...,"Score":1154,"SoftcoreScore":462}
  {"Success":true,...,"Score":1154,"SoftcoreScore":455}

Score does not move; SoftcoreScore does. r=startsession returns
HardcoreUnlocks: [], r=unlocks&h=0 afterwards returns both ids, HardcoreMode
is false, and the next fetch drops from 45 definitions to 43 with #!302329
marked earned.

So the server accepts h=1 from an unrecognised client, answers Success:true,
and records a softcore unlock. Not a refusal -- a silent downgrade, which is
the one outcome this document said had nothing in the reply to match on. There
is nothing to match on.

Which corrects the ra.cfg warning in the other direction. It called this the
bad case and framed it as a cost of turning hardcore on. An unlock is filed
softcore whether this client sends h=0 or h=1, so h=1 buys nothing today and
costs nothing extra. "An achievement is spent the moment it lands" is the
standing behaviour of a softcore client, is not about hardcore, and is why
submit=0 exists.

The registration draft now reports the measurement rather than asking about
it, which is a better position to ask from.
