## Step 4 crashed. Three hypotheses measured and killed, one real bug found

*2026-08-09 00:09*

The first run of the server's 56 definitions inside the game ended in a Data
Abort with PC 0x0377EEEA and lr 0x0377EE05 -- both inside the definitions block.
PC is offset 28,386 into the definition text and lr's Thumb target is 21 bytes
into line 52, mid-string. So control flow left the code and the ARM9 was decoding
the achievement set as instructions. That is all the photograph proves.

Stack depth was the obvious suspect and is not it. Measured on a host by building
rcheevos with -finstrument-functions: 2,383 bytes for the deepest definition in
the set, 2,079 for the shallowest -- and 2,383 for the self-test definition and
for the shape of the three that have always worked on hardware. The parser is
iterative, so depth does not scale with the definition, and the definitions that
worked use exactly as much stack as the ones that crashed.

The arena is not it either: 128,352 bytes from __bss_end reaches 0x03770B7C, 29 KB
short of the block at 0x03778000.

The linker script is real but is not the crash. cardengine.ld.in inherited
__sp_irq, __sp_svc, __sp_usr, __irq_flags, __irq_flagsaux and __irq_vector from
the libnds script it was copied from, all computed down from __vram_top -- so all
six land inside the definitions block, and a stack seeded at __sp_usr would grow
down through the achievement set. Nothing references them (no crt0; the crash
screen's sp is in main RAM), so they were harmless by accident. Deleted rather
than relocated: an unused symbol pointing at live data gets used eventually, and
absent means a link error, which is the failure to want.

What turned up instead is a genuine bug. ra_read() fell through to a 32-bit load
for any size that was not 1 or 2 -- correct for watch lines, which are restricted
to 1, 2 and 4, and wrong for rcheevos, which asks for three when a definition uses
0xW. Line 39 of this set has one. So a 24-bit read answered with 32 bits, and
because that 0xW is an AddAddress the extra byte becomes part of a pointer and the
read after it lands somewhere the definition never named. The alignment test in
peek() had the matching flaw: (address & (numBytes - 1)) assumes a power of two, so
with three the mask is 2 and an address 1 mod 4 passes a test it should fail. Every
width goes through ra_read() now, which assembles anything that is not a native
aligned width from bytes. This is not claimed to be the abort -- the faulting
address is in the block, not in game RAM -- but it would have made achievements
silently never fire.

What remains unmeasured is the one thing that scales: total time inside the game's
VCOUNT handler. rcInitTotal was added to measure it and the run died first. So
activation is spread over frames -- RA_RC_LOADING, one definition per tick, about a
second for the set. If that was the cause it is gone; if it was not, it is off the
list, which is worth as much.

The half that matters more is diagnostic: rcActivated is published after every
definition, so a crash names the line it died on. A set that dies at the same
definition every time is one definition's problem; one that gets through all 56 and
dies later is the frame budget's. The previous build published nothing until all 56
were in, which is exactly the value a crash does not give you.

RA_RC_LOADING went in at 5, moving RA_RC_ACTIVE to 6 and RA_RC_FRAME to 7. Every
guard reads `rcStage < RA_RC_ACTIVE` so none needed changing, but readings
photographed before this build read one lower and the checklist is updated.
Renumbered rather than parked above ACTIVE, because a loading state sorting after
active would invert every one of those guards.

The host test drives the state machine the way hardware does -- prepare, then one
call per definition, bounded -- so a machine that never reports ACTIVE fails in
milliseconds instead of wedging a console. Two things fell out: ra_rc_prepare()
resets every static it uses, because the test prepares twice and a carried-over
count showed up immediately; and an assertion of `wramTicks == 10` became
`before + 9`, since the absolute number encoded how many ticks happened earlier in
the file.

## It is the game's IRQ stack: rcheevos gets one of its own

*2026-08-09 00:28*

Three crashed runs, and the third is the one that settles it. A set trimmed to
lines 9-56 -- no 6,264-byte definitions, 311 of the 1,946 conditions, and 27,664
bytes of the arena out of 158,644 -- crashes with the same signature as all 56.
That kills the frame budget, total memory, and any particular heavy definition in
one run.

Both of the last two crashes have PC in the game's own data with ADDR 00000000.
Nothing nds-bootstrap places in DSi mode lives at 0x023Cxxxx and SM64DS's ARM9
ends at 0x0205D544, so the ARM9 was executing game memory -- which is what
corrupted game state looks like from outside.

ra_tick() is called from myIrqHandlerVcount(), so everything here runs on the
game's IRQ stack. Measured on a host with -finstrument-functions:
rc_runtime_do_frame() needs 767 bytes and has run every frame for many sessions
without trouble; rc_runtime_activate_achievement() needs 2,383. The parse wants
3.1 times what the evaluation does, and a real set turned three parses into
fifty-six.

Worth being precise about the earlier stack measurement, because this is a
correction to a conclusion rather than to a number. It showed depth is flat --
2,079 to 2,383 across the set, and the same 2,383 for the definitions that have
always worked -- which correctly killed "the big definitions recurse deeper". It
was then read as exonerating the stack, and that does not follow: flat and too
large is still too large. What changed between working and crashing was how many
times the excursion was taken, and over memory the game was by then using. The
three-definition builds overflowed too; they did it during boot over memory the
game had not started using, which is luck.

So rcheevos gets 8 KB of its own in the cardengine's window, against a measured
2,383, with the arena still holding 130 KB of margin at this set size.
ra_rc_on_stack() switches sp around each step -- r4 and r5 carry the old sp and
the target and are in the clobber list, which is what stops the compiler placing
an input in either; an earlier shape took the function pointer in r0 and then
loaded the argument into r0 before branching. do_frame runs on it too, so there
is one stack to reason about and the high-water mark covers everything rcheevos
does.

rcStackUsed (+0x6A) reports that mark, measured the way the host could not: the
region is painted once and the deepest word that changed bounds every excursion
of the session. It went into reserved2, so no offset above it moved, and the host
test pins it. The next reading is a prediction rather than a hope -- it should
land near 2,383, and 8192 exactly would mean 8 KB is not enough either.

The host build calls straight through rather than switching stacks, so the suite
does not exercise the switch; it exercises that everything reached through it
still works.

## Step 4a: fetch at boot, then boot the game

*2026-08-09 00:51*

The online half of step 4 is two problems that have been conflated all along.
4a is fetching in the launcher and then booting, with no network inside the game;
4b is network in context B, which is what r=awardachievement needs and what #1g has
flagged from the start. This is 4a. 4b is not started.

The launcher already ran the whole ladder and staged the set before runNdsFile();
the only reason it never booted was that mode 1 halts deliberately, because four
things are live when the ladder finishes and every one fires after the bootloader
has replaced the code it belongs to: the ARM7's SDIO card IRQ and its TIMER3, the
ARM9's TIMER3 driving ath_lwip_tick(), and dsiwifi's datamsg handler on
FIFO_DSWIFI.

DSiWifi_DisconnectAP() is an unimplemented sassert(false), but wifi_card_deinit()
in dsiwifi's ARM7 half does exactly the right four things. It is declared by hand
because arm_iop/source/wifi_card.h is not on the exported include path -- which is
how dsiwifi's own test_app reaches it. The ARM9's two are ours to stop.

What nothing does is power the chip down; dsiwifi has no path for it. So the game
boots with the radio associated and its interrupts masked. Nothing can poke either
CPU and nothing is moving memory, but the chip is on, and that is stated rather
than glossed because it is what 4b inherits.

The ARM7 goes first, since it holds the chip -- until its card interrupt is masked
the radio can still call it -- and only then the ARM9's timer and FIFO handler.
The handshake is a round trip on FIFO_USER_07, because 01 through 06 are spoken for
and a channel with two owners is the bug this project already paid for once with
FIFO_DSWIFI. wifi_card_deinit() runs from the ARM7's idle loop rather than the FIFO
handler that asks for it: it polls SDIO registers, and that is not a wait to take
inside an interrupt on a CPU about to be overwritten.

If the ARM7 never acknowledges, mode 2 halts exactly as mode 1 does. That is the
better bad outcome -- the alternative is a crash inside the game minutes later with
nothing on the card explaining it.

Mode 2 also introduced a regression worth naming. Stage 12 invalidates the block
before sending, so a reply that never arrives cannot leave stale bytes looking
valid. Free in mode 1; not in mode 2, because the block already holds the user's
ra_achievements.txt, staged during loadFromSD(). A console with no network would
lose the definitions it would otherwise have played. Preserving them is not
available -- the reply is three times the block, which is why it is streamed into
it -- so the file is re-staged on every failure path after the invalidation.
loadRaDefinitions() stopped being static for that.

The build stamp had to learn to count: $(if $(filter 1,...),on,off) cannot tell 1
from 2 and would have handed back objects built for the wrong mode, which is the
same silent-success failure the stamp exists to prevent. It records the raw value
now, verified by building 2, then 1, then 0 and grepping each mode's own strings out
of the .nds.

One thing checked rather than assumed: mode 2 calls myConsoleDemoInit() and then
boots, which no build had done before. It is fine, and not by luck --
createRamDumpBin() and the pagefile creation both do exactly that on any game's
first run.

## Step 5: the definitions block carries achievement ids

*2026-08-09 01:13*

Every staged line was a memaddr and nothing else, and the cardengine numbered them
1..56 by position. Invisible while nothing reported anything, and blocking for
everything that would: r=unlocks answers in ids, r=awardachievement is asked in
them, and a popup or a leaderboard names an achievement. Each line is now
`<id>:<memaddr>`.

The discriminator is digits-then-colon, and it is exact rather than heuristic. It
has to survive a definition that begins with a digit, because the shipped set's
first line is `1=1.300.` -- and it does, because every memaddr prefix flag ending
in a colon is a letter. Checked against that set rather than asserted: of its 47
lines containing a colon, the character before the first one is M, N, O, P, R or T,
never a digit, and no line already matches `<digits>:`. Lines with no id still
work, which the shipped artifact and any hand-written file depend on.

Writing it turned up a bug worth more than the feature. The scanner attaches the
most recent `"ID":` to the next MemAddr -- ids arrive before their MemAddr, the
opposite of Flags, so no deferral is needed. But the reply opens
`{"Success":true,"PatchData":{"ID":14856,...` before reaching the achievements, so
an achievement arriving without an id of its own would inherit the *game's* and be
counted as having one. That is worse than having none: a wrong id reports an unlock
the player did not earn. Fixed by clearing the pending id at every `{`, since an id
belongs to the object it was written in -- safe against a brace inside a string
because RA puts ID first in each object and MemAddr immediately after, leaving no
text between them. The host test feeds exactly that case and requires the id not to
appear. The needle also carries its opening quote, which is what keeps "GameID" and
"ConsoleID" from matching; pinned separately.

RA_SYNTHETIC_ID_BASE is not tidiness. rcheevos identifies achievements by id and
reuses the trigger of one it has already seen, so numbering id-less lines from 1 --
as every build before this did -- was safe only while nothing carried a real id. Mix
the two and a real id of 3 collides with the third id-less line. They are numbered
from 0xF0000000 now, which six- or seven-digit real ids cannot reach.

Two silent consequences of ids being real, both fixed: the measured-progress
lookups asked about the constant RA_TEST_ACHIEVEMENT_ID, which was the first
definition's id only while everything was numbered from it, and now ask about
defIds[0]; and the event handler derived a line as `id - base + 1`, which no
server-assigned id supports, so it searches defIds instead.

The snapshot grows 0xA0 to 0xA8, appended, so every offset above keeps its address.
rcFirstId (+0xA0) is the RA id of the first unlock -- a number that can be looked up
on the set's page -- with rcDefsWithId and rcDefsNoId beside it, and stage 12's log
gains an `ids N with, M without` line.

The block grows by the ids: 56 of about six digits plus a colon is +392 bytes,
28,585 to roughly 28,977 of 32,759. That moves the block-size question from
comfortable to worth watching, and `wanted` reports it either way.

## Ids confirmed on hardware, and the data found a bug in their own bound

*2026-08-09 01:26*

`ids 56 with, 0 without`, all 56 distinct, and rcFirstId read 101000001 -- which is
line 1 of the dump to the digit. That single number closes eight hops: server,
streaming scanner, staging block, bootloader copy, the cardengine's splitter,
rcheevos' identity for the trigger, the event handler, the snapshot.

Distinctness matters more than it looks. rcheevos identifies achievements by id and
reuses the trigger of one it has already seen, so a duplicate would have merged two
achievements into one silently.

The block landed at 28,943 of 32,759 -- 88.4% -- against a predicted 28,977; ids
average 5.4 characters rather than the 6 assumed.

And 101000001 is worth a second look. Every other id in this set is between 92,869
and 579,308. That one is nine digits, its definition is `1=1.300.` -- always true,
three hundred hits -- and it is the one that unlocks about five seconds into every
session. What it is is not something to guess at; the consequence is concrete, and
it is that step 6 would report that unlock on every boot. So it needs identifying
before anything reports, and Flags 3 versus 5 will not separate it since it arrived
as core.

Which brings the actual bug. The clamp guarding both id parsers was
`if (id < 100000000u)`, written because "RA ids are six or seven digits today".
101000001 survives it -- but a ten-digit id, which a u32 holds perfectly well, comes
out one digit short and names a different achievement. Silently. That is precisely
the failure mode the commit before this one called worse than having no id,
reintroduced by a lazy bound in the same change.

Both parsers refuse on overflow now instead of clamping, the discipline
raNetJsonNumber() has had since step 3c. In the scanner the definition is counted in
withoutId. In ra_take_id() the prefix is still stripped even when the number is
refused, because a line left with `<digits>:` on the front is not memaddr syntax and
rcheevos would refuse the whole definition -- losing the ability to report one
achievement beats losing the achievement. Pinned with 101000001 from the real set,
4294967295 at the boundary, and 99999999999 past it.

## Capture what 101000001 actually is, rather than filtering on a threshold

*2026-08-09 01:34*

Two lookups settled what it is not. retroachievements.org/achievement/101000001
returns NOT FOUND, and the set's page -- which redirects to game/9983?set=6112 --
lists 55 achievements against the 56 core definitions that arrive. The extra one is
exactly that id, and it is the one that unlocks five seconds into every session.

It is still staged, deliberately. One set and one id is not a rule, and a filter on
"ids at or above 100,000,000 are not real" would be inferred from a single data
point -- the first time RA numbers a genuine achievement differently it would drop
something real, silently, which is the failure this project keeps refusing to ship.

So the reply's own bytes are captured instead. When an id at or above RA_ODD_ID_FROM
completes, the scanner copies the following 240 bytes verbatim and the log prints
them. Title, Points, Flags and Type all follow the id inside its object, so this is
the only place they can be caught without holding a reply that does not fit. The
first odd id only: one example identifies a shape.

The likely answer is already written down as a limitation -- the scanner does not
know which object a MemAddr belonged to, and this game has subsets, so a flat scan
over a reply with more than one set reads across all of them. If the capture shows
the id sitting in a second set rather than in Achievements, the fix is structural
(track which array the scanner is inside) and not a threshold.

## A retry for the lwip race the third socket lost

*2026-08-09 01:58*

The first run with r=unlocks in it never reached the fetch: stage 11 printed
`Assert "state!" failed at line 1411 in .../lwip/api/api_msg.c` and returned step 4,
RA_NET_NO_CONNECT.

That assert is the one *after* the semaphore wait in lwip_netconn_do_connect. The wait
has no timeout, so its returning means the semaphore was signalled -- and the state
still being NETCONN_CONNECT means the connect had not completed when it was. A
semaphore already signalled before the wait began produces exactly that, and netconns
come from a static pool of eight, so a recycled netconn carrying a stale op_completed
count is the shape that fits.

Nothing in stage 11's path changed. r=unlocks is stage 12 and had not run; the only
difference below stage 11 is 4.6 KB more .bss, which changes no behaviour. So this is
a pre-existing race that showed itself once, on the third socket of a run, after
several dozen runs that did the same thing and did not.

What the failure proves about the design is worth recording before the fix. The error
came back as a named step rather than a hang or a wrong answer; stages 12 and 13 both
took their fail-open paths; stage 13's early return happens before the block is
invalidated, so the user's own ra_achievements.txt survived untouched; and the radio
came down cleanly and the game booted. A random lwip race cost this run its set and
cost nothing else.

It is not fixed at the root, and the reason is that it is a race inside a vendored
lwip on a console with no debugger -- the tooling to chase a semaphore lifecycle there
does not exist here, and claiming otherwise would be worse than saying so. A retry
draws a different netconn from the pool, so a poisoned one is stepped over rather than
fatal. raNetConnect() tries up to RA_NET_CONNECT_TRIES times with RA_NET_RETRY_FRAMES
between, and the gap does work rather than marking time: lwip's processing runs off a
100 ms TIMER3 in dsiwifi's ARM9 half, so waiting frames is what lets a half-finished
netconn finish and return to the pool.

Factoring it also removed a liability that was already there -- DNS, socket and
connect existed twice, so a retry policy would have had to be written twice and could
have drifted.

## Step 3b, producer half: an earned id crosses to the ARM7's doorstep

*2026-08-09 03:20*

The cardengine has no network and the ARM9 has no SD card -- on a DSi the card is
the ARM7's, and every file nds-bootstrap writes from inside a game goes through
fileWrite() there. So an unlock detected by rcheevos has to cross CPUs. This is
the ARM9 side of that crossing; the ARM7 side is next and touches a file every
game depends on, which is why it is not in this commit.

The channel is the one that already exists. sharedAddr is how the ARM9 cardengine
has always driven the ARM7 and the ARM7 already polls it from VBlank ('TESR' and
'EXIT' are checked there today), which brings two things for free: the region is
coherent with nothing but volatile -- every card read in every game depends on
that -- and there is an established idiom of a magic in one slot and data in the
next, which is how the in-game menu already gets the battery and the clock.

Measuring where the block ends mattered more than expected. UNPATCHED_FUNCTION_LOCATION
is 0x027FFA40 and sharedAddr is 0x027FFA0C, so the block is exactly 13 slots and
sharedAddr[13] *is* the table the loader uses to restore the game's own functions.
Slots 0-8 are taken, leaving four. This takes two and the suite now asserts the
bound both ways, because overrunning it would present as a game misbehaving with
nothing pointing back here.

The protocol writes the id before the magic -- the ARM7 can wake between the two
stores, and a magic paired with a stale id would award a real but wrong
achievement. One in flight at a time; the rest wait in an 8-deep ring on the ARM9
side, and what the ring drops is counted rather than lost silently.

The host suite caught a genuine bug, not a test artifact: this binary was
dereferencing an address handed to it through a structure its own header documents
as garbage until claim() runs, and a null check would have passed on garbage and
then written four bytes to an arbitrary address inside a running game. There are
exactly two legal values, so it is now a compare rather than a heuristic, and
refusals are counted. On hardware ra_tick publishes it before every call, but
"correct because the caller happens to do it first" is not a property this project
asserts without checking.

Snapshot 0xA8 -> 0xB0, appended, so it stays at 0x027FED50 and every existing
offset the hardware checklist reads is unmoved.

## The teardown never disconnects, so in-game networking gets cheaper

*2026-08-09 15:12*

Open question #1 was closed for the launcher and open for the game, on a size
argument that is correct but incomplete: dsiwifi's ARM7 half is 104,148 bytes
against a 62,464-byte region with 12,636 free.

Keeping the link alive is not keeping the stack alive, and our own teardown is the
evidence. wifi_card_deinit() does five things and all five mask an interrupt -- the
SDIO controller's card IRQ, the AUX IRQ, TIMER3, and the chip's own two enable
registers. No reset, no power-down, no WMI disconnect, nothing sent to the AP. And
DSiWifi_DisconnectAP() is an unimplemented sassert(false), so nothing else does it
either. The firmware keeps its WPA2 session and its association; we only silenced
the path it used to tell us about them.

That changes the estimate. Bring-up, scan and the handshake are most of those 104 KB
and are needed once, which the launcher already did. Resident in-game would be two
register writes, a minimal WMI data path, and enough TCP for one connection.

The first measurement needs no code, because the shipped teardown is already the
non-destructive one: leave a game running and watch the AP's client list for the MAC
and IP the launcher already logs. Pinging proves nothing -- ICMP and ARP were lwip's
job and lwip is gone.

Prediction recorded before the run: it appears and then disappears, because the WPA2
supplicant is software on the ARM7 and a group rekey's EAPOL frames will never be
processed with the interrupts masked. A disappearance at a round interval is that
rekey and makes the idea materially more expensive; surviving a whole session opens
the cheap path; never appearing kills it for one session's cost.

## Step 3b closes: the ARM7 appends an earned id to the queue file

*2026-08-09 15:53*

The loop now starts from play rather than from a text editor. rcheevos fires on the
ARM9 inside the game's VCOUNT handler, where there is no SD card -- on a DSi the
card is the ARM7's -- so the id crosses through sharedAddr[9]/[10] and this commit
adds the CPU on the other side.

The chain the last commit mapped is now wired end to end: main.cpp stats the file,
nds_loader_arm9 puts the cluster in loadCrt0, both bootloaders' load_crt0.s carry it,
main.arm7.c passes it to hook_arm7 at both call sites, hook_arm7 writes ce7, and the
cardengine opens it with getFileFromCluster beside srParamsFile.

Appending needs no stored index. Records are a fixed 16 bytes, so record N is at
offset N*16, and the append point is found once per session by reading the first byte
of each record until one is not a digit -- which is exactly the boundary, because the
launcher zero-fills and packs unsent ids to the front. Sixty-four one-byte reads on
the frame of the first unlock and never again. A full queue is dropped and counted
rather than grown, since this CPU cannot allocate clusters. The statics are
magic-guarded like the overlay's, because this binary is copied in without a crt0 and
.bss holds whatever the last occupant left.

Two things I want on the record rather than buried.

The guard is a critical section and no mutex, deliberately: cardEgnineCommandMutex is
commented out at its declaration and a private mutex would protect nothing, since the
card-read path would not take it. IME off stops a competing read from starting, which
on this CPU is the real risk. I did not establish what else serialises card access
here, so that is the conservative subset and not a claim of correctness. The cost is
an ARM9 read stalling a few milliseconds on the frame an achievement unlocks.

And card_engine_header.s is a *second* positional mirror, of cardengineArm7. Its
offsets are pinned in hook_arm7.c against nm, on the writing side. They are not in
ra_reader_test.sh with loadCrt0's, and the reason matters: that check compiles the
struct on the host, which is valid only because loadCrt0 has no pointers. This struct
does, and a 64-bit host gives them eight bytes -- my first attempt reported a
mismatch that was the probe's fault, not the code's. Verified instead with
arm-none-eabi-gcc, which agrees at 0x34, 0x8C and 0xEC.

## Re-arm the per-frame hook from cardRead, and say which part the game removed

*2026-08-09 16:54*

hookIPC_SYNC() installs the VCOUNT hook exactly once, guarded by IPC_SYNC_hooked,
and nothing ever put it back. That was fine for every game measured until Contra 4:

## Cache the fetched set per ROM, keyed by its hash rather than its GameID

*2026-08-09 18:50*

Offline play only ever worked for whichever game's ra_definitions.txt had last been
copied to ra_achievements.txt by hand. One file, no way to know which game is running,
so a card with five games had a set for one of them.

The set is now kept at _nds/nds-bootstrap/ra/<hash>.txt after every successful fetch,
and read back when a fetch does not happen or does not work.

Keyed by the ROM hash, and that is the design rather than a detail. The GameID comes
from r=gameid, which needs the radio -- so a cache indexed by it could only be found by
a boot that had already done the exact request the cache exists to avoid. The hash is
computed at stage 0b from the file on the card with nothing up, and it identifies
exactly one set.

Both sides go through one function each. raWifiWriteBlockTo() is factored out of the
definitions dump so the cache writes the same bytes the same way -- two writers of one
format is two chances to disagree, and this one is read back by the reader that reads
ra_achievements.txt. The loader writes the block's magic *last*, so a half-written
staging area is never mistaken for a whole one.

Wired into raWifiRestoreDefinitionsFile(), which every failure path in the fetch already
calls, because the fetch streams into that block and destroys what was there even when
it then fails. Cache first, ra_achievements.txt underneath it: the cache is this ROM's
own answer from the server, the hand-managed file is the fallback that cannot know which
game it is for.

What this does not yet cover, stated rather than left to be discovered: a build with the
ladder off entirely never computes the hash, because ra_hash.c sits behind the same
switch. Making the offline path work with no radio at all needs the hash hoisted out
from under that gate -- which is the other half of the sync=off switch this was the
prerequisite for.

## sync=0 in ra.cfg: skip the ladder and play from the cache

*2026-08-09 19:10*

A boot with no access point in range spends forty seconds failing to associate before
the game starts, and a boot with one spends about fifteen re-fetching a set that has

## Carry the launcher's log into the game, in what the set leaves unused

*2026-08-09 19:17*

First half of the in-game log reader, and the half that decides whether the other half
is cheap. A reader inside the game needs the text in memory the ARM9 can reach, and the
obvious route -- hand the in-game menu the log file's cluster -- is a second trip through
loadCrt0, two bootloaders and ce7 for one diagnostic. The definitions block is already
copied into DSi WRAM by the bootloader and already read by the ARM9, so it costs nothing
new.

Laid out after the definitions rather than at a fixed offset, because the definitions are
the tenant with the claim: 'RLG1' and a length at HEADER + defsLength + 1, text after. A
set that fills the block leaves no log and says so, which is the right precedence -- the
game needs the set, the log is a diagnostic. In practice there is usually room: Contra 4's
set is 7,416 of 32,759 bytes and Mario 64's filtered set was 16,382.

The tail rather than the head, because a failure is at the end. Read back off the card
rather than kept in RAM -- the log is written line by line and there was never a buffer
holding all of it, and reading it back is what makes the copy include the summary, which
is the part worth reading. Synced first, or the tail would be missing everything since the
last flush.

Called last of everything that touches the block, because it fills what is left and can
only know how much that is once the definitions are final. Unconditional: the run whose
log is worth reading from inside the game is the one that failed.

The address printed is the final one in DSi WRAM rather than the staging copy, so the RAM
viewer can be pointed at it directly -- deriving it by hand from two constants is exactly
the step that produces a wrong reading, and this session has already lost a run to
quoting the wrong address once.

So the log is readable in-game today through the existing RAM viewer's ASCII column. A
dedicated menu page with line scrolling is the remaining half and is now pure UI, with no

## The fade was hiding the corruption too: stop trusting layer-enable bits

*2026-08-09 20:21*

The deferral build was run on hardware and glitched the whole of stage 2 of Contra 4. That
is worse than before and worse in a way that makes sense: while every notification landed
inside a fade it was invisible *and* harmless, because a screen on its way to black does
not show what the overlay got wrong either. Moving the draw to an ordinary frame moved it
into the middle of a game that is actively using its VRAM.

So the fade was masking two faults, not one, and fixing the visible one exposed the other.
It is the bug already written down as item 3 of the deferred graphical limitations, filed
there as latent with no observed effect. It is not latent.

The false assumption was in surveyBlocks():

    if (!(SUB_DISPCNT & (1u << (8 + i)))) continue;  /* layer off, VRAM not in use */

A layer that is off *this instant* was treated as owning nothing. The survey runs once, at
show time, from a VCOUNT handler at line 0; the game turns the layer back on later, with
its character base still pointing at the block the overlay has since filled with glyphs.
The block was never free, it was momentarily unreferenced by an enabled layer, and those

## The flicker was the tick rate: move the reader's hook to VBlank

*2026-08-09 21:32*

The deferral fix worked -- "RA UNLOCKED, but very subtle, like 1-2 frames, intermittent".
overlayState read 0x4A on Contra 4: layer 1, block 1, extPal off, bit 5 clear so *not* inside
a fade, bit 6 set so it had been held back and released, bit 7 clear so nothing still owed,
with denied, evicted and deniedNoLayer all zero. The whole chain confirmed in one reading, and
the same reading explains the flicker.

My hypothesis was wrong. It was: the game writes SUB_DISPCNT later in the frame than our
line-0 handler, so we win alternate frames. The mechanism is frequency, not phase.

ticks reached 1,132 across a session long enough to score 43,050 points -- thousands of frames
-- while rearmDispstat saturated at 255. Contra 4 clears DISP_YTRIGGER_IRQ constantly, each
re-arm from cardRead() buys roughly one tick, so the reader ran on about 8% of frames. The
overlay has to re-assert its borrowed layer every frame because the game rewrites those
registers every frame, so it was visible about one frame in twelve. That is exactly an
intermittent 1-2 frame flash. Both hypotheses predicted a fast flicker; the tick count is what
separates them, and it was in every snapshot already taken.

So the hook moved to VBlank. Three conditions had to hold for the old one to fire -- the game's
irqTable[2] entry, IRQ_VCOUNT in REG_IE, and the Y-trigger in REG_DISPSTAT -- and the third is
the one a game destroys. VBlank has no third condition: a DS game keeps IRQ_VBLANK on and
irqTable[0] pointed at something of its own, because it needs the interrupt itself.

Three things follow beyond the flicker:

- A tick is a frame again. OVERLAY_SHOW_FRAMES 180 is three seconds rather than half a minute
  and the fade bound is a second and a half rather than minutes. Both numbers were wrong by an
  order of magnitude while the reader ran on a hook that fired 8% of the time.
- The reader stops forcing an interrupt on. RA_READER_ENABLED no longer switches IRQ_VCOUNT on
  for a game that never asked for one; that hook is the colour LUT's alone again.
- rearmDispstat retires at 0, and reading 0 forever is the clearest statement that the fragile
  condition is gone. ticks tracking the frame count is the other half of the same reading.

Installing and re-arming are the same act, so there is one function and no separate install: if
irqTable[0] is not ours, save what is there and put ours in. That is an install the first time
cardRead() runs and a repair every time after, and cardRead is patched into the game's *code*
rather than its interrupt table, so it survives what kills interrupt hooks.

Neither mirrored layout had to change. The game's original handler lives in a word inside
card_engine_header.s beside the stub, loaded PC-relative, rather than in the cardengineArm9
header -- so sizeof(cardengineArm9) is still 0x108 and the patch table still sits at +0x120.
The assembly is guarded by RA_VBLANK_HOOK from ASFLAGS rather than RA_READER_ENABLED, which the
assembler never sees; both are set in the same three Makefiles, and drift fails the link on
raVblankHandler instead of quietly building a cardengine with no hook.

cardengineArm9 is now pinned the way cardengineArm7 is: raCe9OffsetsPinned asserts five field
offsets against what nm reports for the assembly labels. misc.c reads irqTable to install an
interrupt handler now, and a shifted field would not fail to build -- it would write a wild
pointer into a running game's interrupt table. Verified by inserting a field and watching the
build fail.

The window came out ahead: 8 bytes free before, 24 after, because the VBlank hook is cheaper
than the VCOUNT machinery it replaces. Snapshot at 0x027FEEC0. Host suite 578 assertions, 0
failures; both RA_LAUNCHER_WIFI=0 and =2 build.

## The notification says which achievement, not that there was one

*2026-08-09 22:38*

RA UNLOCKED was always a placeholder. With 45 definitions armed, "something fired" stopped
being a reading a long time ago. Three pieces, and the split went the opposite way to the one
this project predicted.

**The record carries a title.** `<id>:<memaddr>` becomes `<id>:<memaddr>\t<title>`. A tab, and
that is what makes it unambiguous rather than convenient: a title contains whatever a person
typed, colons included -- "Chapter 1: Beginnings" -- so it cannot be another colon-separated
field, and it cannot be a second line because the reader treats every line as a definition. A
memaddr has no whitespace anywhere in its syntax and JSON cannot carry a raw tab inside a string
(it arrives as \t, two characters, and unknown escapes are written through verbatim), so a tab
appears in exactly one place in the record and means exactly one thing. A block with no tabs
parses as it always did.

RA_PATCH_TITLE_MAX is sized from the display, not from what RA sends: the strip is 30 usable
characters wide, so storing more would spend block space -- 88% full on a real set -- on text
nothing could draw. And if the label is what does not fit, the label goes and the achievement
stays. Without that guard, adding titles would have silently switched off achievements at the end
of a large set for the sake of thirty bytes of text.

**Two bugs this found, both older than the change.**

A brace inside a string cost an achievement its id. The scanner cleared the pending id on every
`{`, justified by "ID comes first and MemAddr immediately after, so there is no text between them
for a stray brace to sit in". That is not the order RA sends -- the one captured reply has a
Description between the id and the memaddr, and an Author between the memaddr and the Flags field
that commits. A brace in either cleared a good id, leaving an achievement that can never be
reported to the server, silently, because an id-less definition still evaluates and still
unlocks. The scanner tracks quoting for that one rule now.

And the overlay could put a tilemap inside a block it had not borrowed. BGCNT holds the character
base in four bits but the screen base in five, reaching 62K; the DISPCNT offsets that would
extend it are main-engine only. A map inside block 4 or above needs a screen base of 32, the
field truncates, and 2K of tilemap lands in a low block the game may be using. The survey still
examines all eight -- a block the game uses has to be detected wherever it is -- and only the
choice is narrowed to the first four.

**The font moved; the overlay did not.** ra_overlay.h predicted the notification "needs a font and
layout code that will not fit in the cardengine's remaining ~840 bytes, and belongs in a separate
ARM9 binary". Half right. Printable ASCII is 760 bytes against a window with 24 free, so the font
had to go -- but the file stayed. arm9_ra owns the font, the lookup, the centring and the bit
expansion and renders a fixed 32x2 tile strip on the frame an achievement fires, which is the only
moment the id exists and has to survive up to 90 frames of fade deferral. The overlay gets the
address in raSnapshot.overlayText, range-checked by ra_tick() so the drawing side needs no opinion
about where WRAM is, and blits it. Everything that negotiates with the game for VRAM stays exactly
where it was, because that was the expensive part.

It came out ahead: the ARM9 window went from 24 bytes free to 116, the glyph table and bit
expansion being bigger than the blit that replaced them. The arena margin fell from 19,676 to
15,932, which is where a 2K strip and 760 bytes of font should show up.

The font is generated from pixel art rather than typed as hex. A wrong nibble in a hand-typed font
is a letter that looks nearly right in one word and wrong in another -- exactly the class of
mistake a photograph taken hours later cannot diagnose.

Tested where a hardware run would otherwise have paid for it. The nibble order cannot be checked
on hardware without spending a session: a 4bpp tile stores the leftmost pixel in the low nibble,
and reversing it mirrors every glyph, which reads as "the font is wrong" rather than as an
ordering bug. Pinned against L -- upright at nibbles 1-2, which reversal moves to 5-6 -- and
verified by reversing it and watching the check fail. The foot alone would not have caught it,
because `.######.` is symmetric. Also pinned: the strip is cleared whole between calls, so a
shorter message cannot keep the tail of the previous achievement's name, which would read as
plausible rather than as corruption.

RA_LAUNCHER_WIFI=0 and =2 build.
