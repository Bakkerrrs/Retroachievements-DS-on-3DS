## Add RetroAchievements game RAM reader (phase 0)

*2026-08-04 00:06*

Groundwork for RetroAchievements support on real DS hardware, following the
wii-ra-adapter model: run alongside the game, sample its RAM every frame, and
later hand that to rcheevos.

The ARM9 cardengine already owns a per-frame entry point in myIrqHandlerVcount(),
installed into the game's IRQ table by hookIPC_SYNC(). Upstream only installs it
for the colour LUT; install it for the reader too and force IRQ_VCOUNT on so it
fires. Games flagged colorLutBlockVCount already misbehave when a VCOUNT
interrupt is forced on, so that flag vetoes the reader's hook as well.

ra_reader_tick() copies 256 bytes from 0x02000000 into a snapshot buffer in the
cardengine's own .bss once per frame. That .bss is never zeroed -- an injected
binary has no crt0 -- so the header is validated by magic on every tick rather
than assuming an initial state. tools/ra_snapshot_addr.sh reports the buffer
address so it can be found in the in-game menu's RAM viewer.

RA_READER_ENABLED in retail/common/include/ra.h turns all of this off and
restores upstream behaviour exactly.

Also documents the build requirements that are easy to miss (libnds 1.8.0, the
host lzss tool, serial make) and records a blocking finding for phase 2: the
cardengine is linked into a fixed 12K window with 840 bytes free, so rc_client
cannot live there and will need a different home.

## Instrument the RA reader to show where the hook chain breaks

*2026-08-04 01:29*

On hardware the snapshot stayed all zeros across several games, with no crash.
That rules out a bad handler being installed but says nothing about which link
failed, and the buffer itself cannot distinguish "never written" from "not
there": the bootloader copies only the loaded image, which ends exactly where
.bss begins, so an untouched snapshot and an unreadable address look identical.

Record a breadcrumb at each step the reader depends on -- cardRead (the
cardengine has control), myIrqEnable (the game called the patched irqEnable),
hookIPC_SYNC (the install ran), and the tick itself -- plus the three values
that decide whether the install can work: ce9->irqTable, vcountHandlerRef, and
the game's original VCOUNT handler. Any of them initialises the buffer, so the
snapshot becomes readable as soon as any part of the cardengine runs rather than
only once the per-frame hook works.

Also stop installing the hook when irqTable or vcountHandlerRef is null. With a
null table the write would land on the exception vectors, and with a null
handler the forced VCOUNT interrupt would jump to address zero -- both are
plausible given the symptoms.

Align the snapshot to 16 bytes so the in-game menu's RAM viewer, which only
jumps in 0x10 steps, can land directly on it.

## Report the console's real memory map in the snapshot

*2026-08-04 01:46*

The cardengine is linked into a fixed 12K window with ~840 bytes spare, so
neither a full watchlist nor rc_client can live there. The plan is to reserve a
region off the end of the ROM cache, which is exactly how the cheat engine
already gets its own space (dev_CACHE_ADRESS_SIZE_TWLSDK_CHEAT is the plain
TWLSDK size minus 0x4400, and the engine sits at 0x0DFFBC00).

Choosing that region from the constants alone is guesswork: the cache start and
size depend on console model, DSi mode, SDK version and whether cheats are
enabled, and getting it wrong means scribbling on the game's cached ROM. So
report what the cardengine actually sees -- cache start, end, slot geometry, ROM
location, console model and feature bits -- and pick the region from measured
values instead.

Sampled every tick rather than once, because the bootloader fills these in over
the course of setup and an early caller would cache zeroes.

## Probe the memory above the ROM cache as a home for RA state

*2026-08-04 01:55*

Measured on a 3DS: the ROM cache runs 0x0C3EC000 to 0x0DFCC000 (1784 slots of
16K, matching dev_CACHE_ADRESS_SIZE exactly), leaving 208K up to the 32MB top.
Better still, only the first 16MB is mirrored into the 0x02xxxxxx window the
game sees, so everything above 0x0D000000 is memory the game cannot reach even
by accident -- the right place for RA state.

Before committing to it, two things need confirming on hardware: that the MPU
lets the cardengine touch memory past the cache, and that nothing else is
already using it. So write a pattern just above the measured cache end each
frame and check it both reads back and survives to the next frame.

Bounds come from the measured cache end rather than the constants, since those
vary with console model, DSi mode, SDK version and cheats, and being wrong means
writing over the game's cached ROM. The probe also refuses to run when there is
no cache (cacheEnd would be meaningless, and the region could be holding a ROM
loaded into RAM) and on DSi, which has no memory up there at all.

DC_FlushRange after each write keeps the line clean, so the pre-read flush on the
next frame only invalidates and cannot mask a clobber by writing our own stale
copy back out.

## Turn the probe off: memory past the ROM cache is not usable

*2026-08-04 02:03*

The probe faulted on its very first store. Disassembling the reported PC
(0x027FE4A4 -> 'str r3, [r7]', r3 = the probe magic, r7 = 0x0DFCC000) shows the
Data Abort is the write to the probe base itself; the error screen's ADDR column
was showing the value being stored, not the address.

So the 208K between the cache end and the 32MB top is not ours. The cardengine
reaches the cache with the CPU -- readCachedRom() dereferences
ce9->cacheAddress + slot*blockSize directly -- but the mapping stops where the
cache does. The default MPU patch backs this up: region 1 is set to
PAGE_32M | 0x02000000, which does not cover the address the probe used.

Keep the probe code but gate it behind RA_PROBE_ENABLED, off by default, since it
writes to memory to prove a point and the last build crashed games at boot.

The next candidate is memory carved out of the ROM cache rather than found above
it: reduce the slot count so the tail belongs to us. That region is known-good
because the cardengine already reads and writes it on every card read, and it
follows the same trick the cheat engine uses to get its own space -- at the cost
of a slightly smaller cache, which only affects load times.

Also make the snapshot a named global. ra_reader.o now has other statics in .bss,
so the start of its .bss contribution was no longer the snapshot -- which is why
the last reported address was 0x10 low.

## Settle whether the memory past the ROM cache exists, using DMA

*2026-08-04 02:13*

The CPU store that faulted leaves two explanations with opposite conclusions:
either there is no RAM above the cache, or there is and the MPU will not let the
CPU reach it. The first means abandoning the region, the second means widening an
MPU region -- too different to guess between.

DMA decides it. NDMA does not go through the MPU and cannot fault; a transfer to
memory that is not there simply goes nowhere and the read-back comes back wrong.
So round-trip a pattern through the address and see what returns. A control
round-trip through known-good .bss runs first, otherwise a failure at the target
would be ambiguous all over again -- it could just mean the transfer never worked.

Runs once on channel 3, since channels 0 and 1 carry card reads and there is
nothing to gain from poking the hardware every frame. Cache maintenance
brackets the transfers so the CPU is comparing what the DMA actually moved and
not its own stale lines.

The probe buffers are 16 bytes rather than 64: three of them at 64 pushed
arm9_twlsdk_dldi's .bss past the end of its region, and four words is plenty to
tell a real round-trip from a dead one.

## Dump the MPU regions; the memory above the cache is real

*2026-08-04 02:19*

The DMA round-trip came back clean on hardware: pattern written to 0x0DFCC000
and read back intact, with the known-good control passing too. So the RAM above
the ROM cache exists and the earlier Data Abort was the MPU refusing the CPU, not
missing memory. The 208K is recoverable.

The in-game menu already solves this problem for its RAM viewer: changeMpu()
widens protection region 3 to base 0x08000000 / 128MB, which covers the whole
0x0C-0x0D range, and revertMpu() puts it back on exit. It reverts because
clobbering a region the game is using can break the game -- so the clean version
for a permanently-running reader is to claim a region the game does not use.

That needs knowing which regions are spare, so read all eight CP15 protection
region registers and report them. ARM assembly because MRC has no Thumb encoding
and the cardengine builds as Thumb.

The DMA probe is removed now that it has answered its question: three buffers
plus its code pushed arm9_twlsdk_dldi's .bss past the end of its region, and that
variant has almost nothing to spare.

## Check whether the memory above the cache is just a mirror

*2026-08-04 02:24*

The MPU dump undoes the previous conclusion. Region 3 is already 0x08000035 --
base 0x08000000, 128MB -- which spans both 0x0C3EC000, where the cardengine's
stores to the ROM cache work, and 0x0DFCC000, where the store faulted. Same
region, same permissions, so the MPU cannot be what distinguishes them, and
'the RAM is real and only the MPU blocks it' was wrong.

What the DMA round-trip actually proved is weaker than it looked: if main RAM
ends at 16MB then 0x0DFCC000 mirrors 0x0CFCC000, and writing then reading the
same existing byte succeeds whether or not there is anything new up there. The
test could not tell the two apart.

So test for the alias directly: sample the candidate 16MB lower, write the
pattern at the target, and sample it again. If it changes to match, they are the
same memory and the region is not free after all.

(Region 2 is disabled and therefore genuinely spare, which stays useful whatever
this returns.)

## Read the MPU access permissions; the region is real memory

*2026-08-04 02:31*

The mirror test came back negative: writing at 0x0DFCC000 left 0x0CFCC000
untouched and the target read back the pattern, so that memory is real and
distinct, not an alias of RAM 16MB lower. Both earlier explanations are now dead
-- it is neither missing memory nor a region that fails to cover the address,
since region 3 spans 0x08000000 +128MB and covers the cache and the fault site
alike.

What is left is permissions, and there is a detail that fits: the cardengine only
ever *reads* the ROM cache with the CPU. Fills go through NDMA. So a region that
permits loads and denies stores would go unnoticed in normal operation and fault
exactly where this probe did.

Read the extended access permission registers to confirm, plus the cacheable and
bufferable bits, which the RA region will need set correctly whatever the answer.

The mirror test is removed now that it has answered, freeing exactly the space
these four fields need in the tightest cardengine variant.

## Add an on-screen notification channel, starting with a flash

*2026-08-04 02:43*

An unlock nobody can see is worth little, so this moves feedback ahead of the
remaining reader work. It also replaces reading hex out of the RAM viewer as the
way to observe anything, which is worth having for its own sake.

Text over a running game needs resources the game owns -- a spare VRAM bank, a
spare background layer, palette entries -- and how much is spare is entirely
game-dependent. The in-game menu's screenshot code shows the detection trick
(a VRAM bank control byte with bit 0 clear is unmapped), but it only has to find
one bank once, not composite every frame.

So split it: ship a channel that works now, and measure before designing the one
that might not. Master brightness needs nothing from the game, so the first
notification is a flash of both screens, pulsed so it reads as a notification
rather than a glitch. The previous register value is saved and restored, since
games drive master brightness for fades and clobbering it would leave one stuck
bright or dark.

Alongside it, report DISPCNT for both engines and all nine VRAM bank control
bytes, so the text overlay can be designed from what real games leave spare.

The flash fires on a ten-second timer for now, behind RA_TOAST_DEMO_INTERVAL,
so the channel can be confirmed before there is any achievement logic to drive
it.

## Report the BG control registers to place the overlay's tiles

*2026-08-04 02:48*

Measured on Space Invaders Extreme: the main engine has BG1-3 free and the sub
engine has BG0 free, and VRAM bank H is disabled. So a text overlay is possible,
which was the open question.

The catch is mapping, not availability. No bank is mapped to main BG at all --
A and B are 3D texture, since main BG0 is the 3D layer -- so the main engine's
three free layers have nowhere to put tiles. Bank H can map to sub BG, but bank C
is already the sub BG and the two would overlap at 0x06200000.

That leaves the sub engine's free BG0 with its tiles and map inside a hole in
bank C. Whether a hole exists depends on which character and screen base blocks
the game has taken, which is exactly what BGxCNT records -- so read them for both
engines, plus bank I, which the earlier two-word read of the bank controls missed.

The flash notification is confirmed working on hardware without disturbing the
game, so the universal fallback is secured whatever the overlay turns out to
allow.

## Draw text over the running game to prove the overlay works

*2026-08-04 02:59*

Replaces the flash with the thing that actually needed proving: compositing text
onto a running game. Uses the sub engine's BG0, which the display measurements
found free with priority 0 so it draws above the game's layers, with the map at
screen base block 10 and tiles at character base block 2 -- both inside the
0x06205000-0x0620BFFF gap between the game's maps and its own tiles.

4bpp matters and is not an arbitrary choice. The game's 256-colour layers read
the extended palette, since DISPCNT bit 30 is set and bank H is disabled, so a
256-colour overlay would render black. A 16-colour layer uses the standard
palette and avoids that entirely.

Registers are reasserted every frame because the game rewrites DISPCNT and the BG
control registers itself; holding the layer means re-claiming it.

Glyphs are stored in message order rather than as a font, so there is no lookup
table and no unused glyph. That, plus removing the measurement scaffolding the
docs now record -- the MPU dump, the display registers, the hook breadcrumbs, and
a 256-byte window cut to 32 -- is what makes this fit at all. .bss had already
grown past __sp_usr into the stacks before the trim.

Which is the point about the final version: a real font with layout will not fit,
so it belongs in the separate ARM9 binary. This proves the mechanism, not the
implementation.

## Fix the overlay never initialising, and add a failure discriminator

*2026-08-04 03:04*

Nothing appeared on hardware. The cause was a plain bool guard: the cardengine's
.bss is never zeroed -- the bootloader copies only the loaded image and an injected
binary has no crt0 -- so  started as whatever was in RAM, and any
non-zero garbage meant prepare() never ran. The registers were still set every
frame, so BG0 was enabled and showing tile 0 everywhere, which in 16-colour mode
is transparent. Invisible rather than obviously broken.

This is the exact trap already documented in ra.h for the snapshot, walked into
again in a new file. Use the same magic-value guard.

Also reassert the palette entry and the message's map row every frame rather than
once, so the overlay survives the game writing to palette RAM or that VRAM.

And draw a solid bar above the text, so the next test distinguishes two very
different failures: a bar with no letters means the glyph expansion is wrong,
nothing at all means the layer is not reaching the screen.

## Write the overlay tiles as words: DS VRAM ignores byte writes

*2026-08-04 03:25*

The palette read back white, the map read back exactly as written, and the
registers were already confirmed. Every verifiable link was correct -- and they
were all correct for the same reason: they were halfword writes.

The one link never verified was the tile data, and it was built a byte at a time
through a vu8*. DS VRAM ignores 8-bit writes, so the tiles were never written.
Every pixel stayed at index 0, which in 16-colour mode is transparent, so a fully
configured layer drew nothing. That accounts for every observation, including why
the solid bar was invisible too.

Build each tile row as a 32-bit word instead. Also point the window at the first
glyph tile, so the fix is verified rather than assumed.

## Repair the overlay's tiles when the game reclaims that VRAM

*2026-08-04 03:29*

Text over a running game works: RA UNLOCKED and the solid bar both appeared on
hardware. Feasibility is settled.

They then vanished, and the tiles were the one thing written once rather than
every frame. A clobbered 4bpp tile reads as index 0, which is transparent, so the
overlay disappears silently instead of looking wrong -- the same failure mode as
never writing the tiles at all.

So check a sentinel word each frame and rewrite the tiles if it has changed,
counting the repairs into the snapshot. That both keeps the overlay up and answers
whether the game really is reusing that VRAM, rather than assuming it.

Worth noting for the real implementation: if the game reclaims this region, a
notification that simply reasserts itself is fighting the game for VRAM. The final
version needs to re-detect what is free rather than hold a spot it chose once, and
back off instead of corrupting the game's graphics when nothing is free.

## Make the overlay borrow VRAM per notification instead of holding it

*2026-08-04 03:36*

The graphics corruption was the overlay's fault, and the registers say exactly how:
the game moved its BG2 character base to block 2, the block the overlay had chosen
at boot, and the repair loop kept rewriting the game's tiles underneath it. Two
repairs recorded, and both were the overlay destroying the game's graphics.

So a game's VRAM layout is not fixed, and a spot that is free at boot is not free
later. The overlay now negotiates rather than insists:

- picks a character base block only when about to show, from the live registers,
  surveying what all the enabled layers use for both tiles and maps
- stays quiet if nothing is spare, rather than corrupting the game
- re-surveys every frame while visible and gives the block back immediately if the
  game starts using it
- restores BG0CNT, the DISPCNT bit and the palette bank it borrowed
- shows for a bounded time, which is what a notification wants anyway

Tiles and map both fit in one borrowed 16K block: tiles at its start, map 2K in.
Counters for shows, denials and evictions go into the snapshot so the negotiation
is observable instead of inferred from glitches.

## Borrow the background layer at show time, not just the VRAM block

*2026-08-04 03:43*

The counters say the negotiation works -- 4 shows, 0 denials, 1 eviction -- and the
graphics recovering when the notification ends confirms the restore is sound.

But the remaining corruption has the same cause as the first: an assumption that a
resource is the overlay's by right. BG0CNT read back as 0x0098 with the DISPCNT bit
set, so this game enables its own sub BG0 at times, with a character base of its
own. Treating BG0 as ours displaced a layer the game was using.

So choose the layer at show time too, from whichever the game currently has switched
off, and stay quiet if all four are in use. The block survey now takes the borrowed
layer as a parameter rather than assuming it is BG0.

Scroll registers are per layer, four bytes apart, so a borrowed BG2 would have kept
BG2's scroll and drawn the text off-position; zero and restore the right ones.

## Document the on-screen notification, confirmed working on hardware

*2026-08-04 03:47*

Text draws over a running DS game on a 3DS without pausing it, and the game keeps
running normally underneath. That was the open feasibility question and it is
answered.

Records how the overlay borrows a layer and a VRAM block per notification and hands
them back, why it has to work that way, and what it means for the real thing --
notably that it is opportunistic: on a game that keeps all four sub layers busy

three will bite again elsewhere: DS VRAM ignores 8-bit writes, the cardengine's
.bss is never zeroed, and a game's display resource allocation changes while it
runs.

Trims the phase 0 section where it had gone stale -- the snapshot layout is now
documented by pointing at the struct, since it changes with whatever is being
diagnosed rather than being a fixed format.
