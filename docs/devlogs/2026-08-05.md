## Phase 1: read a watchlist with pointer chains, not one fixed window

*2026-08-05 02:11*

The reader now evaluates up to RA_WATCH_MAX watches per frame. A watch is
either a direct address or a pointer chain: read the word at the base, add an
offset, read the word there, add another, then read the value.

The chain is walked from scratch every tick and the resolved address is never
kept. That is the whole reason chains exist -- the structure they point into
moves when the game changes scene, so an address that was right last frame
now reads a plausible number out of whatever is there instead.

Nothing read out of the game is trusted. A pointer the walker is about to
follow must be word-aligned and in main RAM; the final address must be
readable and aligned for its size. Following a garbage pointer would take a
Data Abort inside the game's own VCOUNT handler, which is a crash rather than
a bad reading. A chain that does not resolve is reported, not an error: games
null their pointers between scenes and the reader has to survive that. Each
watch carries its own status so a RAM viewer shows which one broke and where.

Three default watches prove the machinery without needing a game address,
which is phase 2's job: one direct read of a register that really changes,
and two self-test chains walking one and two indirections to the frame
counter. Their values climbing is proof a chain resolved against live memory.

VCOUNT is sampled before and after the tick, so the per-frame cost is now
measured in scanlines instead of argued about -- open question #2. The game
owns the hardware timers, so it is the only clock available.

Two supporting changes, both from finding out how little room is left:

- tools/ra_reader_test.c builds ra_reader.c verbatim for the host, linked at
  0x02100000 with a page mapped at 0x04000000 so the reader's own globals sit
  inside the main RAM range it validates against. The self-tests resolve for
  the same reason they will on hardware, not because a check was relaxed. It
  covers every failure status, and it caught BAD_POINTER/BAD_TARGET being
  expected backwards. CI runs it before the ARM build.

- The stacks are placed by subtracting from the top of the cardengine window,
  so they sit directly above .bss with nothing between them. Overrunning was
  silent: the region only overflows once .bss passes the very top, and long
  before that the stacks are running through .data on the first call. The
  eight linker scripts that carry the reader now assert __bss_end <= __sp_usr,
  and ra_snapshot_addr.sh reports the remaining margin per variant.

840 bytes free was never the real ceiling either -- cardenginei_arm9 is not
the tightest of the eight variants. Phase 1 costs about 520 of them, which is
why RA_WATCH_MAX and RA_CHAIN_MAX are documented knobs and why this one file
is built -Os. The conclusion is unchanged and better supported: code that
grows does not belong in the cardengine.

Not yet confirmed on hardware; docs/retroachievements.md says what to look
for in the RAM viewer.

## Measure the cardengine budget against the right symbol, and scope the reader

*2026-08-05 02:22*

Verified phase 1 against the pinned toolchain (devkitARM r65 / gcc 14.2, pulled
out of the devkitpro/devkitarm:20241104 image) rather than trusting a local
gcc, and two claims in the previous commit turn out to be wrong.

The free space was never measured against the right symbol. __sp_usr is where
a normal NDS program's user stack starts; nothing in retail/cardenginei/
references it, or __sp_svc, or __sp_irq. Injected code runs on the game's
stack -- those symbols come from the stock linker script this was derived from
and are vestigial. The real ceiling is __vram_top, 0x260 bytes higher. So the
"840 bytes free" this project has been working from was 1,448, and the story
about the stacks silently eating .bss cannot happen: ld already errors when a
section leaves the region. The assert now checks __bss_end <= __vram_top,
which is a clearer message for the same condition rather than a new one, and
ra_snapshot_addr.sh reports the same margin.

With that corrected, phase 1's real cost is 500 bytes against the 544 that
cardenginei_arm9 actually had, leaving 44. Thin, and deliberately left thin
rather than trimmed further: the useful conclusion is not that it fits but
that nothing else will.

Eight variants compiled the reader and only three could ever run it. The four
*_dldi ones are flashcard builds the fork does not target, and they are the
tightest of the eight -- after phase 1 two of them would have had 176 bytes
left against a reader costing 550, so they could not have carried it at all.
The GSDD ones never tick: hookIPC_SYNC() is compiled out under #ifndef GSDD,
so they linked the reader and never installed the handler. RA_READER_ENABLED
now defaults to 0 for both groups, overridable on the command line. All eight
variants link on the pinned toolchain.

Also dropped ra_reader_watch_clear(). It is the obvious counterpart to _add
and phase 2 will want it, but it has no caller today and costs 44 bytes --
the whole remaining margin. The host test does that state change directly.

One build note worth recording: the cardengine Makefiles generate their linker
scripts with $(CPP) -P ... $@, which needs CPP to be a preprocessor driver
that accepts an output filename. devkitARM sets no CPP, so make's default
$(CC) -E applies, and gcc -E treats the second filename as another input --
it fails with "linker input file not found: cardengine.ld". Building needs
make CPP=arm-none-eabi-cpp. This repository's Actions have never run, so the
workflow is unproven either way; that is in the docs now rather than left for
whoever triggers the first build.
