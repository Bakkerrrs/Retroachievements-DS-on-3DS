## The reader spends too much of the game's VBlank, and two games say so

*2026-08-20 02:48*

Confirmed, and it is ours. Chrono Trigger freezes on entering Leene Square --
always, same screen, no menu involved -- and the same build tears on the world
map. Both stop when raRearmVBlank() returns immediately, in a build where the
binary is still staged, so the memory accounting is identical and only the
execution is gone.

Four measurements pin it. The cache column is what kills the memory
explanations: 205 KB of ROM cache passes and 256 KB freezes, so it is not a
size effect, which takes out dsiWramCacheSize() and the isROMLoadableInRAM()
threshold together. Nor is the window oversized -- rcheevos links to 68 KB and
its arena measures 91.8% full on a real set, 11 KB spare. What is left
correlates perfectly with the reader executing.

raVblankHandler chains to the game's handler first, so the game's own VBlank
work is not delayed, but the interrupt stays open and everything after it is
pushed later. Spill past the blanking period and the game's next display work
lands in the visible frame. Where the game has slack that is tearing; where it
has none it is fatal.

The cost scales with the set: Contra 4's 45 definitions have never torn on any
build. The init path already respects that axis with a 120-of-263-scanline
budget. The steady-state path measures lines and linesMax and caps nothing.

Running less often is already known to be acceptable here: on the old VCOUNT
hook the reader ran on about 8% of frames and achievements still fired. So a
self-tuning throttle -- measure the cost, sit out proportionally many frames --
is cheap rather than a compromise. Skipping whole frames rather than splitting
the set keeps rcheevos' delta operators coherent.

Not built yet. Noted for whoever writes it: this binary's .bss is never zeroed,
so a skip counter needs initialising with the rest of the state.

Documentation only; no code changed.

## Budget the reader's frame against what is left of the blanking period

*2026-08-20 02:55*

The steady-state path measured its cost and capped nothing, so a set larger
than the blanking period paid for it out of the game's visible frame -- tearing
on Chrono Trigger's world map, and a dead ARM9 entering Leene Square where the
game had no slack.

The budget is not a constant. The reader is chained after the game's own VBlank
handler, so what remains depends on what the game just did, and startLine is
already sampled: room is RA_SCANLINES_PER_FRAME - startLine when that lands
inside blanking. Measuring it rather than assuming it is what makes this right
on a game nobody has tested, which is the case that produced the bug.

ra_rc_frame_skip(lines, room) then says how many frames to sit out so the
average lands inside that room. Contra 4 is untouched -- 28-31 scanlines
against 71 -- because a set that fits is never throttled.

Whole frames are skipped, never a partial set: rc_runtime_do_frame() updates
every memref and evaluates every trigger in one call, so splitting it would
hand the delta operators two different notions of "previous". Skipping is a
lower sample rate, and the old VCOUNT hook already shipped one at 8% of frames
with achievements still firing.

Three things the writing turned up. A cost of zero must never throttle: on a
host RA_VCOUNT never advances so every frame measures free, and the first
version throttled to the floor whenever room was zero, which silently stopped
the suite's own frame ticks from evaluating -- one existing test caught it. The
decision is extracted as a pure function for the reason ra_queue.c is pure, and
the suite drives it directly with the boundary cases. And the earlier note about
.bss needing hand-initialisation was wrong: ra_startup() zeroes it, which is the
guarantee stateMagic already leans on.

RA_RC_FRAME_SKIP_MAX is 3, bounding the throttle rather than the cost so a
pathological reading cannot stall detection for seconds.

Built with tools/ra_release.sh, host suite green. Not yet confirmed on hardware.
