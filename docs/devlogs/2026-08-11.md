## Share the queue scratch: a second copy cost 8 KB of the launcher's heap

*2026-08-11 23:52*

Two hardware logs from the same console, same game, same boot:

    build with the menu   heap after hash 20480 safe + 9984 free
    build without it      heap after hash 28672 safe + 10912 free

raWifiStagePending() had declared statics of its own -- a second
RA_QUEUE_BYTES buffer and a second raQueue, which now carries a game code
and a title per entry. That is 8,192 bytes of safe heap for a copy of
something raWifiSubmitQueue() already had, and it can share it: the staging
pass runs only after the submit pass has returned.

Both move to file scope under their existing names, so the bodies are
untouched and `file` stays an array -- the eight `sizeof(file)` uses in the
submit path keep meaning 3,072 rather than the size of a pointer.

The measurement was in the first log this investigation produced and I read
past it twice. Stage 15 staged all 45 definitions and the run reached 15 of
15, so the ladder looked healthy and I concluded the statics were exonerated
-- from the absence of a failure, in a launcher whose failures would not
have shown up there anyway. The number that mattered was printed beside the
success on every boot.

This does not yet explain the boss-fight crash; the counts point at the menu
build (3 of 3) over cb14541 (1 of 2, on the boot straight after a menu build
left a 3,072-byte queue file for a 2,048-byte reader). It removes the one
regression that is measured rather than suspected.

Suite passes with 0 failures. Builds clean at RA_LAUNCHER_WIFI=0 and =2.
